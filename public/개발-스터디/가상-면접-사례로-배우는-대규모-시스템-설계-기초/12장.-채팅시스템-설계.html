채팅 서비스 접속 key-alive header 동작 방식

Keep-Alive 헤더는 TCP 연결을 계속 유지해서 여러 요청을 같은 연결로 처리하도록 하는 HTTP 연결 관리 메커니즘

HTTP/1.1부터 Persistent Connection(Keep-Alive)

TCP 연결 1개  
여러 HTTP 요청/응답 처리

keep-alive Header 예시

GET /chat HTTP/1.1  
Host: example.com  
Connection: keep-alive  
Keep-Alive: timeout=60, max=100

Keep-Alive는 클라이언트와 서버가 HTTP 프로토콜 규칙에 따라 연결을 계속 유지하겠다고 합의하는 것

Keep-Alive가 없으면 항상 연결이 끊기나?

HTTP 버전기본 동작
HTTP/1.0요청 처리 후 TCP 연결 종료
HTTP/1.1기본적으로 Keep-Alive (연결 유지)

Keep-Alive는 클라이언트와 서버의 약속인가?

네. 정확히 말하면 HTTP 프로토콜 규칙에 따른 합의

그 약속은 누가 만든 것인가?

이 규칙은 **HTTP 표준 문서(RFC)**에서 정의되어 있습니다.

대표적인 RFC

  • RFC 2068 (HTTP/1.1 초안)
  • RFC 2616 (HTTP/1.1)
  • RFC 7230 (HTTP/1.1 message syntax)
  • RFC 9112 (최신 HTTP/1.1 spec)
    여기서 Persistent Connection 규칙이 정의됩니다.
Persistent connections allow multiple HTTP requests and responses
to be carried over a single TCP connection.

왜 WebSocket 서버는 Keep-Alive가 아니라 heartbeat(ping/pong)를 사용해야 하는가

HTTP Keep-Alive의 목적

Keep-Alive는 HTTP 요청 재사용을 위한 기능입니다.

WebSocket은 HTTP가 아니다

WebSocket은 처음에만 HTTP를 사용합니다.

GET /chat HTTP/1.1  
Upgrade: websocket  
Connection: Upgrade

Half-open connection 문제

Client ----X---- Server

서버 입장에서는

connection still exists

서버는 계속

connection count 증가
memory 유지
session 유지

WebSocket은 HTTP가 아니기 때문에 Keep-Alive가 의미 없고
대신 heartbeat(ping/pong) 으로 연결 생존 여부를 확인합니다.

TCP는 연결 상태를 계속 확인하지 않는다.

TCP는 데이터가 오갈 때만 연결 상태를 확인합니다.

데이터 전송 없음 → 연결 상태 확인 안함

Client ───────── TCP ───────── Server  
	ESTABLISHED

다음 이벤트가 발생해야 연결 상태를 알 있다.

이벤트상태 변화
FIN정상 종료
RST비정상 종료
데이터 전송 실패오류 발생

웹소켓이 Http로 시작하는 이유

1️⃣ 기존 웹 인프라와 호환되기 위해서
2️⃣ 브라우저 보안 모델(Same-Origin / Cookie / Header)을 그대로 사용하기 위해서

이 두가지 덕분에 대부분의 방화벽과 네트워크 장비를 통과할 수 있다.

WebSocket RFC 6455

Run over HTTP ports  
and coexist with HTTP infrastructure

HTTP 인프라와 공존하기 위해서 HTTP Upgrade 사용

웹 환경에는 이미 이런 인프라가 있습니다.

Browser
   │
HTTP Proxy
   │
Load Balancer
   │
Firewall
   │
Web Server

이 인프라는 대부분 HTTP 트래픽만 통과시키도록 설계되어 있습니다.

  • 회사 방화벽
  • HTTP proxy
  • CDN
  • corporate network
    HTTP로 시작하면 브라우저 보안 모델을 그대로 사용할 수 있습니다.

쿠키 인증

JWT 인증

Authorization: Bearer token

헤더 전달 가능

Same Origin Policy

WebSocket 연결 관리

1️⃣ Heartbeat (ping / pong)

  • 목적: 죽은 연결(dead connection) 감지
  • 방법
    Server → ping
    Client → pong
  • pong 없으면 connection 종료

2️⃣ Connection Registry

서버에서 연결을 메모리 구조로 관리

userId -> WebSocket session  
roomId -> session set

채팅 메시지 전송 시

roomId -> session list -> send

3️⃣ Idle Timeout

일정 시간 활동이 없는 연결 종료

idle timeout = 5 min

목적

  • 불필요한 연결 제거
  • 리소스 절약

4️⃣ Connection Limit

서버당 최대 연결 수 제한

max connections = 50k

목적: 서버 과부하 방지

5️⃣ Horizontal Scaling

여러 WebSocket 서버로 분산

Client  
  ↓  
Load Balancer  
  ↓  
WS Server 1  
WS Server 2  
WS Server 3

6️⃣ Reconnect 전략

네트워크 끊김 시 재접속 제어
목적: reconnect storm 방지
