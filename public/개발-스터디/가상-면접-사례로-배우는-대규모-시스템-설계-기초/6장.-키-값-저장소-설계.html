6장. 키-값 저장소 설계

Feb 08, 20269 min read

단일 키-값 저장소

  • 키-값 쌍 전부 메모리에 해시 테이블에 저장
  • 모든 데이터를 메모리 안에 두는 건 불가능

개선사항

  • 데이터 압축
  • 자주 쓰이는 데이터만 메모리에 두고 나머지 디스크 저장

하지만 많은 데이터 저장하려면 분산 키-값 저장소 필요

분산 키-값 저장소

키-값 쌍을 여러 서버에 분산시킨다.
분산 시스템을 설계할 때는 CAP 정리 고려해서 설계해야 한다.

CAP 정리:

  • C(consistency) = 일관성 = 어떤 노드에 접근해도 같은 값
  • A(availability) = 가용성 = 일부 노드 장애 발생해도 응답
  • P(partition tolerance) = 파티션 감내

파티션 감내가 뭐지? 가용성이랑 차이가 뭐지?

CAP에서 P(Partition tolerance)랑 A(Availability)는 둘 다 “안 죽는 것처럼” 보이거든.  
근데 버티는 대상이 다르다고 보면 딱 정리돼.

- P (파티션 감내)
    👉 “네트워크가 찢어져도 시스템 전체가 죽지는 않는다”
    👉 “올바른 응답”이나 “응답을 반드시 준다”는 보장은 없다.
    
- A (가용성)
    👉 “요청을 보내면 항상 응답을 돌려준다 (성공이든 실패든)”

파티션 감내

파티션 = 두 노드 사이 통신 장애 발생
파티션 감내:
네트워크에 파티션이 생기더라도 시스템은 계속 동작하여야 한다는 뜻

통상 네트워크 장애 피할 수 없으므로, 분산 시스템은 반드시 파티션 문제를 감내할 수 있도록 설계되어야 한다. 그러므로 실세계에서 CA 시스템은 존재하지 않는다.

데이터 파티션

데이터 파티션 단위로 나눌 때 다음 두 가지 중요

  • 데이터를 여러 서버에 고르게 분산할 수 있는가
  • 노드가 추가되거나 삭제될 때 데이터의 이동을 최소화 할 수 있는가

데이터 다중화

높은 가용성과 안정성 확보를 위해서, 데이터를 N개 서버에 비동기적으로 다중화할 필요가 있다. 여기서 N은 튜닝 가능한 값

데이터 일관성

여로 노드 다중화된 데이터는 적절히 동기화가 되어야 한다.
정족수 합의(Quorum Consensus) 프로토콜을 사용하면 읽기/쓰기 연산 일관성 보장할 수 있다.

  • N = 사본 개수
  • W = 쓰기 연산 정족수
  • R = 일기 연산 정족수
    W = 1은 데이터가 한 대 서버에만 기록된다는 뜻이 아니다. 쓰기 연산이 성공했다고 판단하기 위해 중재자(coordinator)는 최소 한 대 서버로부터 쓰기 성공 응답 받아야 한다는 뜻이다.
    ex. R = 1, W = N: 빠른 읽기 연산에 최적화된 시스템

일관성 모델

데이터의 일관성 수준을 결정

  • 강한 일관성: 모든 읽기 연산은 가장 최신 결과 반환
  • 약한 일관성: 가장 최신 결과 반환 못할 수 있음
  • 결과적 일관성: 약한 일관성의 형태, 갱신 결과가 결국 모든 사본에 반영
    강한 일관성은 가용성에 적합하지 않다. 모든 사본에 현재 쓰기 연산 결과가 반영될 때까지 읽기/쓰기 금지하기 때문이다.

다이나모 또는 카산드라는 결과적 일관성을 채택
쓰기 연산이 병렬적으로 발생하면 시스템 저장된 값 일관성 깨질 수 있는데 이 문제는 클라이언트가 해결해야 한다.

비 일관성 해소 기법: 데이터 버저닝(versioning)

버저닝과 벡터 시계:
사본 일관성 깨짐 문제 해소

클라이언트가 해결해야 한다는 의미는?

클라이언트가 읽기하면:
[
  { "value": "Alice Kim", "version": v1 },
  { "value": "Alice Lee", "version": v2 }
]
- 여러 버전이 함께 반환됨
- 충돌 사실과 힌트(벡터 시계)로 어떤 데이터가 최종적으로 옳은지 클라이언트가 결정

단점:
충돌 감지 및 해소 로직이 클라이언트에 들어가야 하므로, 클라이언트 구현이 복잡

장애 처리

모든 노드 사이에 멀티캐스팅 채널을 구축하는 것이 서버 장애 감지하는 손쉬운 방법이다.

가십 프로토콜: 분산형 장애 감지 솔루션
동작원리:

  1. 각 노드 멤버십 목록를 유지한다.
  2. 각 노드는 주기적으로 자신의 박동 카운터 증가
  3. 각 노드 무작위로 선정된 노드들에게 주기적으로 자기 박동 카운터 목록을 보낸다.
  4. 박동 카운터 목록 받은 노드는 멤버십 목록을 최신 값으로 갱신
  5. 받은 멤버십 목록에서 지정 시간 동안 갱신되지 않은 노드가 있다면 장애 상태로 간주
멤버십 목록은 각 멤버 ID와 그 박동 카운터 쌍의 목록이다.

일시적 장애 처리

느슨한 정족수 프로토콜(sloppy quorum)과 단서 후 임시 위탁(hinted handoff)

1. sloppy quorum(느슨한 정족수)

  • 정족수 조건은 유지
  • 노드 집합만 느슨해짐
  • 가용성 우선 (AP 성향)
원래 책임 노드: A, B, C
B 장애 발생

→ A, C, D 에 write 성공
→ W=2 만족

2. hinted handoff(단서 후 임시 위탁)

Sloppy quorum만 쓰면 생기는 문제:
“그럼 B가 복구되면? B는 데이터 못 받았잖아?”

동작 방식

  1. B가 장애 → D가 대신 데이터 저장
  2. D는 이렇게 기록함:
"value = X" "hint = 이 데이터는 원래 B의 것"
  1. B가 복구됨
  2. D → B에게 누락된 데이터 전달
  3. hint 제거

📌 핵심:

  • 임시 대리 저장
  • 정상 복구 시 원래 자리로 돌려줌

영구적 장애 처리

머클 트리

대량의 데이터 집합이 “같은지 다른지”를 아주 적은 비용으로 증명하기 위한 해시 기반 트리 구조

  • 요약
  • 부분 비교
  • 증명
    전체 데이터를 직접 비교하지 않고, 해시만 비교해서 어디가 다른지 정확히 집어내는 구조

아이디어:

  1. 각 노드는 자신의 데이터를 해시 트리로 요약
  2. 루트 해시부터 비교
  3. 다르면 → 하위 노드로 내려감
  4. 다른 부분만 정확히 찾아냄

문제 상황:
노드 B가 죽고 새 노드 B’가 들어옴

A: key1, key2, key3
C: key1, key2, key3
B': key1, key3   (key2 누락)

👉 뭐가 빠졌는지 모름
👉 전체 스캔은 너무 비쌈

전체 데이터
 ├── hash(A)
 │    ├── hash(A1)
 │    └── hash(A2)
 └── hash(B)
      ├── hash(B1)
      └── hash(B2)

📌 장점

  • 네트워크 비용 ↓↓↓
  • 전체 데이터를 비교하지 않음
  • 불일치 범위만 동기화
