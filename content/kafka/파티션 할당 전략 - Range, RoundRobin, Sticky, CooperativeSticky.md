# 리밸런싱 때 파티션을 컨슈머에게 어떻게 나눠줄까?

리밸런싱이 "누가 죽었는지 감지하는 문제"라면, 파티션 할당 전략(Assignor)은 "그럼 남은 파티션을 컨슈머들에게 실제로 어떻게 나눠줄지" 정하는 문제다. `partition.assignment.strategy` 설정으로 고를 수 있고, 전략마다 목표가 다르다.

## 1. RangeAssignor (오래된 기본값)

**동작**: 토픽별로 따로따로 계산한다. 한 토픽의 파티션을 정렬하고, 그 토픽을 구독하는 컨슈머들도 이름순으로 정렬한 다음, 파티션을 앞에서부터 순서대로 나눠준다. 나누어떨어지지 않으면 앞쪽 컨슈머가 하나 더 가져간다.

예시: 토픽 T1이 파티션 3개(0,1,2), 컨슈머 C1·C2가 구독 중이면 → C1: [0,1], C2: [2].

**문제점**: 이 계산이 **토픽마다 독립적으로** 일어난다. 그룹이 T1, T2, T3를 함께 구독하면, 매번 "정렬상 앞쪽"인 C1이 계속 여분의 파티션을 가져가게 된다. 토픽이 여러 개일수록 C1과 C2 사이 부하 불균형이 누적된다.

## 2. RoundRobinAssignor

**동작**: 토픽별로 나누지 않고, 그룹이 구독하는 **모든 토픽의 모든 파티션을 하나의 목록으로 합쳐서** 컨슈머들에게 순서대로 하나씩 돌아가며 배분한다.

예시: T1(P0,P1,P2), T2(P0,P1,P2), 컨슈머 C1·C2 → 전체 파티션 목록 [T1P0, T1P1, T1P2, T2P0, T2P1, T2P2]을 C1, C2, C1, C2, C1, C2 순으로 배분 → C1: [T1P0, T1P2, T2P1], C2: [T1P1, T2P0, T2P2]. Range보다 훨씬 고르게 나뉜다.

**단점**: 그룹 내 모든 컨슈머가 **똑같은 토픽 집합을 구독**하고 있어야 잘 작동한다. 컨슈머마다 구독 토픽이 다르면 계산이 꼬여서 오히려 불균형해질 수 있다.

**결정적 단점**: 균형은 좋지만, 리밸런싱이 일어날 때마다 **파티션 배정을 처음부터 완전히 새로 계산**한다. 컨슈머 C3가 하나 더 추가되면, C1과 C2가 원래 잘 처리하고 있던 파티션까지 포함해서 전체를 다시 섞어버린다.

## 3. StickyAssignor

**목표**: RoundRobin만큼 균형 잡힌 분배는 유지하면서, **리밸런싱 전후로 파티션 이동을 최소화**한다.

**왜 이동을 최소화하는 게 중요한가**: 파티션이 다른 컨슈머로 넘어가면, 새로 받은 컨슈머는 그 파티션에 대해 아무 상태(로컬 캐시, DB 커넥션 워밍업, Kafka Streams라면 로컬 스토어 등)가 없어서 다시 준비해야 한다. 매번 전체를 재분배하면 이 비용이 리밸런싱마다 반복된다.

예시: C1:[P0,P1,P2], C2:[P3,P4,P5]로 돌고 있는데 C3가 추가되면 → RoundRobin은 6개 파티션을 3명에게 처음부터 재분배(모두 뒤섞임)하지만, Sticky는 "C1, C2가 이미 갖고 있던 파티션은 최대한 유지하고, C3에게 줄 파티션만 골라서 옮긴다" → 예를 들어 C1:[P0,P1], C2:[P3,P4], C3:[P2,P5]처럼 기존 배정을 최대한 보존한다.

**주의할 점**: Sticky 로직 자체는 "누가 뭘 갖는지" 계산 방식이고, 리밸런싱을 실행하는 방식(프로토콜)은 초기 StickyAssignor까지는 여전히 **Eager**였다 — 계산은 영리하게 하지만, 실행할 때는 일단 전원이 파티션을 반납했다가 다시 새 배정을 받는 방식이라 stop-the-world는 여전히 발생했다.

## 4. CooperativeStickyAssignor (2.4+, 사실상 지금의 기본값)

**동작**: Sticky와 같은 균형/이동 최소화 로직을 쓰면서, 실행 방식을 **Cooperative(점진적)** 프로토콜로 바꿨다. 반납이 필요한 파티션(예: C3에게 넘어갈 P2, P5)만 딱 반납하고, **영향받지 않는 파티션(C1의 P0,P1 등)은 반납 없이 계속 처리를 이어간다.** 리밸런싱이 두 라운드로 나뉘어 진행되지만, 전체가 멈추는 대신 정말 옮겨야 할 부분만 멈춘다.

정리하면 균형(Range → RoundRobin)과 이동 최소화(→ Sticky)는 "누구에게 파티션을 줄지"의 문제고, Eager/Cooperative는 "그 배정을 실행하는 방식"의 문제다. 이 둘을 합친 게 CooperativeStickyAssignor라서, 요즘 카프카 클라이언트에서는 사실상 이걸 기본으로 쓰는 게 권장된다.

## 비교 정리

| 전략 | 균형도 | 이동 최소화 | 정지 범위 |
|---|---|---|---|
| Range | 낮음(토픽 여러 개면 불균형 누적) | 안 함 | 전체 정지 |
| RoundRobin | 높음(구독 동일 시) | 안 함 | 전체 정지 |
| Sticky | 높음 | 함 | 전체 정지 (계산만 영리) |
| CooperativeSticky | 높음 | 함 | 필요한 파티션만 정지 |

## 한 줄 정리
> Range/RoundRobin은 균형만 신경 쓰고 매번 전체를 재분배하지만, Sticky는 기존 배정을 최대한 보존해 이동을 줄이고, CooperativeSticky는 거기에 더해 옮길 파티션만 반납하는 점진적 프로토콜로 실행해 stop-the-world를 최소화한다.
