[[DLQ와 멱등성 처리]]에서 정리한 "메시지 ID + 유니크 인덱스 + 트랜잭션" 방식이 왜 필요한지는, 애초에 "그냥 멱등하게 만들면 되지 않나"라는 질문에 왜 "제한적으로만 가능하다"고 답해야 하는지를 먼저 짚어야 설득력이 생긴다.

## 멱등하다는 것

같은 메시지를 1번 처리하나 3번 처리하나 최종 상태가 동일한 것.

- **자연스럽게 멱등한 예**: `user.setEmail(...)`, `order.setStatus("COMPLETED")` — 특정 값으로 "설정"하는 연산
- **자연스럽게 멱등하지 않은 예**: `balance += 1000`, `sendEmail(...)`, `inventory.decrease(qty)` — 누적/증감/부수 효과가 있는 연산

## 제한적인 이유 세 가지

1. **비즈니스 로직 대부분이 누적/증감 연산이다** — 포인트 적립, 재고 차감, 잔액 이체 등은 실행 횟수에 따라 결과가 달라진다. "최종 값을 계산해서 절대값으로 SET"하는 식으로 우회할 수는 있지만, 로직을 아예 다시 설계해야 해서 항상 가능하지는 않다.
2. **외부 시스템에 미치는 부수 효과는 되돌릴 수 없다** — 카드 결제, SMS 발송, 배송 요청 생성 등은 우리 DB 상태가 아니라 외부 세계에 실제로 일어난 일이라, "다시 실행해도 결과가 같다"는 조건 자체를 만족시킬 수 없다.
3. **순서에 의존하는 로직은 멱등성이 애매해진다** — 상태 전이 조건문(`if PENDING then COMPLETED`) 자체는 멱등해 보여도, 완료·취소 이벤트가 뒤섞여 중복 도착하면 상태를 잘못 되돌릴 위험이 있다. 로직이 복잡할수록 "다시 실행해도 안전"을 장담하기 어렵다.

## 결론

멱등 처리가 통하는 경우는 "값을 그대로 설정"하는 단순한 상태 변경 정도로 제한적이다. 누적 연산·외부 API 호출·복잡한 상태 전이는 자연히 멱등하지 않으므로, 이런 경우엔 "처리한 메시지 ID를 유니크 인덱스로 저장 + 비즈니스 로직과 한 트랜잭션으로 묶기" 방식이 더 범용적인 해법이다. 이 방식이 DB 안의 부작용은 막아주지만 트랜잭션 밖(외부 API 호출 등)의 부작용까지는 못 막는다는 한계는 [[DLQ와 멱등성 처리]]에서 이어서 다룬다.

## 한 줄 정리
> 멱등 처리는 "값을 그대로 설정"하는 연산에서만 자연스럽게 성립하고, 누적 연산·외부 API 부수효과·순서 의존 로직에서는 성립하지 않는다. 그래서 실무에서는 멱등한 연산으로 우회하기보다 "메시지 ID 기반 dedup + 트랜잭션"이 더 범용적으로 쓰인다.
