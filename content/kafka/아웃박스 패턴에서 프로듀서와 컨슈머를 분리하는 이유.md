# 아웃박스 패턴에서 프로듀서(스케줄러)와 컨슈머를 왜 분리해야 할까

면접에서 "아웃박스 테이블을 폴링해서 발행하는 스케줄러(프로듀서)와, 이를 구독하는 웹소켓 서버(컨슈머)가 있다"고 설명했더니, 면접관이 "그 스케줄러 역할을 컨슈머가 그냥 해주면 안 되나요?"라고 물었다. "장애 전파 방지"라고만 답했는데, 더 근본적인 이유가 있다. 관련: [[아웃박스 패턴 심화 - 재시도, 순서 보장, Dual Write 문제]] — 거기가 outbox 자체의 신뢰성 메커니즘이라면, 이 노트는 "왜 발행자와 구독자를 아예 다른 프로세스로 쪼개는가"라는 아키텍처 레벨의 질문이다.

## 근본 이유: 두 역할의 스케일링 축이 다르다

"장애 격리"보다 먼저 짚어야 하는 건, 프로듀서와 컨슈머가 인스턴스를 늘리는 **이유 자체가 다르다**는 점이다.

- **컨슈머(웹소켓 서버)**: 동시 접속 커넥션 수에 따라 수평 확장한다. 접속자가 늘면 인스턴스를 2대, 5대, 10대로 늘린다.
- **프로듀서(아웃박스 스케줄러)**: "DB 아웃박스 테이블 폴링 → 발행"이라는 흐름이 정확히 한 번만 일어나야 한다. 여러 인스턴스가 동시에 돌면 같은 row를 동시에 읽어서 중복 발행이 생기고, 이를 막으려면 `SELECT ... FOR UPDATE SKIP LOCKED`, 분산 락, 리더 선출 같은 별도 복잡도가 필요해진다.

두 역할을 한 프로세스에 합치면, 컨슈머가 트래픽 때문에 스케일 아웃될 때마다 아웃박스 폴링도 같이 여러 벌 동작하게 되어 중복 발행 문제가 발생한다. 이게 "그럼 여러 대 띄우면 어떻게 처리할 건가요?"로 이어지는 후속 질문의 함정이었을 가능성이 크다.

## 이유 2: Pub/Sub의 N:M 확장성이 사라진다

지금은 컨슈머가 웹소켓 서버 하나뿐이라도, 이벤트 기반 아키텍처는 컨슈머가 늘어나는 걸 전제로 설계하는 경우가 많다. 예를 들어 "메시지 전송" 이벤트에:

- 알림 서비스가 나중에 붙어서 오프라인 사용자에게 푸시를 보내야 하거나
- 통계 서비스가 실시간 대시보드로 트래픽을 집계하거나
- 감사(audit) 서비스가 발송 이력을 별도로 적재해야 하는

요구사항이 추가될 수 있다. 발행 로직이 웹소켓 서버 안에 박혀 있으면, 새 컨슈머는 웹소켓 서버가 각 서비스에 개별 HTTP 호출을 해주거나(→ 웹소켓 서버가 무거워지고, 알림 서비스가 느려지면 웹소켓 서버 응답까지 지연됨), 각자 아웃박스 테이블을 직접 폴링해야 한다(→ 테이블 하나를 여러 서비스가 동시에 긁는 구조가 서비스 개수만큼 곱해짐).

```
[아웃박스 테이블] → 스케줄러(발행 전담) → Kafka topic "message.sent"
                                              ├─ 웹소켓 서버 (consumer group A)
                                              ├─ 알림 서비스 (consumer group B)
                                              ├─ 통계 서비스 (consumer group C)
                                              └─ 감사 로그 서비스 (consumer group D)
```

브로커를 사이에 두고 발행자를 분리해두면, 새 컨슈머 추가는 "같은 토픽을 구독하는 컨슈머 하나 추가"로 끝난다. 발행 로직은 한 줄도 안 건드리고, 컨슈머 그룹이 분리되어 있으니 알림 서비스가 느려지든 죽든 웹소켓 서버 성능에는 영향이 없다.

## 이유 3: 배포/재시작 주기가 다르다

웹소켓 서버는 커넥션 특성상 배포·재시작이 잦다(연결 끊김을 최소화하려는 롤링 재시작 등). 이 재시작 주기에 아웃박스 폴링이 묶이면, 재시작 타이밍에 이벤트 발행이 누락되거나 중복될 위험이 커진다. 스케줄러를 분리해두면 발행 주기를 컨슈머의 배포 사이클과 무관하게 안정적으로 유지할 수 있다.

## 면접에서 어떻게 답했어야 했나

"장애 전파 방지"도 틀린 답은 아니지만, 이 질문의 의도는 "인스턴스를 여러 개 띄웠을 때 뭐가 문제냐"는 확장성/동시성 관점이었을 가능성이 크다. 스케일링 축 차이를 먼저 짚고, 장애 격리는 보조 논거로 붙이는 순서가 더 탄탄하다.

> "컨슈머(웹소켓 서버)는 접속자 수에 따라 수평 확장되는데, 프로듀서 역할까지 컨슈머가 맡으면 여러 인스턴스가 동시에 아웃박스 테이블을 폴링하면서 이벤트가 중복 발행될 수 있습니다. 이를 막으려면 분산 락이나 리더 선출 같은 추가 복잡도가 필요해지고, 다른 서비스가 같은 이벤트를 구독하고 싶을 때도 유연하게 대응하기 어려워집니다. 그래서 발행 책임은 단일 스케줄러(또는 리더 선출된 인스턴스)로 분리하고, 컨슈머는 순수하게 이벤트 소비/전달에만 집중하도록 설계했습니다."

## 한 줄 정리

> 프로듀서와 컨슈머를 분리하는 근본 이유는 장애 격리 이전에 스케일링 축이 다르기 때문이다 — 컨슈머는 접속자 수로, 프로듀서는 "정확히 한 번의 폴링"이라는 제약으로 확장 방식이 갈린다. 여기에 N:M 구독 확장성과 배포 주기 독립성이 보조 논거로 붙는다.
