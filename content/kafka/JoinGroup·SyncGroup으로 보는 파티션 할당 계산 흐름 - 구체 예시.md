# JoinGroup·SyncGroup으로 보는 파티션 할당 계산 흐름

[[파티션 소유권과 리밸런싱의 관계]]에서 "계산은 그룹 리더 컨슈머가, 관리·전달은 코디네이터가 한다"고 정리했는데, 말로만 들으면 실제로 뭐가 누구한테 오가는지 감이 잘 안 잡힌다. 숫자를 넣어서 순서대로 따라가 본다.

## 상황 설정

토픽 `orders`가 파티션 6개(P0~P5), 이걸 구독하는 그룹 `order-processor`에 컨슈머 인스턴스 3개(C1, C2, C3)가 떠 있다.

## 1단계 — 각 컨슈머가 JoinGroup 요청 전송

C1, C2, C3 모두 코디네이터에게 각자 이렇게 보낸다.

```
C1 → { groupId: "order-processor", 구독토픽: [orders], 지원전략: [range, sticky] }
C2 → { groupId: "order-processor", 구독토픽: [orders], 지원전략: [range, sticky] }
C3 → { groupId: "order-processor", 구독토픽: [orders], 지원전략: [range, sticky] }
```

이 시점에서 코디네이터는 각 컨슈머가 뭘 구독하는지, 뭘 지원하는지는 알지만 6개 파티션을 어떻게 나눌지는 아직 계산하지 않는다.

## 2단계 — 코디네이터가 정리해서 리더에게만 전체 정보 전달

코디네이터가 하는 일:
- 멤버 ID 부여
- 셋 중 하나를 리더로 지정 (보통 가장 먼저 join한 컨슈머) → 예: C1이 리더
- 공통 지원 전략 중 하나 확정 → range로 결정

그리고 응답을 다르게 보낸다.

```
C2, C3에게: { leader: "C1", protocol: "range", members: [] }
   → 리더는 C1이고 range 쓴다는 것만 알려줌

C1(리더)에게: { leader: "C1", protocol: "range",
   members: [
     { id: "C1", subscription: [orders] },
     { id: "C2", subscription: [orders] },
     { id: "C3", subscription: [orders] }
   ]
}
   → 리더에게만 그룹 전체 멤버 목록과 각자의 구독 정보를 통째로 넘김
```

여기가 핵심이다. C2와 C3는 그룹에 자기 말고 누가 더 있는지조차 모른다. 오직 리더인 C1만 "멤버가 C1, C2, C3 셋이고 다들 orders를 구독한다"는 전체 그림을 받는다.

## 3단계 — 리더(C1)가 로컬에서 계산 수행

C1은 브로커가 아니라 일반 애플리케이션 프로세스다. 방금 받은 정보(멤버 3명, 파티션 6개, range 전략)를 가지고 **자기 컴퓨터/JVM 안에서** range 할당 알고리즘([[파티션 할당 전략 - Range, RoundRobin, Sticky, CooperativeSticky]] 참고)을 직접 실행한다.

```
range 알고리즘 실행 결과 (C1의 컨슈머 클라이언트 라이브러리 코드가 계산):
  C1 → 파티션 [P0, P1]
  C2 → 파티션 [P2, P3]
  C3 → 파티션 [P4, P5]
```

이 계산은 브로커(코디네이터)가 아니라 C1 프로세스의 CPU에서 일어난다는 게 포인트다. 코디네이터는 이 계산에 전혀 관여하지 않는다.

## 4단계 — SyncGroup으로 결과 전파

```
C1 → 코디네이터에게 SyncGroup 요청 전송, 계산 결과 첨부:
     { C1: [P0,P1], C2: [P2,P3], C3: [P4,P5] }

C2, C3 → 코디네이터에게 SyncGroup 요청 전송하지만 내용은 비어있음
         (그냥 "내 결과 뭐야?" 하고 물어보는 용도)

코디네이터 → 각자에게 자기 몫만 잘라서 응답:
     C1에게 [P0,P1], C2에게 [P2,P3], C3에게 [P4,P5]
```

## 왜 굳이 리더한테 계산을 시키나

브로커(코디네이터)는 클러스터 전체의 수많은 그룹을 동시에 처리해야 하는데, 모든 그룹의 파티션 할당 계산까지 브로커가 다 떠맡으면 브로커 부하가 커진다. 그래서 카프카는 계산 로직을 클라이언트 라이브러리 안에 넣어두고, 코디네이터는 "누가 리더인지 지정하고, 전체 멤버 정보를 리더에게 전달하고, 리더가 계산한 결과를 각자에게 나눠주는" 중계자 역할만 한다.

## 한 줄 정리
> JoinGroup에서 코디네이터는 리더만 지정하고 전체 멤버 정보를 리더에게만 넘기며, 실제 파티션 할당 계산은 리더 컨슈머 프로세스가 로컬에서 수행해 SyncGroup으로 결과를 되돌려주면 코디네이터가 각자에게 배포한다 — 계산 CPU는 클라이언트가, 중계·검증은 브로커가 나눠 맡는 구조다.
