# 컨슈머는 브로커에서 메시지를 어떻게 가져올까 - Pull 기반 Fetch

카프카가 RabbitMQ 같은 전통 메시징 시스템과 다른 핵심 설계 중 하나가 컨슈머가 메시지를 받는 방식이다. 브로커가 밀어넣는 게 아니라 컨슈머가 직접 요청해서 가져간다.

## Push vs Pull

| 구분 | Push (예: RabbitMQ) | Pull (Kafka) |
|---|---|---|
| 주도권 | 브로커가 컨슈머에게 전송 | 컨슈머가 브로커에게 요청 |
| 속도 조절 | 브로커가 컨슈머 처리 속도를 모름 → 과부하 위험 | 컨슈머가 자기 처리 속도에 맞춰 요청 |
| 배치 처리 | 어려움 | 자연스러움 (한 번에 여러 메시지 fetch) |

## 동작 순서

1. 컨슈머는 자신이 맡은 각 파티션의 **리더 리플리카**에게 `Fetch` 요청을 보낸다. "오프셋 N부터 읽고 싶다"는 정보를 담는다.
2. 매번 요청하면 비효율적이므로 `fetch.min.bytes`(최소 이만큼 쌓이면 응답), `fetch.max.wait.ms`(그래도 이 시간 지나면 적더라도 응답)로 **롱 폴링**처럼 동작한다. 데이터가 없으면 브로커가 응답을 잠깐 보류했다가 도착 또는 타임아웃 시 응답한다.
3. 브로커는 요청받은 오프셋부터 디스크(세그먼트 파일)에서 순차적으로 읽어 배치로 응답한다. 이 순차 디스크 I/O + OS 페이지 캐시 활용이 카프카가 빠른 핵심 이유 중 하나다 ([[1. kafka]] 참고).
4. 컨슈머는 받은 메시지를 처리하며 로컬 `current offset`을 증가시키고, 주기적으로(자동 커밋) 또는 명시적으로(`commitSync`/`commitAsync`) 처리 완료 지점을 커밋 오프셋으로 코디네이터에 기록한다 ([[Commit Offset과 Current Offset 차이]] 참고).
5. 컨슈머가 재시작되면 마지막 커밋 오프셋부터 다시 Fetch를 시작한다.

## 한 줄 정리
> 카프카는 컨슈머가 리더 리플리카에게 오프셋을 지정해 Fetch 요청을 보내는 Pull 방식이고, fetch.min.bytes/fetch.max.wait.ms로 롱 폴링처럼 동작해 배치 처리와 컨슈머 자체 속도 조절을 가능하게 한다.
