# session.timeout.ms와 max.poll.interval.ms는 뭐가 다를까?

둘 다 "컨슈머가 죽었다고 판단해서 리밸런싱을 트리거하는 타임아웃"이지만, 감지하는 대상이 완전히 다르다. 면접에서 리밸런싱 원인을 물어보면 이 둘을 구분해서 설명할 수 있어야 한다.

## 핵심 차이

| | session.timeout.ms | max.poll.interval.ms |
|---|---|---|
| 감지 대상 | 프로세스가 살아있는가 (하트비트) | 메시지 처리 로직이 멈췄는가 (poll 호출) |
| 담당 스레드 | 백그라운드 하트비트 스레드 | 메인 스레드(poll을 부르는 스레드) |
| 기본값 | 45초 (버전에 따라 10초였던 적도 있음) | 5분(300000ms) |
| 대표 발동 상황 | 프로세스 크래시, GC 정지, 네트워크 단절 | 메시지 처리 로직이 너무 오래 걸림 (느린 외부 API 호출 등) |

## 왜 두 개로 나뉘었는가

옛날 카프카 클라이언트는 하트비트를 `poll()` 호출 안에서 같이 보냈다. 그러니 "하트비트가 끊겼다"와 "poll이 안 불린다"가 사실상 같은 신호였다. 문제는 메시지 처리에 시간이 오래 걸리는 경우다 — 예를 들어 배치로 500건을 받아서 하나씩 DB에 쓰는데 총 2분이 걸리면, 다음 `poll()`을 부를 때까지 하트비트도 같이 못 보내니 컨슈머가 멀쩡히 일하고 있는데도 죽은 걸로 오판되어 쫓겨나는 일이 생겼다.

그래서 KIP-62로 하트비트를 **별도의 백그라운드 스레드**로 분리했다. 메인 스레드가 메시지를 처리하느라 바빠도 백그라운드 스레드는 독립적으로 하트비트를 계속 보낼 수 있다. 대신 "그럼 진짜로 메인 스레드가 멈춘 건 어떻게 잡지?"라는 문제가 남아서, 이걸 감지하는 별도의 타임아웃으로 `max.poll.interval.ms`가 새로 생겼다.

## 각각 언제 발동하는지

**session.timeout.ms 발동 예시**
- 컨슈머 프로세스가 OOM으로 죽음 → 하트비트 스레드 자체가 멈춤 → session.timeout.ms 동안 하트비트 없음 → 코디네이터가 죽었다고 판단, 리밸런싱
- Full GC로 JVM이 통째로 멈춘 경우(Stop-The-World GC)도 하트비트 스레드까지 같이 멈추니 여기 해당

**max.poll.interval.ms 발동 예시**
- `poll()`로 500건을 받아서 각 건마다 외부 결제 API를 호출하는데, API가 느려져서 처리에 6분이 걸림 → 하트비트는 계속 정상적으로 나가고 있어서 session.timeout.ms는 안 걸리지만, 다음 poll() 호출까지 5분(기본값)이 넘어감 → 코디네이터가 "하트비트는 보내는데 일을 안 하고 있다(=멈췄다)"고 판단해서 그룹에서 제거, 리밸런싱

두 번째 케이스가 실무에서 자주 놓치는 부분이다 — 로그에 리밸런싱은 찍히는데 컨슈머 프로세스는 안 죽어있고 하트비트도 정상으로 찍혀있으니, "왜 리밸런싱이 났지?" 하고 헤매다가 나중에 max.poll.interval.ms가 원인인 걸 알게 되는 경우가 많다.

## 실무 설정 팁

- 메시지 하나 처리가 오래 걸리는 워크로드(배치 처리, 무거운 연산)라면 max.poll.interval.ms를 넉넉히 늘리거나, max.poll.records를 줄여서 한 번에 처리할 메시지 수를 줄이는 방향으로 대응
- session.timeout.ms는 너무 짧으면 일시적 네트워크 지연에도 리밸런싱이 남발되고, 너무 길면 진짜 장애 컨슈머를 늦게 발견하니 이 트레이드오프를 고려해서 조정

## 한 줄 정리
> session.timeout.ms는 "살아있냐"를 하트비트 스레드로 체크하고, max.poll.interval.ms는 "일하고 있냐"를 메인 스레드의 poll 호출 간격으로 체크한다. 둘이 분리된 이유는 처리 시간이 긴 작업 때문에 살아있는 컨슈머가 죽은 것으로 오판되는 문제(KIP-62)를 막기 위해서다.
