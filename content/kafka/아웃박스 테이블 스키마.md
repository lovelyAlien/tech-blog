# 일반적인 아웃박스 테이블 스키마는 어떻게 생겼나

관련: [[아웃박스 패턴 심화 - 재시도, 순서 보장, Dual Write 문제]] — 거기서 정리한 상태 관리(PENDING/FAILED), 재시도, 발행 순서 보장 개념을 실제 DDL로 옮기면 이런 모양이 된다.

## 폴링 방식 (앱이 직접 폴링해서 발행)

```sql
CREATE TABLE outbox_event (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,   -- ORDER BY id ASC로 발행 순서 결정
    aggregate_type  VARCHAR(100)  NOT NULL,               -- 예: "Reservation"
    aggregate_id    VARCHAR(100)  NOT NULL,               -- 예: reservationId — 카프카 메시지 키로 사용 (같은 엔티티는 같은 파티션)
    event_type      VARCHAR(100)  NOT NULL,               -- 예: "ReservationConfirmed"
    payload         JSON          NOT NULL,               -- 컨슈머에게 보낼 완성된 이벤트 본문
    status          VARCHAR(20)   NOT NULL DEFAULT 'PENDING', -- PENDING / SUCCESS / FAILED
    retry_count     INT           NOT NULL DEFAULT 0,
    next_retry_at   DATETIME      NULL,                   -- 지수 백오프로 다음 재시도 시점 미룸
    created_at      DATETIME      NOT NULL DEFAULT NOW(),
    published_at    DATETIME      NULL                    -- 발행 성공 시각 (감사/디버깅용)
);

CREATE INDEX idx_outbox_polling ON outbox_event (status, next_retry_at);
```

컬럼별 역할:

| 컬럼 | 역할 |
|---|---|
| `id` | 발행 순서 기준. auto-increment라 커밋 순서와 일치 |
| `aggregate_type` / `aggregate_id` | 어떤 엔티티의 이벤트인지. `aggregate_id`를 카프카 메시지 키로 써서 같은 엔티티 이벤트의 순서를 보장 |
| `event_type` | 컨슈머가 메시지 종류를 구분하는 값. 카프카 헤더나 payload 안에도 넣는 경우가 많음 |
| `payload` | 앱이 조인/가공까지 끝낸 **완성된 도메인 이벤트 JSON**. DB 컬럼이 아니라 이 안에 원하는 필드를 뭐든 넣을 수 있다는 게 핵심 |
| `status` | 재시도 폴러가 `WHERE status = 'PENDING'`으로 조회하는 기준. `FAILED`는 재시도 소진 후의 종료 상태 |
| `retry_count` / `next_retry_at` | 재시도 로직(지수 백오프)의 상태를 DB에 영속화 |
| `published_at` | 필수는 아니지만, 발행까지 걸린 지연시간 모니터링이나 감사 로그용으로 자주 추가됨 |

## CDC(Debezium) 방식이면 더 단순해진다

폴링이 아니라 CDC로 이 테이블을 tail한다면, `status`/`retry_count`/`next_retry_at` 컬럼 자체가 필요 없다 — "재시도했는지, 발행됐는지"를 앱이 DB에 기록할 필요 없이, Debezium 커넥터의 binlog offset이 "어디까지 읽었는지"를 대신 관리해주기 때문이다.

```sql
CREATE TABLE outbox_event (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    aggregate_type  VARCHAR(100)  NOT NULL,
    aggregate_id    VARCHAR(100)  NOT NULL,
    event_type      VARCHAR(100)  NOT NULL,
    payload         JSON          NOT NULL,
    created_at      DATETIME      NOT NULL DEFAULT NOW()
);
```

Debezium의 [outbox event router SMT](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/)가 바로 이 필드 이름 관례(`aggregate_type`, `aggregate_id`, `payload`)를 기본값으로 인식하도록 설계되어 있어서, 실무에서도 이 컬럼명을 그대로 많이 쓴다.

## 한 줄 정리

> 아웃박스 테이블의 핵심 컬럼은 발행 순서(`id`), 메시지 키(`aggregate_id`), 완성된 이벤트 본문(`payload`) 세 가지다. 폴링 방식은 여기에 재시도 상태(`status`, `retry_count`, `next_retry_at`)를 더 얹지만, CDC 방식은 커넥터가 진행 상황을 대신 관리해줘서 테이블이 그만큼 단순해진다.
