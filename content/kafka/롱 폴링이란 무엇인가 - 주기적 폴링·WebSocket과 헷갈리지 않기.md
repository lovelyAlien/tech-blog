# 롱 폴링이란 무엇인가 - 주기적 폴링·WebSocket과 헷갈리지 않기

[[파티션 리더 위치는 어떻게 알아내는가 - Metadata 프로토콜과 Fetch 시퀀스]]에서 컨슈머의 Fetch가 "끊임없이 이어지는 루프 + 롱 폴링" 조합이라고 했는데, 이게 "주기적으로 물어본다"는 것과 뭐가 다른지, 그리고 이렇게 브로커가 먼저 보내주는 것처럼 보이는데 왜 "응답"이라고 부르는지, 웹소켓과는 뭐가 다른지, HTTP와 비교하면 어떤지, 요청마다 연결을 끊었다 다시 맺는 건지 다섯 가지가 헷갈리기 쉽다.

## 1. 롱 폴링 vs 주기적(짧은 간격) 폴링

핵심 차이는 **"쉬는 시간이 클라이언트 쪽에 있느냐 없느냐"** 다.

**일반적인 짧은 간격 폴링** (예: 100ms마다 요청):

```
t=0ms    : 요청 전송 → 브로커가 "지금 없음" 즉시 응답
t=0~100ms: 컨슈머는 아무것도 안 하고 대기 (sleep)
t=100ms  : 요청 전송 → "지금 없음" 즉시 응답
t=350ms  : 사실 이때 메시지가 브로커에 도착. 하지만 컨슈머는 모름
t=400ms  : 요청 전송 → 이제서야 응답 받음
```

메시지가 t=350ms에 도착했는데 컨슈머는 t=400ms에야 알게 된다. 최대 인터벌만큼(여기선 최대 100ms) 불필요한 지연이 생기고, 데이터가 없을 때도 "없음" 응답을 주고받는 헛수고 요청이 반복된다.

**롱 폴링** (`fetch.max.wait.ms=500`):

```
t=0ms   : 요청 전송
          → 브로커는 즉시 응답 안 하고 "요청을 손에 쥔 채" 대기 시작
t=350ms : 메시지 도착 → 브로커가 그 순간 즉시 응답 전송
t=350ms : 컨슈머는 응답 받자마자 곧바로 다음 요청 재전송, 또 대기 시작
```

컨슈머 쪽에는 쉬는 구간이 없다. 요청 하나가 끝나는 즉시 다음 요청을 쏘고, 그 요청이 열려있는 동안 브로커가 데이터 도착 시점까지 붙잡고 있다가 정확히 그 순간에 응답하기 때문에 지연이 훨씬 작고 불필요한 빈 요청도 줄어든다.

## 2. 브로커가 먼저 보내주는 것처럼 보이는데 왜 "응답"이라고 하는가

push와 pull을 가르는 기준은 **"누가 마지막에 바이트를 전송했는가"가 아니라 "누가 먼저 연결/요청을 열었는가"** 다.

롱 폴링에서 브로커가 데이터를 보내는 순간은, 컨슈머가 이미 열어놓은 요청에 대한 완결(응답)이다. 같은 TCP 커넥션 위에서 컨슈머가 보낸 요청의 correlation ID와 매칭되는 응답으로 돌아간다. 브로커가 스스로 "얘한테 지금 보내야겠다"고 판단해서 새 통신을 시작한 게 아니라, 이미 와 있던 질문에 뒤늦게 답한 것뿐이다.

만약 컨슈머가 애초에 그 요청을 보내지 않았다면, 브로커는 메시지가 아무리 쌓여도 그 컨슈머에게 아무것도 보내지 않는다. 컨슈머가 `pause()`를 호출해서 특정 파티션에 대한 Fetch 요청을 스스로 멈추면, 그 파티션에 메시지가 계속 쌓여도 브로커는 아무 것도 전송하지 않는다. 이게 진짜 push와의 결정적 차이다 — push였다면 브로커가 컨슈머 상태와 무관하게 자기 판단으로 새 연결/알림을 열 수 있어야 하는데, 카프카는 그런 능력 자체가 브로커에 없다.

비유:
- **Push**: 배달원이 "너 주문 안 했지만 그냥 문 앞에 두고 갈게"
- **Pull(롱 폴링)**: 손님이 이미 "준비되면 알려주세요" 하고 카운터에서 기다리고 있고(요청이 열려있음), 준비되는 순간 점원이 "나왔습니다" 하고 건네주는 것(응답) — 손님이 먼저 요청 안 했으면 점원은 절대 먼저 부르지 않음

## 3. 그럼 WebSocket처럼 연결을 유지하는 게 맞나?

**연결 자체는 비슷하게 유지되지만, 그 위에서 일어나는 통신 방식은 완전히 다르다.**

카프카 클라이언트는 브로커별로 TCP 커넥션을 한 번 맺으면 계속 재사용한다(요청마다 새로 연결하지 않음). 이 점만 보면 WebSocket이 연결을 계속 유지하는 것과 유사하다.

| 특성 | WebSocket | Kafka 롱 폴링(Fetch) |
|---|---|---|
| 연결 자체 | 지속적 TCP | 지속적 TCP (브로커 커넥션 재사용) |
| 통신 방향 | 진짜 양방향 비동기 — 서버가 아무 때나 먼저 메시지를 보낼 수 있음 | 반드시 요청-응답 짝을 이뤄야 함 |
| 서버가 요청 없이 먼저 데이터를 보낼 수 있는가 | 가능 | 불가능 — 반드시 그 전에 와 있던 요청에 대한 응답이어야 함 |
| 하나의 연결로 몇 번의 교환이 가능한가 | 자유 형식, 무제한, 순서 상관없이 아무 때나 | 요청 1개당 응답 1개. 응답이 오면 교환은 끝나고, 다음 데이터를 받으려면 새 요청을 또 보내야 함 |

WebSocket은 "문을 한 번 열어두면 그 이후로는 언제든 누구든 마음대로 소리칠 수 있는 통로"에 가깝고, 카프카 롱 폴링은 "연결이라는 도로는 유지하지만, 그 위를 지나가는 모든 메시지는 반드시 질문표(요청 ID)를 달고 있어야 하고, 각 질문표는 정확히 하나의 답변표(응답)와만 짝지어지는" 구조다.

## 4. HTTP와 비교하면 어떤가

"연결을 유지한다"는 게 카프카 롱 폴링이나 WebSocket만의 특징처럼 보일 수 있는데, 사실 일반 HTTP도 이미 연결을 유지한다. 이 부분을 정확히 짚어야 진짜 차이가 보인다.

| | HTTP/1.0 (구식) | HTTP/1.1 (현재 사실상 표준) | HTTP 롱 폴링 | WebSocket |
|---|---|---|---|---|
| 연결 유지 | 기본값은 요청마다 새 연결, 응답 후 닫음 | 기본값이 Keep-Alive — 연결을 열어두고 여러 요청에 재사용 | 유지(Keep-Alive 위에서 구현) | 유지 (HTTP Upgrade 후 별개 프로토콜로 전환) |
| 요청-응답 모양 | 요청 1개 = 응답 1개, 즉시 응답 | 요청 1개 = 응답 1개, 즉시 응답 | 서버가 데이터 생길 때까지 응답을 붙잡고 있다가 응답 | 요청-응답 짝 개념 자체가 없음, 자유 형식 |
| 서버가 먼저 보낼 수 있나 | 불가능 | 불가능 | 불가능 (붙잡고 있다가 응답만 할 뿐, 시작은 여전히 클라이언트 요청) | 가능 |

즉 "옛날 HTTP는 매번 끊었다 다시 연결한다"는 게 맞지만, 지금 REST API 호출에 쓰는 HTTP/1.1은 이미 연결을 유지한 채로 여러 요청-응답을 주고받는다. 그래서 일반 HTTP와 롱 폴링의 진짜 차이는 "연결 유지 여부"가 아니라 **"서버가 응답을 즉시 주느냐, 아니면 데이터 생길 때까지 들고 있다가 주느냐"**이고, 이 둘과 WebSocket의 차이는 **"요청-응답이라는 짝 규칙 자체가 있느냐 없느냐"**다.

카프카의 Fetch는 HTTP가 전혀 아니고 자체 바이너리 TCP 프로토콜이지만, 개념적으로는 위 표의 "HTTP 롱 폴링" 열과 정확히 같은 자리에 있다 — 연결 유지 + 응답을 데이터 생길 때까지 들고 있다가 줌 + 서버는 절대 먼저 못 보냄.

## 5. 요청마다 연결을 끊었다 다시 맺는 건 아니다

"요청 보내고 응답 기다리는 동안 연결 유지, 응답 받으면 연결 끊고 다시 요청"이라고 생각하기 쉬운데 아니다. **하나의 TCP 연결을 계속 유지한 채로, 그 위에서 요청-응답 사이클만 반복한다.**

```
[한 번 연결 맺음]
   |
   ├─ 요청1 전송 → (연결 유지한 채 대기) → 응답1 수신
   ├─ 요청2 전송 → (연결 유지한 채 대기) → 응답2 수신
   ├─ 요청3 전송 → (연결 유지한 채 대기) → 응답3 수신
   ...
[연결은 계속 열려있는 상태로 유지됨]
```

혼동하기 쉬운 지점은 두 레벨을 섞어서 보기 때문이다.

- **"요청-응답이 짝을 이룬다"**는 건 **프로토콜(논리) 레벨**의 이야기다 — 각 요청 프레임에는 correlation ID가 붙고, 그 ID와 일치하는 응답 프레임이 돌아온다는 규약.
- **"연결을 끊고 다시 맺는다"**는 건 **네트워크(물리) 레벨**의 이야기인데, 카프카는 이 둘을 분리해놨다. 요청-응답 페어링은 지키되, 밑바닥 TCP 소켓은 계속 재사용한다.

실제로 카프카 클라이언트는 브로커마다 커넥션을 하나 맺어두고(`connections.max.idle.ms` 기본 9분 동안 아무 요청도 없을 때만 닫음), 그 위에서 수많은 Fetch 요청을 순차적으로 흘려보낸다. 심지어 완전히 순차적이지도 않고, `max.in.flight.requests.per.connection`(기본 5) 설정만큼 응답을 기다리는 동안에도 다음 요청을 미리 여러 개 더 보내는 파이프라이닝까지 한다.

비유하면, 전화를 걸었다 끊었다 반복하는 게 아니라 한 번 통화 연결을 해놓고 그 통화 안에서 질문 하나 하고 답 듣고, 또 질문하고 답 듣고를 반복하는 것과 비슷하다. 통화(연결) 자체는 끊지 않는다.

## 한 줄 정리
> 롱 폴링은 "연결은 오래 유지하되, 프로토콜 규약(요청-응답 페어링)은 여전히 pull 방식 그대로인" 절충안이다. 연결 유지 자체는 HTTP/1.1 Keep-Alive와 다를 게 없고, 진짜 차이는 서버가 응답을 즉시 주는지(일반 HTTP) 데이터 생길 때까지 붙잡고 있다가 주는지(롱 폴링)이며, WebSocket과 달리 브로커는 컨슈머가 먼저 보낸 요청 없이는 절대 먼저 데이터를 보낼 수 없다. 요청-응답이 짝을 이루는 것은 연결을 매번 끊고 다시 맺는 것과는 무관한 프로토콜 레벨의 규약일 뿐 TCP 연결 자체는 계속 재사용된다.
