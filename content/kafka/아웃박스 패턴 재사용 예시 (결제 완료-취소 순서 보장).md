# 아웃박스 패턴 재사용 예시 (결제 완료·취소 순서 보장)

[[아웃박스 테이블 스키마]]와 [[아웃박스 패턴 심화 - 재시도, 순서 보장, Dual Write 문제]]에서 정리한 개념(dual write 문제, PENDING/FAILED 상태, aggregate_id 키)을 그대로 "결제 완료 → 취소" 시나리오에 적용하면 이런 모양이 된다. 새 개념보다는 바로 갖다 쓸 수 있는 최소 예시로 정리.

## OUTBOX 테이블

```sql
CREATE TABLE outbox (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    aggregate_id VARCHAR(64) NOT NULL,   -- 파티션 키로 쓸 값 (예: orderId)
    event_type  VARCHAR(50) NOT NULL,    -- PAYMENT_COMPLETED, PAYMENT_REFUNDED
    payload     JSON NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status      VARCHAR(20) DEFAULT 'PENDING'
);
```

## 비즈니스 로직 + outbox 기록을 한 트랜잭션으로

```java
@Transactional
public void completePayment(Order order) {
    // 1. 비즈니스 로직 처리
    order.markAsCompleted();
    orderRepository.save(order);

    // 2. 같은 트랜잭션 안에서 outbox에 이벤트 기록
    OutboxEvent event = OutboxEvent.builder()
        .aggregateId(order.getId().toString())   // orderId를 aggregate_id로
        .eventType("PAYMENT_COMPLETED")
        .payload(toJson(order))
        .build();
    outboxRepository.save(event);
    // order 저장과 outbox 저장이 하나의 트랜잭션
    // 둘 중 하나라도 실패하면 전체 롤백 → 이중 쓰기 문제 원천 차단
}
```

## 릴레이 (폴링 방식)

```java
@Scheduled(fixedDelay = 1000)
public void relayOutboxEvents() {
    List<OutboxEvent> pending = outboxRepository.findByStatus("PENDING");
    for (OutboxEvent event : pending) {
        // aggregate_id(orderId)를 Kafka 메시지 키로 사용
        // → 같은 주문의 completed/refunded 이벤트가 항상 같은 파티션으로
        kafkaTemplate.send("payment-events", event.getAggregateId(), event.getPayload());
        event.markAsSent();
        outboxRepository.save(event);
    }
}
```

## 핵심 포인트

- `aggregate_id`(주문 ID)를 **Kafka 메시지 키**로 사용 → 완료/취소 이벤트가 항상 같은 파티션에 순서대로 적재. 왜 이게 순서를 보장하는지는 [[토픽은 이벤트 종류가 아니라 엔티티 단위로 나눠야 하는 이유]] 참고.
- 릴레이는 폴링(구현 간단, 폴링 간격만큼 지연) 또는 CDC(Debezium, 지연 적음, 운영 학습 비용 있음) 중 선택 — 두 방식의 스키마 차이는 [[아웃박스 테이블 스키마]] 참고.
- 발행 성공 후 outbox 레코드는 삭제하거나 상태를 `SENT`로 마킹해서 재발행 방지.
- 발행 성공 직후 상태 마킹 사이에 장애가 나면 중복 발행 가능 → 컨슈머 측에서 `message_id` 기반 멱등 처리 필요 (at-least-once 특성). 왜 멱등 처리가 항상 간단하지만은 않은지는 [[멱등 처리가 제한적인 이유]] 참고.

## 한 줄 정리
> 이중 쓰기 문제는 비즈니스 로직 + outbox insert를 한 트랜잭션으로 묶어서 막고, 순서 보장은 aggregate_id를 Kafka 메시지 키로 써서 같은 파티션에 몰아 해결한다. 남는 중복 가능성은 컨슈머 측 멱등 처리로 흡수한다.
