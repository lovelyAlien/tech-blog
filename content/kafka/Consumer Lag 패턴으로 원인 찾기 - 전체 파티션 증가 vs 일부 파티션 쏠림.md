# Consumer Lag 패턴으로 원인 찾기 - 전체 파티션 증가 vs 일부 파티션 쏠림

"Lag 알림이 왔다"만으로는 무엇을 고쳐야 할지 모릅니다. 먼저 **Lag이 어느 파티션에서 오르는지**를 보면 확인할 곳이 절반으로 줄어듭니다. 모든 파티션이 같이 오르면 "전체 처리량" 문제이고, 일부만 오르면 "특정 키나 특정 컨슈머" 문제입니다.

## 먼저 Lag이 뭔지 다시 보기

파티션마다 따로 계산됩니다.

```
Lag = Log End Offset (브로커에 쓰인 최신 위치) - Committed Offset (컨슈머 그룹이 커밋한 위치)
```

그래서 Lag은 **유입 속도와 소비 속도의 차이**가 쌓인 값입니다. Lag이 오른다는 건 둘 중 하나입니다.

- 들어오는 양이 늘었다 (유입 ↑)
- 처리하는 속도가 떨어졌다 (소비 ↓)

커밋이 늦어도 Lag이 부풀어 보일 수 있다는 점은 [[Commit Offset과 Current Offset 차이]]에 정리해 두었습니다.

## 진단 순서

```
Lag 알림
 └─ 파티션별 Lag을 나눠 본다
     ├─ 모든 파티션이 고르게 증가 ──▶ [A] 전체 처리량 부족
     │     ├─ 유입 속도가 늘었나?  → 트래픽 급증 (이벤트·배치 유입)
     │     └─ 소비 속도가 줄었나?  → 처리 시간·외부 호출(DB/API) 지연, GC
     │
     └─ 일부 파티션만 증가 ──────▶ [B] 특정 키 또는 특정 컨슈머 문제
           ├─ 그 파티션 유입만 많나?        → 핫 키 쏠림
           ├─ 그 파티션 커밋이 멈췄나?       → 담당 컨슈머가 멈춤 (poison pill, 블로킹)
           └─ 담당 컨슈머가 계속 바뀌나?     → 리밸런싱 반복
```

핵심은 **유입 속도와 소비 속도를 파티션별로 따로 본다**는 것입니다. Lag 숫자 하나만 보면 둘을 구분할 수 없습니다.

## [A] 모든 파티션에서 Lag이 오를 때 — 처리량 부족

파티션이 고르게 밀린다는 건 키 분포는 정상이고, **그룹 전체가 유입을 못 따라간다**는 뜻입니다.

| 확인할 것 | 보는 곳 | 의심되는 원인 |
|---|---|---|
| 유입 속도 | 파티션 최신 오프셋 증가율, 프로듀서 쪽 요청 수 | 행사 시작·배치 유입 같은 트래픽 급증 |
| 리스너 처리 시간 | `spring_kafka_listener_seconds` (`sum / count`, `max`) | 처리 로직이 느려짐 |
| 외부 호출 지연 | DB 쿼리 시간, 커넥션 풀 대기, 외부 API 응답 시간 | 다운스트림이 병목 — 가장 흔함 |
| JVM 상태 | GC 시간, 힙 사용률, CPU | GC로 멈추는 시간이 늘어남 |
| 컨슈머 수 vs 파티션 수 | 그룹 멤버 수 | 컨슈머가 파티션보다 적어 한 컨슈머가 여러 파티션을 맡음 |

**조치 방향**
- 처리가 느린 원인부터 고칩니다. 건마다 DB·Redis를 오간다면 묶어서 처리(배치 소비)해 왕복을 줄입니다.
- 컨슈머를 늘리는 건 **파티션 수까지만** 효과가 있습니다. 파티션보다 많은 컨슈머는 할 일이 없이 놉니다.
- 파티션을 늘리면 키 → 파티션 매핑이 바뀌어서, 그 시점 전후로 **같은 키의 순서 보장이 깨질 수 있습니다.** 순서가 중요한 토픽이면 신중하게 결정합니다.

## [B] 일부 파티션만 Lag이 오를 때 — 쏠림 또는 멈춤

### 1. 핫 키 쏠림

같은 키는 항상 같은 파티션으로 갑니다. 특정 키(큰 방, 인기 상품, 큰 고객사)에 메시지가 몰리면 그 파티션만 유입이 폭증합니다.

- **확인:** 그 파티션의 **유입 속도만** 다른 파티션보다 확연히 높은지 봅니다. 소비 속도는 다른 파티션과 비슷한데 유입이 많아서 밀리는 모양입니다.
- **조치:** 키 설계를 바꿉니다. 예를 들어 `방 ID` 대신 `방 ID + 하위 구분값`으로 키를 쪼개면 퍼지지만, **순서가 보장되는 범위도 같이 좁아집니다.** "어디까지 순서가 필요한가"를 먼저 정해야 합니다.

### 2. 그 파티션 담당 컨슈머가 멈춤

유입은 평범한데 **그 파티션의 커밋 오프셋만 움직이지 않는** 모양입니다.

- **흔한 원인**
  - 처리할 수 없는 메시지(poison pill)를 계속 재시도하느라 다음 메시지로 못 넘어감
  - 타임아웃 없는 외부 호출이 블로킹됨
  - 그 컨슈머 스레드가 예외로 죽었거나 교착 상태
- **확인:** 그 파티션의 커밋 오프셋 증가율이 0에 가까운지, 해당 컨슈머 로그에 같은 오프셋 에러가 반복되는지 봅니다.
- **조치:** 재시도 횟수를 제한하고 실패 메시지는 DLQ로 보내 다음 메시지로 넘어가게 합니다([[DLQ와 멱등성 처리]]). 외부 호출에는 반드시 타임아웃을 둡니다.

### 3. 리밸런싱 반복

처리가 느린 컨슈머가 `max.poll.interval.ms` 안에 다음 `poll()`을 못 부르면, 그룹에서 쫓겨나고 다시 들어오면서 리밸런싱이 반복됩니다. 그 사이 담당 파티션은 소비가 멈춥니다.

- **확인:** 컨슈머 로그의 그룹 이탈·재합류 메시지, 리밸런싱 횟수 지표, `kafka-consumer-groups --describe`에서 파티션 담당자(CONSUMER-ID)가 자주 바뀌거나 비어 있는지 봅니다.
- **조치:** 한 번에 가져오는 양(`max.poll.records`)을 줄이거나, 처리 시간을 줄이거나, `max.poll.interval.ms`를 실제 처리 시간에 맞게 늘립니다. 차이는 [[session.timeout.ms와 max.poll.interval.ms 차이]] 참고.

**정확히는:** 리밸런싱은 "일부 파티션 문제"로만 나타나지 않습니다. 기본(eager) 방식에서는 리밸런싱 동안 **그룹 전체가 소비를 멈추기** 때문에, 모든 파티션의 Lag이 톱니 모양으로 같이 튈 수 있습니다. 그래서 [A] 패턴인데 처리 시간·외부 호출에 이상이 없다면 리밸런싱 반복도 의심합니다. CooperativeSticky 전략은 옮겨지는 파티션만 멈추게 해서 영향을 줄입니다([[파티션 할당 전략 - Range, RoundRobin, Sticky, CooperativeSticky]]).

## 한눈에 비교

| | [A] 전체 파티션 증가 | [B-1] 핫 키 | [B-2] 컨슈머 멈춤 | [B-3] 리밸런싱 반복 |
|---|---|---|---|---|
| Lag 모양 | 모든 파티션이 고르게 상승 | 일부 파티션만 상승 | 일부 파티션만 상승 (평평하게 계속) | 톱니 모양, 담당이 바뀌며 튐 |
| 유입 속도 | 전체가 높거나 평범 | **그 파티션만 높음** | 평범 | 평범 |
| 소비 속도 | 전체가 낮음 | 평범 | **그 파티션만 0에 가까움** | 리밸런싱 때마다 끊김 |
| 먼저 볼 것 | 처리 시간, 외부 호출, GC | 파티션별 유입량, 키 분포 | 그 컨슈머 에러 로그 | 그룹 이탈 로그, 리밸런싱 횟수 |

## 대시보드에서 보는 법 (kafka-exporter 기준)

```promql
# 파티션별 Lag — 전체 증가인지 일부 쏠림인지 먼저 구분
sum by (partition) (kafka_consumergroup_lag{consumergroup="my-group", topic="my-topic"})

# 파티션별 유입 속도 — 핫 키 확인
rate(kafka_topic_partition_current_offset{topic="my-topic"}[5m])

# 파티션별 소비(커밋) 속도 — 멈춘 컨슈머 확인
rate(kafka_consumergroup_current_offset{consumergroup="my-group", topic="my-topic"}[5m])
```

CLI로 바로 볼 때는 이것 하나면 파티션별 Lag과 담당 컨슈머가 다 나옵니다.

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group my-group
# PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG   CONSUMER-ID ...
# 0          1200            1210            10    consumer-1-...
# 3          5000            98000           93000 consumer-2-...   ← 이 파티션만 밀림
```

## 한 줄 정리
> Lag은 파티션별로 나눠 본다. 모두 오르면 처리량 부족이라 처리 시간·외부 호출을 보고, 일부만 오르면 그 파티션의 유입(핫 키)·커밋 정지(멈춘 컨슈머)·담당 변경(리밸런싱)을 차례로 본다.
