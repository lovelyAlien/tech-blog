# Commit Offset과 Current Offset은 뭐가 다를까?

둘 다 "컨슈머가 어디까지 읽었나"를 가리키는 값이지만, 같은 값의 두 가지 상태가 아니라 **서로 다른 목적을 위해 존재하는 별개의 개념**이다. 이 간격을 이해해야 카프카의 중복 컨슈밍(at-least-once)이 왜 생기는지 설명할 수 있다.

## 핵심 차이

| | Current Offset (Position) | Committed Offset |
|---|---|---|
| 의미 | 컨슈머가 poll()로 **다음에 가져올** 위치 | 브로커에 **명시적으로 기록한** "여기까지 처리 완료" 위치 |
| 저장 위치 | 컨슈머 프로세스 메모리 (클라이언트 내부) | 브로커의 내부 토픽 `__consumer_offsets` |
| 갱신 시점 | poll()로 메시지를 받아오는 즉시 (처리 여부 무관) | commitSync()/commitAsync() 호출 시 (또는 auto-commit 주기) |
| 재시작/리밸런싱 시 | 사라짐 (메모리라서) | 새 컨슈머가 이 지점부터 다시 읽기 시작 |
| 조회 API | `consumer.position(partition)` | `consumer.committed(partition)` |

## Current Offset — "poll이 어디까지 가져왔나"

컨슈머가 `poll()`을 호출해서 메시지를 배치로 받아오면, 그 즉시 "다음 poll에서는 여기서부터 가져와야 한다"는 위치가 앞으로 전진한다. 이건 **처리(비즈니스 로직 수행)를 했는지와 무관하게** 그냥 "브로커에서 가져온" 사실만으로 움직이는 값이고, 컨슈머 프로세스가 메모리에 들고 있을 뿐 브로커에는 아무것도 기록되지 않는다.

## Committed Offset — "여기까지는 확실히 처리했다고 브로커에 알린 위치"

`commitSync()`나 `commitAsync()`를 호출하면(혹은 `enable.auto.commit=true`로 주기적 자동 커밋), 그 오프셋이 브로커의 `__consumer_offsets` 토픽에 저장된다. 컨슈머가 재시작되거나 리밸런싱으로 파티션이 다른 컨슈머에게 넘어가면, **새로 배정받은 컨슈머는 이 커밋된 오프셋부터** 읽기를 시작한다.

## 왜 역할이 다른가 — 하나로 합치면 안 되는 이유

- Current offset은 "지금 이 순간 어디를 읽고 있는가"를 실시간으로 추적하는 **진행 커서(cursor)** 역할. poll()이 다음에 어디서부터 가져올지 결정하는 데만 쓰인다.
- Committed offset은 "장애가 나거나, 재시작되거나, 리밸런싱이 일어났을 때 어디서부터 다시 시작할지"를 정하는 **복구 기준점(체크포인트)** 역할. 컨슈머 프로세스가 죽어도 살아남아야 하는 정보라서 브로커에 영속적으로 저장된다.

만약 이 둘이 항상 같은 값이라면, poll로 메시지를 가져오자마자 자동으로 커밋되는 셈인데 — 처리도 안 했는데 "처리 완료"로 브로커에 기록해버리는 꼴이라, 처리 중 컨슈머가 죽으면 그 메시지는 영영 재처리되지 않고 유실된다. 반대로 처리를 다 끝낸 뒤에만 current offset이 움직인다면, poll 자체가 처리 완료를 기다려야 해서 다음 배치를 미리 가져오는 파이프라이닝이 불가능해져 처리량이 크게 떨어진다.

그래서 카프카는 이 둘을 의도적으로 분리해서, "어디까지 가져왔다"(current)와 "어디까지 확실히 처리했다고 보증한다"(committed)를 컨슈머 애플리케이션이 자기 처리 로직에 맞춰 원하는 시점에 따로 커밋하도록 설계했다.

## 구체적 예시 — 중복 컨슈밍이 여기서 나온다

파티션에 메시지 0~99가 있다고 하자.

1. 컨슈머가 `poll()`로 0~49를 받아옴 → **current offset = 50** (다음 poll은 50부터)
2. 이 중 0~29까지 처리 완료하고 `commitSync()` 호출 → **committed offset = 30**
3. 30~49는 아직 처리 중(또는 처리는 했지만 커밋 전)인 상태에서 **리밸런싱 발생** (다른 컨슈머가 그룹에 join)
4. 이 파티션이 새 컨슈머에게 재배정됨. 새 컨슈머는 current offset(50)이 아니라 **committed offset인 30부터** 다시 읽기 시작
5. → 30~49는 원래 컨슈머가 이미 처리했는데도 새 컨슈머가 또 처리 → **중복 처리 발생**

current offset과 committed offset 사이의 간격(30~49 구간)이 벌어져 있는 상태에서 리밸런싱이 끼어들면, 그 간격만큼 항상 중복 처리 위험이 생긴다. 이게 "카프카는 기본이 at-least-once"라는 말의 근본 메커니즘이다.

## 참고: Lag과의 관계

모니터링 도구(kafka-lag-exporter 등)가 보여주는 컨슈머 랙(lag)은 보통 **Log End Offset(브로커에 실제로 쓰여진 최신 위치) - Committed Offset**으로 계산한다. 커밋이 늦어지면(또는 auto-commit 주기가 길면) 실제 처리 속도와 무관하게 랙 수치가 부풀어 보일 수 있다.

## 비유

동영상 스트리밍 서비스로 비유하면, current offset은 지금 재생 중인 **재생 헤드(playhead) 위치**이고, committed offset은 서버에 주기적으로 동기화되는 **"이어보기" 저장 지점**이다. 재생은 계속 진행 중인데(current offset 전진) 저장 동기화가 아직 안 된 상태(committed offset 정체)에서 앱이 꺼지면, 다시 켰을 때 방금 본 부분을 또 봐야 하는 것 — 이게 중복 컨슈밍과 완전히 같은 구조다.

## 한 줄 정리
> Current offset은 컨슈머 메모리에만 있는 "다음 poll 위치"이고, committed offset은 브로커에 저장되어 재시작/리밸런싱 시 복구 기준점이 되는 "처리 완료 보증 위치"다. 둘 사이 간격이 벌어진 상태에서 리밸런싱이 일어나면 그 구간이 중복 처리된다.
