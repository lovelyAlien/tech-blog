# 카프카가 대량 데이터 처리와 실시간 전송에 강한 이유

"카프카는 대량 데이터 처리와 실시간 전송에 유리하다"는 말은 자주 나오는데, 막상 근거를 대라고 하면 막히기 쉽다. "빠르다"는 결과이고, 그 결과를 만드는 구조적 장치들을 따로 짚어봐야 한다.

## 대량 처리(높은 처리량)의 근거

**순차 디스크 I/O (Sequential I/O)**
카프카는 파티션 로그 파일에 메시지를 append-only(끝에 이어붙이기)로만 쓴다. 랜덤 액세스가 아니라 순차 쓰기/읽기라서, 디스크가 HDD여도 랜덤 I/O 대비 훨씬 빠르다. RDBMS의 랜덤 쓰기/인덱스 갱신과 대비되는 지점이다.

**OS 페이지 캐시 활용**
JVM 힙이 아니라 OS 페이지 캐시에 크게 의존한다. 디스크에 있는 데이터라도 최근 것은 사실상 메모리 속도로 서빙된다 ([[1. kafka]] 참고).

**Zero-Copy 전송**
일반적인 파일 전송은 디스크 → 커널 버퍼 → 애플리케이션 버퍼 → 소켓 버퍼로 여러 번 복사가 일어난다. 카프카는 `sendfile()` 시스템 콜 기반 zero-copy로 커널 영역에서 바로 네트워크로 데이터를 흘려보내, 불필요한 복사와 컨텍스트 스위칭을 없앤다.

**배치(batch) 처리 + 압축**
프로듀서는 메시지를 모아서 배치 단위로 전송하고, gzip/snappy/lz4 등으로 압축까지 건다. 네트워크 왕복 횟수와 전송량 자체를 줄인다.

**파티션 기반 수평 확장**
토픽을 여러 파티션으로 나누면 컨슈머 그룹 내 여러 컨슈머가 병렬로 읽을 수 있다. 처리량이 부족하면 파티션 수·브로커 수를 늘려 확장한다. 단, 파티션 수는 컨슈머 병렬 처리의 상한이 된다는 점도 같이 알아둘 것 ([[1. kafka]], [[파티션 수는 왜 신중하게 정해야 하나]] 참고).

## 실시간 전송(낮은 지연)의 근거

**Pull 기반 컨슈머 모델**
브로커가 push하는 게 아니라 컨슈머가 자기 처리 속도에 맞춰 pull 해간다. `fetch.min.bytes`/`fetch.max.wait.ms`로 롱 폴링처럼 동작해서, 데이터가 도착하는 즉시 가져가면서도 불필요한 빈 요청은 줄인다 ([[컨슈머는 브로커에서 메시지를 어떻게 가져올까 - Pull 기반 Fetch]] 참고).

**프로듀서-컨슈머 디커플링(비동기)**
프로듀서는 컨슈머를 기다리지 않고 브로커에 쓰기만 하면 다음 작업으로 넘어간다. 컨슈머는 독립적으로, 자기 속도로 실시간 소비한다. 이 비동기성 덕분에 발행 지연이 컨슈머 처리 속도에 발목 잡히지 않는다.

**스트림 처리로 즉시 집계**
Kafka Streams 같은 스트림 처리기를 얹으면 메시지가 도착하는 즉시 집계·변환까지 이어져, 배치 처리(예: 매시간 정산)가 아니라 이벤트 발생 직후 반영되는 실시간 대시보드/지표를 만들 수 있다.

## 주의할 트레이드오프

디커플링과 비동기성이 실시간성을 만들어주지만, 동시에 "DB는 갱신됐는데 이벤트는 발행 안 됨" 같은 정합성 문제의 원인이 되기도 한다. 그래서 실무에서는 Transactional Outbox Pattern으로 DB 쓰기와 메시지 발행을 하나의 트랜잭션으로 묶어 보완한다 ([[아웃박스 패턴 심화 - 재시도, 순서 보장, Dual Write 문제]] 참고).

## 한 줄 정리
> 대량 처리는 순차 I/O·페이지 캐시·zero-copy·배치압축·파티션 병렬성이 근거이고, 실시간 전송은 pull 기반 저지연 롱 폴링과 프로듀서-컨슈머 비동기 디커플링이 근거다. 다만 그 디커플링이 정합성 문제를 낳기 때문에 Outbox 패턴으로 보완한다.
