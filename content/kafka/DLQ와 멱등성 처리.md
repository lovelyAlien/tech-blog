## 중복 컨슈밍은 왜 생기는가

카프카 컨슈머가 메시지를 처리했지만 **오프셋 커밋 직전에 리밸런싱**이 일어나면, 파티션을 넘겨받은 새 컨슈머는 마지막으로 커밋된 오프셋부터 다시 읽는다. 그 구간만큼 이미 처리된 메시지가 다시 소비된다.

배포가 잦은 마이크로서비스 구조에서는 배포할 때마다 컨슈머가 재기동되며 리밸런싱이 반복적으로 일어나기 때문에, 이 중복은 예외적 상황이 아니라 **평소에도 늘 발생할 수 있는 정상 케이스**로 취급해야 한다.

카프카는 기본적으로 **at-least-once**를 보장한다. "최소 한 번은 처리된다"는 것이지 "정확히 한 번만 처리된다"는 게 아니다. 이 전제를 먼저 인정하는 것이 멱등성 설계의 출발점.

## 애플리케이션 레벨 멱등성 처리

카프카 설정만으로는 중복을 없앨 수 없으므로, 애플리케이션에서 멱등성을 보장해야 한다.

1. 메시지마다 고유한 **메시지 ID**를 부여
2. 처리 완료된 메시지 ID를 **유니크 제약**이 걸린 테이블/컬럼에 기록
3. 비즈니스 로직 처리와 이 기록을 **같은 트랜잭션**으로 묶음

같은 메시지가 다시 들어와도 유니크 제약 위반으로 걸러지거나, 처리 전에 이미 기록된 ID인지 먼저 조회해서 건너뛴다.

멱등한 연산(같은 입력을 여러 번 적용해도 결과가 같은 연산, 예: `set` 성격의 업데이트)이 가능한 경우엔 그쪽이 더 단순하지만, 실무에서는 적용 가능한 범위가 제한적이라 위 ID 기반 dedup 방식이 더 일반적으로 쓰인다.

## DLQ의 역할

DLQ(Dead Letter Queue)는 N회 재시도 후에도 실패하는 메시지를 별도 토픽으로 옮겨, **무한 재시도로 인한 컨슈머 블로킹을 막는 용도**다. 실패한 메시지 하나 때문에 뒤에 쌓인 정상 메시지들까지 처리가 멈추는 걸 방지한다.

DLQ에 쌓인 메시지는 주기적으로 모니터링하며 원인을 파악한 뒤 수동 재처리하거나, 별도 배치로 재시도하는 방식으로 운영한다.

## 면접 모범 답안 예시

> "배포가 잦은 마이크로서비스 구조라, 배포할 때마다 컨슈머가 재기동되면서 리밸런싱이 발생했습니다. 이때 어떤 컨슈머가 메시지를 처리는 했는데 오프셋 커밋 직전에 리밸런싱이 일어나면, 파티션을 넘겨받은 새 컨슈머는 마지막으로 커밋된 오프셋부터 다시 읽기 때문에 중복 소비가 발생했습니다.
>
> 카프카 자체는 at-least-once가 기본이라 이 중복을 카프카 설정만으로 없앨 수는 없다고 보고, 애플리케이션 레벨에서 멱등성을 보장했습니다. 메시지마다 고유 ID를 부여하고, 처리 완료된 메시지 ID를 유니크 제약이 걸린 테이블에 기록하면서 비즈니스 로직 처리와 같은 트랜잭션으로 묶었습니다.
>
> DLQ는 N회 재시도 후에도 실패하는 메시지를 별도 토픽으로 보내 무한 재시도로 인한 컨슈머 블로킹을 막는 용도로 썼고, DLQ에 쌓인 메시지는 주기적으로 모니터링하며 원인 파악 후 수동/배치로 재처리했습니다."

## 꼬리질문과 모범 답안

### Q. 메시지 ID는 프로듀서가 생성하나요, 아니면 오프셋+파티션을 조합해서 쓰나요?

오프셋+파티션 조합은 "이 물리적 레코드를 두 번 안 읽었다"만 보장한다. **프로듀서가 네트워크 오류로 재전송하면 같은 논리적 이벤트가 새 오프셋으로 다시 발행**될 수 있는데, 이 경우 오프셋 기반 ID로는 중복을 못 잡는다.

그래서 **프로듀서가 도메인 이벤트 ID**(UUID, 혹은 "주문ID+이벤트타입+시퀀스" 같은 자연키 조합)를 메시지 자체에 실어 보내는 방식이 더 안전하다. 재전송돼도 이 ID는 그대로 유지되기 때문에 진짜 논리적 중복을 판별할 수 있다.

> **답변 포인트**: "오프셋 기반 ID는 물리적 중복만 막고, 프로듀서 재시도로 인한 논리적 중복은 못 막는다"는 차이를 짚는 것이 핵심.

### Q. 유니크 제약 위반으로 트랜잭션이 롤백될 텐데, 그 시점에 이미 처리한 부작용(외부 API 호출 등)이 있다면?

이게 진짜 어려운 지점이다. DB 유니크 제약은 **DB 안의 부작용만** 막아준다. 외부 API 호출처럼 트랜잭션 밖에서 일어나는 부작용은 롤백해도 이미 실행된 채로 남는다.

완벽한 멱등은 사실 애플리케이션 혼자 힘으로는 못 만들고, 다음 전략들로 리스크를 낮추는 접근이 현실적이다.

- **외부 API 자체가 멱등키를 지원**하면(결제 PG 등에서 흔함) 같은 idempotency key로 여러 번 호출해도 서버가 중복을 걸러줌 — 가장 확실한 방법
- 외부 API가 멱등을 지원하지 않으면, 처리 시작 전에 상태를 **PENDING으로 먼저 마킹**하고, 완료 후 DONE으로 갱신 — 재시도 시 PENDING 상태면 이미 진행 중/불확실한 상태로 보고 별도 조사 큐로 보냄
- 그래도 못 막는 부작용(예: 알림 중복 발송)은 **보상 트랜잭션**이나 모니터링·수동 개입 대상으로 인정

> **답변 포인트**: "DB 트랜잭션만으로는 완전한 멱등을 못 만든다"는 걸 스스로 인정하고, 외부 API의 멱등키 지원 여부에 따라 대응이 달라진다는 걸 설명하면 실무 경험이 있다는 인상을 준다.

### Q. DLQ로 보낸 메시지의 재처리 순서는 어떻게 보장하나요?

DLQ에 쌓이는 순간 **원래 파티션의 순서 컨텍스트를 잃는다.** 서로 다른 사용자/엔티티의 실패 메시지들이 도착 순서대로 뒤섞여 쌓이기 때문에, DLQ 자체는 순서를 보장하지 않는다.

대응 방법:
- DLQ 메시지에 원본 파티션 키(예: userId)와 원본 오프셋/타임스탬프를 메타데이터로 같이 담아서, 재처리 시 그 키 기준으로 그룹핑·정렬 후 순차 재처리
- 순서가 정말 중요한 도메인이라면, 특정 키의 메시지가 실패했을 때 그 뒤에 오는 같은 키의 메시지도 재시도 전까지 보류하는 정책(해당 키만 별도 큐로 격리)

> **답변 포인트**: "DLQ는 순서 보장을 포기하는 대신 가용성(다른 메시지는 계속 처리됨)을 얻는 트레이드오프"라는 통찰을 던지는 것이 핵심.

## 한 줄 정리
> 카프카의 at-least-once 전제 위에서, 멱등성은 메시지 ID + 유니크 제약 + 트랜잭션으로 DB 안에서는 보장할 수 있지만, 외부 API 호출 같은 트랜잭션 밖 부작용까지 완벽히 막으려면 멱등키 지원 여부에 따라 별도 전략이 필요하다. DLQ는 무한 재시도를 막아주는 대신 순서 보장을 포기하는 트레이드오프다.
