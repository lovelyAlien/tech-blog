# 3Sum: 정렬 + 투 포인터, 그리고 중복 제거가 진짜 핵심인 이유

배열에서 합이 0이 되는 **서로 다른 세 수의 조합을 전부** 찾는 문제다. Two Sum의 확장판처럼 보이지만, "중복 없는 정답 집합"이라는 조건 때문에 풀이 난이도가 확 올라간다. 브루트포스 → 해시셋 → 투 포인터로 이어지는 최적화 과정과, 그 과정에서 실제로 겪은 중복 버그를 정리해 둔다.

- 문제: [LeetCode 15. 3Sum](https://leetcode.com/problems/3sum/)

## 문제 요약

- 정수 배열 `nums`가 주어질 때, `nums[i] + nums[j] + nums[k] == 0` (`i != j != k`)을 만족하는 **모든 유일한 triplet**을 반환한다.
- 정답 집합에 **중복된 triplet이 있으면 안 된다** (값 기준, 인덱스 기준 아님).
- 제약: `3 <= nums.length <= 3000`, `-10^5 <= nums[i] <= 10^5`

```
Input:  nums = [-1,0,1,2,-1,-4]
Output: [[-1,-1,2],[-1,0,1]]
```

## 접근: "짝 찾기"에 "중복 제거"가 얹히는 문제

Two Sum처럼 완전탐색은 O(n³)이다. 하나를 고정하면 나머지 둘은 "합이 특정 값인 두 수 찾기" = Two Sum으로 줄어드니, 바깥에 루프 하나를 더 얹고 안쪽을 O(n) 또는 O(log n)으로 줄이면 O(n²)까지 내려간다. 여기까지는 Two Sum의 확장일 뿐이다.

진짜 어려운 부분은 **"유일한 triplet만"** 조건이다. 배열에 값이 중복되면(`[-1,-1,0,1,1]` 같은 경우) 같은 조합을 여러 경로로 여러 번 찾게 된다. 이걸 막으려고 처음엔 배열을 정렬하지 않은 채로 풀었다가 중복이 그대로 새 나가는 버그를 겪었고, 정렬 후 두 가지 방식으로 다시 풀었다.

| 방식 | 시간 | 공간(출력 제외) | 비고 |
|---|---|---|---|
| 완전탐색 (3중 루프) | O(n³) | O(1) | 가장 단순, 중복 제거도 안 됨 |
| 정렬 + `i` 고정 + 해시셋 | O(n²) | O(n) | `i`마다 `HashSet`을 새로 만들어 나머지 두 수를 찾음 |
| **정렬 + `i` 고정 + 투 포인터** | **O(n²)** | **O(1)** | 정답. 양 끝에서 좁혀가며 탐색 |

시간복잡도는 둘 다 O(n²)로 같지만, 투 포인터는 `i`마다 추가 자료구조가 필요 없어 공간이 O(1)로 줄어든다. 그래서 최종적으로 투 포인터 버전을 정답으로 삼았다.

## 제출한 풀이

```java
class Solution {
    public List<List<Integer>> threeSum(int[] nums) {
        Arrays.sort(nums);
        List<List<Integer>> res = new ArrayList<>();
        int n = nums.length;
        for (int i = 0; i < n - 2; i++) {
            int j = i + 1, k = n - 1;

            if (i > 0 && nums[i] == nums[i - 1]) continue;

            while (j < k) {
                int sum = nums[i] + nums[j] + nums[k];
                if (sum == 0) {
                    res.add(Arrays.asList(nums[i], nums[j], nums[k]));
                    j++;
                    k--;
                    while (j < k && nums[j] == nums[j - 1]) j++;
                } else if (sum < 0) {
                    j++;
                } else {
                    k--;
                }
            }
        }
        return res;
    }
}
```

## 핵심 포인트

### 1. 정렬이 투 포인터를 가능하게 한다

정렬되어 있으면 `nums[i]`를 고정했을 때 `nums[j] + nums[k]`가 "너무 작으면 `j`를 오른쪽으로(더 큰 값), 너무 크면 `k`를 왼쪽으로(더 작은 값)"라는 단조로운 규칙이 성립한다. `j`와 `k`는 서로를 향해서만 움직이고 절대 되돌아가지 않으므로, `i` 하나당 최대 `n`번의 비교로 끝난다.

### 2. 중복 제거는 두 군데서 일어난다

- **`i` 중복 스킵** (`nums[i] == nums[i-1]`): 이전 `i`가 이미 `nums[i+1..]` 전체(현재 `i`의 탐색 범위를 포함하는 더 넓은 범위)를 훑었기 때문에, 같은 값으로 다시 훑어봐야 새로운 조합이 안 나온다.
- **매칭 성공 후 `j` 중복 스킵**: 고정된 `i`에서 `k`가 될 값은 `-nums[i]-nums[j]`로 `nums[j]`에만 의존하는 함수다. `nums[j]`가 연속으로 같은 값이면 같은 `k`를 다시 찾아버리므로, 매칭 직후 중복값을 건너뛴다.

**`k` 쪽엔 대칭적인 dedup이 없는데도 버그가 안 나는 이유**: 매칭 성공 직후 `j`는 반드시 이전 매칭값보다 "엄격히 큰" 값으로 넘어간다(dedup 때문에). 이전 매칭에서 `nums[i] + oldJ + oldK == 0`이었는데, `newJ > oldJ`이므로 `nums[i] + newJ + oldK > 0`이 되어 다음 비교에서 자동으로 `k--`가 실행된다. 즉 `k`가 그대로 있어도 같은 조합이 다시 `sum == 0`이 될 수학적으로 불가능하다. `k` dedup은 정답 정확성이 아니라 (중복값이 많은 입력에서) 비교 횟수를 살짝 줄여주는 효율 최적화일 뿐이다.

### 3. O(n²)가 사실상 하한인 이유

브루트포스 O(n³)에서 O(n²)까지 줄였는데, 여기서 더 줄이기 어렵다. `nums = [-m,...,-1,0,1,...,m]`처럼 값이 0을 중심으로 대칭 분포하면, 합이 0인 유일한 triplet 개수 자체가 `n`에 대해 제곱으로 늘어난다(n=5→2개, n=7→5개, n=9→8개, 점근적으로 Θ(n²)). **정답을 전부 출력하는 것 자체가 최악의 경우 Θ(n²) 시간이 걸리므로**, 어떤 알고리즘도 이보다 빠를 수 없다. "존재 여부만 판단"하는 더 쉬운 decision 버전에 대해서도 일반적인 비교 연산 모델에서는 `O(n^{2-ε})`이 불가능하다는 **3SUM conjecture**가 있다 (computational geometry의 여러 hardness 증명의 기반이 되는 유명한 가정).

### 4. 손 추적 예시

`nums = [-4,-1,-1,0,1,2]` (정렬됨)

```
i=0(-4): j=1,k=5  sum=-4-1+2=-3<0 → j++
         j=2,k=5  sum=-4-1+2=-3<0 → j++
         ...끝까지 가도 양수 두 개 합이 4를 못 넘음 → 매칭 없음

i=1(-1): j=2,k=5  sum=-1-1+2=0  → [-1,-1,2] 추가, j=3,k=4
         j=3,k=4  sum=-1+0+1=0  → [-1,0,1] 추가, j=4,k=3 → j<k 깨짐, 종료

i=2(-1): nums[2]==nums[1] → 스킵

i=3(0):  j=4,k=5  sum=0+1+2=3>0 → k--  → j<k 깨짐, 종료
```

결과: `[[-1,-1,2],[-1,0,1]]` — 정확히 기대값과 일치.

## 주의할 점 / 흔한 실수

- **정렬하지 않고 해시맵/해시셋만으로 풀면 중복 triplet이 그대로 새 나간다.** `nums=[0,0,0,0]`을 정렬 없이 단순 이중 루프 + 해시맵으로 풀면 `[0,0,0]`이 3번 중복 반환되는 걸 직접 확인했다. 정렬 자체는 dedup을 "가능하게" 해주는 전제 조건이지, 정렬만으로 저절로 dedup되는 게 아니다 — `i`/`j` 스킵 로직을 별도로 넣어야 한다.
- **`i` dedup만 넣고 `j`(또는 `k`) dedup을 빠뜨리면**, `i`가 겹치지 않아도 같은 `i` 안에서 `nums[j]`가 연속 중복일 때 같은 triplet이 여러 번 추가된다.
- **`j`와 `k` dedup을 대칭으로 둘 다 넣어야 한다고 착각하기 쉬운데**, 위 "핵심 포인트 2"에서 본 것처럼 한쪽만 있어도 정답은 정확하다. 양쪽 다 넣는 건 스타일/효율 문제지 정합성 문제가 아니다.
- **`i` 루프 종료 조건은 `i < n - 2`.** `n < 3`이면 `n - 2`가 0 이하가 되어 루프가 아예 안 도니, 별도 예외 처리 없이도 빈 리스트가 안전하게 반환된다.

## 한 줄 정리
> 정렬로 단조성을 확보하면 투 포인터로 O(n²)·O(1) 공간에 풀리고, 정답의 "유일성"은 `i`와 매칭 직후 `j`, 단 두 군데의 dedup만으로 충분히 보장된다 — 이 O(n²)는 최악의 경우 출력 자체가 Θ(n²)라 사실상 하한이다.
