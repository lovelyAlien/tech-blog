# MCP는 기존 API와 무엇이 다른가?

AI 에이전트에 도구를 붙일 때마다 API를 하나씩 통합하던 방식은 도구가 늘수록 감당하기 어려워진다. MCP(Model Context Protocol)는 이 연동 방식을 표준화한 프로토콜이라, 개념과 API와의 차이를 같이 설명할 수 있어야 한다.

> 출처: [What is Model Context Protocol (MCP)? How it simplifies AI integrations compared to APIs](https://norahsakal.com/blog/mcp-vs-api-model-context-protocol-explained/) (Norah Klintberg Sakal, 2025-03-07)

## MCP란 무엇인가

MCP는 **AI 에이전트를 외부 도구·데이터 소스에 연결하는 표준 프로토콜**이다. Anthropic이 시작했고 지금은 오픈 스펙이다(modelcontextprotocol.io).

비유하면 **AI용 USB-C 포트**다. USB-C 하나로 여러 기기를 컴퓨터에 꽂듯, MCP 하나로 여러 도구를 AI에 꽂는다.

## 기존 API 방식의 문제: 문마다 열쇠가 다르다

![[API 연동 방식 - 도구마다 열쇠.png]]

AI가 Gmail, Calendar, Slack을 쓰게 하려면 서비스마다 아래를 따로 구현해야 한다.

- 인증 방식
- 요청/응답 형식
- 에러 처리
- 문서 파악과 유지보수

서비스가 늘면 통합 코드가 같은 비율로 늘어난다. 서비스 수만큼 만들어야 하는 N개의 커스텀 통합이다.

## MCP 아키텍처

![[MCP 아키텍처.png]]

클라이언트-서버 구조이고, 구성 요소는 4가지다.

| 구성 요소 | 역할 | 예시 |
|---|---|---|
| MCP Host | 외부 도구/데이터가 필요한 애플리케이션 | Claude Desktop, AI IDE |
| MCP Client | 서버와 **1:1 연결**을 유지 | `client.py` |
| MCP Server | 특정 기능을 노출하는 가벼운 서버 | Slack/Gmail/Calendar/파일시스템 서버 |
| 데이터 소스 | 서버가 접근하는 대상 | 로컬 파일·DB, 원격 서비스 API |

- MCP 서버는 무거운 로직을 직접 처리하지 않는다. 모델과 도구 사이에서 데이터와 지시를 중개하는 다리 역할이다.
- 그림에서 Slack, Gmail, Calendar 같은 원격 서비스와 로컬 파일은 모두 **서버를 거쳐** 같은 포트(MCP)에 연결된다.

## MCP vs API 비교

| 항목 | MCP | 전통적 API |
|---|---|---|
| 통합 노력 | 표준화된 단일 통합 | API마다 별도 통합 |
| 실시간 통신 | 가능 (연결 유지) | 기본적으로 요청/응답 |
| 동적 탐색 | 가능 | 불가 (하드코딩) |
| 확장성 | 서버 추가로 plug-and-play | 통합을 추가로 개발 |
| 보안·제어 | 도구 전반에 일관 | API마다 제각각 |

핵심 차이는 3가지다.

1. **단일 프로토콜**: 통합 하나로 여러 도구를 쓴다. "한 번 만들고 여러 번 연결"하는 구조다.
2. **동적 탐색(Dynamic Discovery)**: 모델이 서버에 어떤 도구가 있는지 물어보고 쓴다. 도구별 지식을 코드에 박아둘 필요가 없다.
3. **양방향 통신**: 데이터를 가져오는 것(캘린더 조회)과 행동을 일으키는 것(일정 변경, 메일 발송)을 둘 다 한다.

> [!warning] 원문 표현 보충
> 원문은 MCP를 "WebSocket처럼 양방향 실시간"이라고 설명한다. MCP는 JSON-RPC 기반 메시지 규약이고, 전송 방식(transport)은 **stdio(로컬)** 또는 **HTTP 기반 스트리밍(원격, SSE 계열)** 이다. 원문이 말하는 WebSocket은 공식 스펙의 기본 transport가 아니다. 면접에서는 "연결을 유지하며 양방향 메시지를 주고받는 구조" 정도로 말하는 게 안전하다.

## 언제 MCP를 쓰는가

- **여행 계획 어시스턴트**: 캘린더 확인, 항공권 예약, 확인 메일 발송을 도구별 커스텀 코드 없이 MCP 서버로 처리한다.
- **IDE**: 파일시스템, 버전 관리, 패키지 매니저, 문서를 한 프로토콜로 묶어 더 풍부한 컨텍스트를 준다.
- **복합 데이터 분석**: 여러 DB와 시각화 도구를 하나의 MCP 계층으로 발견하고 사용한다.

## MCP 도입의 장점

- 개발 단순화: write once, integrate many times
- 유연성: 모델이나 도구를 바꿔도 재설정 부담이 적다
- 실시간 대응: 연결이 유지돼 컨텍스트를 즉시 갱신한다
- 보안·컴플라이언스: 접근 제어와 표준 보안 관행을 갖춘다
- 확장성: MCP 서버를 하나 더 연결하면 기능이 추가된다

## 그래도 API가 나은 경우

MCP는 유연하고 컨텍스트 중심이라, 엄격하고 결정적인(deterministic) 시스템에는 덜 맞는다. 아래 경우에는 세분화된 API가 낫다.

- 기능을 세밀하게 제한해야 할 때
- 성능을 위해 강하게 결합(tight coupling)해야 할 때
- 모델의 자율성을 최소화하고 예측 가능성을 최대화해야 할 때

> [!warning] 보충
> MCP와 API는 대체 관계가 아니다. MCP 서버도 내부에서는 결국 각 서비스의 API를 호출한다. MCP는 "AI가 그 API들을 일관된 방식으로 발견하고 쓰게 하는 중간 계층"이다.

## 시작하는 순서

1. 서버가 제공할 기능을 정의한다
2. 프로토콜 스펙에 맞춰 MCP 계층을 구현한다
3. 전송 방식을 고른다 (로컬 stdio / 원격 SSE 등)
4. 노출할 리소스·도구를 만들거나 연결한다
5. 서버와 클라이언트 사이 연결을 안정적·안전하게 구성한다

## 한 줄 정리
> MCP는 "AI 에이전트용 USB-C"다. 도구마다 API를 따로 통합하는 대신 표준 프로토콜 하나로 도구를 발견하고 쓰게 해서, 도구가 늘어도 통합 비용이 선형으로 커지지 않게 한다.
