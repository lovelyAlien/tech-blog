## 배경
올리브영 배송스쿼드 1년차 개발자가 주문/배송 상태 변경 로직에 직접 박혀있던 알림톡(카카오 알림톡) 발송 코드를, 트랜잭션 커밋 이후 Kafka 이벤트를 발행하고 별도 컨슈머가 처리하는 구조로 분리한 경험담.

## 왜 바꿨나?
- **로직 산재**: 알림톡 발송 코드가 여러 비즈니스 코드에 흩어져 있어 수정이 번거로움
- **데이터 조회 기준 불일치**: 같은 알림도 서비스마다 다른 테이블/조건으로 조회
- **더 근본적인 문제**: 기존엔 알림톡 발송을 `try-catch`로 감싸서 비즈니스 로직 성공/실패와 무관하게 발송 → 알림톡은 이미 나갔는데 이후 로직에서 에러가 나면 **실제 데이터 상태와 고객에게 간 알림이 어긋남**. 재실행하면 중복 발송까지 발생.
## 해결 방법: 트랜잭션 동기화
### 시도 1 — `@TransactionalEventListener` (실패)
가장 표준적인 Spring 방식이지만, 레거시가 구버전 Spring이라 `TransactionPhase.AFTER_COMMIT` 자체가 존재하지 않았음. 버전을 올리려니 공통 모듈 의존성 충돌 → `NoClassDefFoundError`(클래스패스에 신/구버전 클래스가 섞여서 런타임에 메서드 시그니처 불일치) 연쇄 발생. 결국 포기.

### 시도 2 — TransactionSynchronizationManager (채택)
이벤트 발행/리스너 구조는 아니지만, **트랜잭션 커밋 후 실행될 콜백을 직접 등록**해서 동일한 효과(커밋 확정 후에만 후속 처리)를 얻음.
> Spring이 트랜잭션 생명주기(시작/커밋/롤백)에 콜백을 끼워넣을 수 있게 해주는 저수준 API. `@TransactionalEventListener`가 내부적으로 이걸 활용해서 만들어진 고수준 기능이라고 보면 됨. 구버전 Spring에서도 존재해서 이번 케이스의 대안이 될 수 있었음.

- 메시지 발행 실패 시 실패 로그를 DB에 저장해 재처리하는 구조로 설계.
- 저자가 스스로 짚은 개선 여지: **Outbox Pattern**을 쓰면 더 안전.

## 개선 사항

| 구분       | 기존 (Legacy)                   | 개선 후 (Modern)              |
| -------- | ----------------------------- | -------------------------- |
| 아키텍처     | 서비스 로직에 발송 코드 결합 (Monolithic) | Kafka 기반 이벤트 주도 아키텍처 (EDA) |
| 발송 시점 보장 | 비즈니스 로직 결과와 무관하게 발송           | afterCommit으로 트랜잭션 정합성 확보  |
| 데이터 조회   | 서비스별 산재된 테이블/조건               | 통합 기준 조회                   |
| 관리 주체    | 각 비즈니스 도메인 서비스                | Delivery Consumer로 일원화     |
| 확장성      | 알림톡 추가마다 레거시 수정/배포            | 템플릿 등록 + 메시지 발행만으로 확장      |

> **기본 개념 — EDA(Event-Driven Architecture)**  
> 서비스들이 서로 직접 호출하지 않고, "이벤트가 발생했다"는 사실만 메시지 브로커(Kafka)에 발행하고, 관심 있는 다른 서비스가 이를 구독(consume)해서 각자 알아서 처리하는 구조. 서비스 간 결합도(coupling)를 낮추고, 새 구독자를 추가해도 발행자 코드를 안 건드려도 되는 게 장점.

## 주의 
저자가 말했다시피,
```
다행히 운영 환경에서 서버 장애로 인한 메시지 유실은 발생하지 않았지만, 이번 개발 과정을 회고해보니 더 높은 안정성이 요구되는 환경이라면 Outbox Pattern을 통해 이벤트를 DB에 먼저 저장한 후 별도 프로세스가 발행하도록 하거나, 재시도 메커니즘 같은 방어책들을 추가로 고려해볼 필요가 있겠다는 생각이 들었습니다. 당장은 필수는 아니지만 이런 부분들도 점진적으로 개선해나가면 좋을 것 같습니다.
```
저자가 적용한 운영 환경에서는 메시지 유실이 없었지만, 커밋 이후 발행 단계에서 장애가 나면 유실될 여지가 있어 완전한 원자성 보장은 아니라 봅니다. 이를 보완하려면 아웃박스 패턴처럼 이벤트 기록을 비즈니스 트랜잭션에 포함시키는 방식을 고려할 수 있습니다.
## Outbox Pattern
"커밋 후 바로 메시지 발행"은 커밋과 메시지 발행 사이에 아주 짧은 간극이라도 서버가 죽으면 메시지가 유실될 수 있어. Outbox Pattern은 이벤트를 **같은 트랜잭션 안에서 DB의 별도 outbox 테이블에 저장**하고, 별도 프로세스(폴링 또는 CDC)가 이 테이블을 읽어 메시지를 발행하는 방식. 이러면 "DB 저장"과 "이벤트 발행 예정"이 하나의 원자적 트랜잭션이 되어 유실 가능성이 사라짐.

|구성요소|역할|
|---|---|
|**Sender**|비즈니스 로직을 수행하고 메시지를 보내야 하는 서비스 자신 (예: Delivery 서비스)|
|**Database**|비즈니스 엔티티 테이블과 outbox 테이블을 함께 담고 있는 하나의 DB|
|**Message outbox**|DB 안의 테이블 하나. "이런 메시지를 나중에 브로커로 보내야 함"이라는 기록을 임시로 쌓아두는 곳|
|**Message relay**|outbox 테이블을 감시하다가 쌓인 메시지를 실제 메시지 브로커(Kafka 등)로 보내주는 별도 프로세스|
### 동작 흐름
- **Sender**가 비즈니스 데이터 변경과 outbox 메시지 저장을 **같은 트랜잭션**으로 커밋
- **Message relay**(폴링 또는 CDC)가 outbox 테이블을 감시하다가 새 메시지를 발견
- 발견한 메시지를 **Message broker**(Kafka)로 발행

### 핵심(?)
**DB 커밋까지는 원자적**이고, **브로커 발행은 그 이후 별도로 처리**됨. 그래서 "커밋되면 반드시 발행된다"는 보장은 되지만, 발행이 중복될 수 있어 컨슈머는 멱등하게 설계해야 함
