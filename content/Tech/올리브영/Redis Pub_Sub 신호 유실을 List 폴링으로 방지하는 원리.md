핵심부터 말하면, **"신호(알림)"와 "데이터"의 저장 위치를 분리**해서 Pub/Sub의 유실 가능성을 List의 영속성으로 보완한 설계입니다.

- Pub/Sub 메시지 = 그 자체가 처리 대상이 아니라, "확인해봐"라는 알림
- List에 RPush된 값 = 실제로 처리해야 하는 쿠폰 발급 데이터

## 1차 버전: Pub/Sub 단독 사용의 문제

선착순 쿠폰 이벤트에서 동시 접속이 몰리자, 검증까지는 즉시 처리하고 실제 발급은 별도 Worker에 위임하는 비동기 구조로 바꿨습니다. 이때 웹서버 → Worker 전달 수단으로 Redis Pub/Sub만 사용했더니 두 가지 문제가 났습니다.

- **과발급**: 여러 Worker가 같은 메시지를 동시에 수신해서 중복 발급
- **미발급**: Pub/Sub은 메시지를 보관하지 않고 수신 확인(ACK)도 하지 않음 → Worker가 재시작 중이거나 네트워크가 순간적으로 끊겨 구독이 끊긴 타이밍에 온 메시지는 아무도 못 받고 그냥 증발

Pub/Sub = "그 순간 듣고 있던 사람만 듣는 방송"이라, 방송을 놓치면 복구할 방법이 없다는 게 근본 원인입니다.

## 2차 버전: 신호와 데이터를 분리

```
1. Worker 구동 시 '일련번호' 자동 생성
2. 모든 Worker가 '쿠폰발급' Topic 구독
3. Worker가 주기적으로 자신의 저장소 List 크기 확인   ← 안전망
4. 사용자 요청 시 1개 Worker 선택 + Topic Publish       ← 신호(옵션)
5. 선택된 Worker의 List에 RPush                          ← 데이터는 여기 저장
6. Worker가 LPop으로 데이터 취출 후 DB INSERT
```

핵심은 3번(주기적 폴링)이 4번(Pub/Sub 신호)과 **무관하게 항상 동작**한다는 것입니다.

- 신호 정상 수신 → 즉시 List 확인 → 빠르게 처리 (최적화 경로)
- 신호 유실 → Worker는 유실된 줄도 모름 → 하지만 다음 폴링 타이밍에 어차피 List를 열어보므로 결국 발견해서 처리 (안전망 경로)

즉 Worker는 "유실이 발생했는지"를 판단하지 않습니다. 판단할 방법 자체가 없기 때문입니다(신호가 안 온 이유가 애초에 선택을 안 받은 건지, 유실된 건지 구분 불가). 그래서 신호 수신 여부와 무관하게 **무조건 주기적으로 List를 확인**하는 방식으로 우회한 것이 이 설계의 본질입니다.

## 동작 흐름 예시

Worker-3(일련번호 3), 폴링 주기 100ms 가정.

| 시각 | 이벤트 | List(`coupon:worker:3`) 상태 | Worker 동작 |
|---|---|---|---|
| 0ms | 고객A 요청 → Worker-3 선택 → RPush(A) → Publish("3") 시도했으나 네트워크 순단으로 신호 유실 | `[A]` | 신호를 못 받아 대기 |
| 50ms | 고객B 요청 → 다시 Worker-3 선택 → RPush(B) → 이번엔 Publish 신호 정상 도착 | `[A, B]` | 신호 수신 → 즉시 LPop |
| 50ms 직후 | LPop 결과 → FIFO라 먼저 들어간 A가 꺼내짐 (B를 위한 신호였지만 실제로는 A가 처리됨) | `[B]` | DB INSERT(A) |
| 100ms | 폴링 주기 도래 | `[B]` | List에 1개 남아있음 발견 → LPop → B 꺼냄 → DB INSERT(B) |

포인트:
- 고객A의 신호는 유실됐지만 RPush 자체는 Publish와 독립적으로 항상 성공하므로 데이터는 유실되지 않음
- 신호는 "특정 데이터를 처리하라"는 지시가 아니라 그냥 "List를 확인해보라"는 범용 트리거일 뿐 — 실제로 어떤 데이터가 꺼내지는지는 List의 FIFO 순서(RPush/LPop)가 결정
- 최악의 경우(신호가 계속 안 옴)에도 다음 폴링 주기만큼만 지연될 뿐, 데이터는 절대 사라지지 않음

## 왜 신호/폴링 두 경로가 같은 데이터를 중복 처리하지 않는가

`LPop`이 **원자적으로 제거하면서 꺼내는** 연산이기 때문입니다. List 안에 데이터가 남아있다는 것 자체가 "아직 아무도 안 가져갔다"는 뜻이고, 누군가 LPop 하는 순간 즉시 사라집니다.

- 신호로 이미 처리된 데이터 → 폴링 시점엔 이미 List에서 사라진 뒤라 폴링이 봐도 없음 → 중복 처리 안 됨
- 신호가 유실된 데이터 → 아무도 안 건드렸으니 그대로 List에 남아있음 → 폴링이 발견해서 처리

그래서 "신호 경로"와 "폴링 경로"는 서로 다른 감시자가 아니라, **같은 큐를 비우는 동일한 동작을 서로 다른 타이밍(이벤트 발생 시 / 주기적으로)에 트리거하는 것**뿐입니다.

## 원문이 다루지 않는 한계

- Worker가 LPop 한 직후, DB INSERT 하기 전에 죽으면 그 데이터는 여전히 유실 가능 (원문 미언급)
- List 자체가 영속화(AOF/RDB)되어 있는지, 순수 인메모리라 Redis 재시작 시 날아가는지도 불명확

## 한 줄 정리
> 신호(Pub/Sub)는 잃어버려도 되지만 데이터(List)는 잃어버리면 안 된다 — 그래서 데이터를 신호와 분리해 별도로 저장하고, Worker가 신호와 무관하게 주기적으로 List를 확인하도록 만들어 신호 유실이 곧 데이터 유실로 이어지지 않게 했다.
