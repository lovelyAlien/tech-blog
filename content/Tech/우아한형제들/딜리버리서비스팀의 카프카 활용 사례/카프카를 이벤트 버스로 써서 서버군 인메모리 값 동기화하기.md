# 카프카를 이벤트 버스로 써서 서버군 인메모리 값 동기화하기

우아한형제들 딜리버리서비스팀 사례. "이벤트 버스"라는 말이 낯설었는데, 평소 익숙한 카프카 사용법(일감 나눠 갖기)과 정반대 목적(모두에게 방송하기)이라는 걸 알고 나니 이해가 됐다.

## 왜 인메모리에 값을 들고 있나

배달서버는 주문이 들어올 때마다 "이 주문을 어디로 배정할지"를 즉시 결정해야 한다. 예를 들면 이런 규칙이다.

```
RouteRuleSet (인메모리 Map)
{
  "강남구": "라이더그룹A",
  "송파구": "라이더그룹B",
  "종로구": "라이더그룹A"
}
```

이 결정은 초당 수백~수천 건씩 벌어지는 빈번한 연산이라, 매번 DB를 조회하면 부하·지연이 커진다. 그래서 서버가 시작할 때(또는 값이 바뀔 때) 한 번 읽어서 메모리(Map 등)에 캐시해두고, 요청 처리 중에는 그 메모리 값만 참조한다.

## 왜 서버군 전체가 동시에 갱신되어야 하나

배달서버가 3대(delivery-1/2/3)라고 하자. 운영자가 "강남구는 이제 라이더그룹C로 보내라"고 바꿨는데 delivery-1만 갱신되고 나머지는 옛 규칙을 들고 있다면:

```
강남구 주문 → delivery-1이 처리 → 라이더그룹C 배정 (새 규칙)
강남구 주문 → delivery-2가 처리 → 라이더그룹A 배정 (옛 규칙)
강남구 주문 → delivery-3이 처리 → 라이더그룹A 배정 (옛 규칙)
```

같은 강남구 주문인데 어느 서버가 처리하느냐에 따라 결과가 달라지는 비일관성이 생긴다. 그래서 규칙이 바뀌는 순간 서버군 전체가 동시에 갱신돼야 한다.

## 평소 카프카 사용법과의 차이 — "나눠 갖기" vs "다 같이 받기"

평소 컨슈머 그룹은 **일감을 나눠 갖는** 용도다. 같은 그룹 안에서는 메시지 하나를 그룹 내 컨슈머 중 딱 하나만 소비한다(처리량 분산).

```
토픽(파티션 3개) + 컨슈머그룹 "order-processor" (인스턴스 3대)
→ P0는 인스턴스1, P1은 인스턴스2, P2는 인스턴스3이 소비
→ 메시지 하나는 셋 중 하나만 처리
```

그런데 분배 규칙 변경은 반대다. 메시지 하나를 **서버 전부가 각자** 받아서 자기 인메모리를 갱신해야 한다. 이게 이벤트 버스(=방송, broadcast) 개념이다.

## 카프카로 방송을 구현하는 방법 — 그룹 자체를 서버 수만큼 쪼갠다

핵심은 "그룹 내부에서 여러 컨슈머가 나눠 갖는" 게 아니라 **그룹 자체를 서버 개수만큼 쪼개는** 것이다. 각 그룹은 멤버가 딱 1명(그 서버 자신)이다.

```
❌ 오해: 그룹 하나 + 컨슈머 3개 (그룹 내부에서 나눠 가짐 — 하나만 받음)
✅ 실제: 그룹 3개 + 각 그룹에 컨슈머 1개 (그룹끼리는 서로 독립적으로 전체를 다 읽음)
```

카프카에서 오프셋은 **컨슈머 그룹 단위**로 관리되므로, 서로 다른 그룹은 완전히 남남이다. 각자 자기 오프셋으로 토픽을 처음부터 끝까지 독립적으로 읽는다. 그래서 컨슈머 그룹 ID를 `${서버명}:${식별자}` 형식으로 서버마다 다르게 주면, 발행은 한 번인데 그룹 수(=서버 수)만큼 독립적으로 배달되는 결과가 나온다.

```mermaid
flowchart LR
    PUB["운영자가 규칙 변경\n(1회 발행)"] --> TOPIC["event-bus 토픽\n(파티션 1개)"]
    TOPIC --> G1["컨슈머그룹\ndelivery:server1"] --> S1["서버1 인메모리 갱신"]
    TOPIC --> G2["컨슈머그룹\ndelivery:server2"] --> S2["서버2 인메모리 갱신"]
    TOPIC --> G3["컨슈머그룹\ndelivery:server3"] --> S3["서버3 인메모리 갱신"]
```

파티션은 처리량이 크게 필요 없어 1개로 관리한다 — 필요한 건 처리량 분산이 아니라 "같은 서버군이 같은 변경사항을 받는 것"이기 때문이다.

## RemoteApplicationEvent는 이 방송 위에 목적지를 얹는 포장지

스프링 클라우드의 `RemoteApplicationEvent`는 위 브로드캐스트 메커니즘 위에 "이 이벤트가 어떤 서버군을 향한 것인가"라는 라우팅 정보를 추가해주는 추상화다.

### 비유: 3개 지점이 있는 배달 사무실

배달서버 3대를 강남지점·송파지점·종로지점, 이렇게 물리적으로 떨어진 3개 사무실이라고 생각하면 쉽다. 각 지점은 자기 사무실 화이트보드(인메모리 RouteRuleSet)에 분배 규칙을 적어두고, 주문이 오면 화이트보드만 보고 즉시 판단한다.

- **일반 스프링 `ApplicationEvent`**: 같은 사무실 안에서 직원 A가 직원 B한테 소리쳐 알리는 것. 같은 프로세스(JVM) 안에서만 들린다 — 송파·종로 지점은 전혀 못 듣는다.
- **`RemoteApplicationEvent`**: 본사가 무전기(카프카)로 3개 지점 전체에 동시에 방송하는 것. 강남지점이 무전기에 대고 말하면 송파·종로 지점 스피커에서도 똑같이 들린다. 물리적으로 떨어진 사무실끼리 소통하려면 이 무전기가 필요하다.

`destination`은 무전기의 **채널**이다. 무전기에는 "배달팀 채널", "회계팀 채널"처럼 여러 채널이 있을 수 있는데, `destination = "delivery"`는 "이 방송은 배달팀 채널로 보낸다"는 뜻이다. 배달팀 채널을 맞춰놓은 사무실(강남/송파/종로)만 듣고 반응하고, 다른 채널을 듣는 부서는 이 방송이 지나가도 무시한다.

```java
public abstract class DeliveryServiceRemoteApplicationEvent extends RemoteApplicationEvent {
    protected DeliveryServiceRemoteApplicationEvent(String destination) {
        super(SOURCE, ORIGIN, DESTINATION_FACTORY.getDestination(destination));
    }
}

public class RouteRuleRemoteEvent extends DeliveryServiceRemoteApplicationEvent {
    public RouteRuleRemoteEvent() {
        super("delivery"); // destination: 배달서버군
    }
}
```

- `DeliveryServiceRemoteApplicationEvent`(추상클래스): 팀에서 만드는 모든 리모트 이벤트가 공통으로 상속받는 베이스. `RemoteApplicationEvent`가 요구하는 `(source, origin, destination)` 세 값을 팀 공통으로 채워준다. `DESTINATION_FACTORY.getDestination("delivery")`가 문자열 "delivery"를 스프링 클라우드 버스가 이해하는 `Destination` 객체로 바꿔준다.
- `RouteRuleRemoteEvent`(구현체): "분배 규칙이 바뀌었다"는 구체적인 이벤트 타입. `super("delivery")`로 "이 이벤트는 delivery 채널로 보낸다"고 못박는다.

이 코드 자체는 아직 방송을 트는 게 아니라, **"규칙변경 방송문" 양식을 만들고 그 위에 "수신처: 배달팀 채널"이라고 도장을 찍어둔 것**뿐이다.

### 발행/구독 코드 — 실제 방송이 오가는 장면

```java
public void load() {
    routeRuleSetStore.load();                                          // ① 내 화이트보드부터 먼저 고침
    remoteApplicationEventPublisher.publishEvent(new RouteRuleRemoteEvent());  // ② 무전기로 방송 시작
}

@EventListener
public void handle(RouteRuleRemoteEvent event) {
    routeRuleSetStore.load();   // 방송을 들은 즉시 내 화이트보드도 고침
}
```

강남지점에서 운영자가 규칙을 바꿨다고 하자.

- ① `routeRuleSetStore.load()` — 강남지점 직원이 **자기 사무실 화이트보드**부터 먼저 지우고 새로 쓴다.
- ② `publishEvent(...)` — 무전기 버튼을 눌러 "배달팀 채널, 규칙 바뀌었으니 다들 화이트보드 다시 확인해!"라고 방송한다.
- `handle()`은 **강남/송파/종로 사무실 벽에 걸린 스피커**다. 배달팀 채널로 방송이 들어오면 자동으로 반응해서 자기 화이트보드를 갱신한다.

```
운영자가 강남 규칙 변경 지시
        ↓
강남지점: ① 자기 화이트보드 먼저 고침
        ↓
강남지점: ② 무전기 방송 "배달팀 채널! 규칙 바뀜!"
        ↓
   ┌────┴────┬────────┐
   ↓         ↓         ↓
강남지점    송파지점    종로지점
(스피커로   (스피커로   (스피커로
 방송 들음)  방송 들음)  방송 들음)
   ↓         ↓         ↓
화이트보드   화이트보드   화이트보드
다시 씀      다시 씀      다시 씀
(중복이지만  (진짜 필요한  (진짜 필요한
 상관없음)    갱신)        갱신)
```

강남지점은 ①에서 이미 화이트보드를 고쳤는데 방송도 듣고 한 번 더 고친다(중복). 이게 문제가 안 되는 이유는 "화이트보드를 그냥 새 값으로 다시 쓰는 것"이라 몇 번을 다시 써도 결과가 같기 때문이다. 그래서 "누가 방송을 시작했는지 구분해서 걔만 빼고 처리"하는 예외 처리 없이, **"방송을 들으면 무조건 다시 쓴다"**는 규칙 하나로 코드가 단순하게 유지된다.

## Spring Cloud Bus의 용도

`RemoteApplicationEvent`는 단독으로 존재하는 게 아니라 **Spring Cloud Bus**라는 스프링 표준 인프라의 일부다. Spring Cloud Bus는 "분산된 여러 인스턴스에 관리용 신호를 브로커(카프카/RabbitMQ)를 통해 방송한다"는 목적으로 만들어졌다.

**대표 사용 예시 — 설정 변경 전파(Config Server 조합)**

- 설정을 Git 등에 두고 Config Server가 서빙하는 구조에서, 설정이 바뀌면 원래는 인스턴스마다 `/actuator/refresh`를 일일이 호출해서 `@RefreshScope` 빈을 갱신시켜야 한다. 인스턴스가 30대면 30번 호출해야 한다.
- Spring Cloud Bus를 연결해두면 아무 인스턴스에나 `/actuator/busrefresh`를 딱 한 번만 호출하면 된다. 이게 `RefreshRemoteApplicationEvent`를 버스 토픽에 발행하고, 구독 중인 **모든 인스턴스**가 받아서 각자 알아서 `@RefreshScope` 빈을 갱신한다.

우아한형제들 사례(`RouteRuleRemoteEvent`)는 이 프레임워크를 "설정 변경"이 아니라 팀의 커스텀 도메인 이벤트(분배 규칙 변경)를 방송하는 용도로 재활용한 것이다.

## `@KafkaListener`로 직접 하면 안 되나 — Bus가 대신 해주는 4가지

기술적으로는 `@KafkaListener`만으로도 완전히 동일한 브로드캐스트를 만들 수 있다. `RemoteApplicationEvent`가 카프카로는 불가능한 걸 가능하게 하는 게 아니라, **이미 자주 필요한 패턴을 스프링이 미리 조립해서 부품으로 만들어준 것**에 가깝다.

**직접 `@KafkaListener`로 짠다면:**

```java
@Component
public class RouteRuleKafkaListener {

    @KafkaListener(
        topics = "event-bus",
        groupId = "delivery:#{@instanceId}"   // 서버마다 달라야 함을 "개발자가" 직접 챙겨야 함
    )
    public void onMessage(String rawPayload) {
        EventEnvelope envelope = objectMapper.readValue(rawPayload, EventEnvelope.class);

        if (!"delivery".equals(envelope.getDestination())) {   // 필터링도 직접 구현
            return;
        }
        if ("ROUTE_RULE_CHANGED".equals(envelope.getEventType())) {  // 타입 분기도 직접 처리
            routeRuleSetStore.load();
        }
    }
}
```

**Spring Cloud Bus + `RemoteApplicationEvent`로 짜면:**

```java
@EventListener
public void handle(RouteRuleRemoteEvent event) {
    routeRuleSetStore.load();
}
```

| 직접 KafkaListener로 하면 챙겨야 할 것 | Spring Cloud Bus가 미리 해결해둔 것 |
|---|---|
| 서버마다 groupId를 다르게 만드는 로직을 직접 구현 | 인스턴스마다 고유한 groupId를 프레임워크가 자동 생성 |
| "이 메시지가 나를 위한 게 맞나" destination 필터링을 직접 구현 | destination 매칭 로직이 이미 내장됨 |
| 이벤트 타입이 여러 개면 `if/else`나 타입 필드로 직접 분기 | `RouteRuleRemoteEvent` 등 **타입 그대로** 다형성 디시리얼라이즈 지원 → `@EventListener`에 스프링 표준 이벤트 리스너 문법 그대로 사용 가능 |
| "설정 갱신", "셧다운 신호" 같은 흔한 관리용 이벤트를 매번 새로 설계 | `RefreshRemoteApplicationEvent`, `EnvironmentChangeRemoteApplicationEvent`, `ShutdownRemoteApplicationEvent` 등 자주 쓰는 것들이 이미 만들어져 있음 |

**본질**: `@KafkaListener`는 "카프카에서 메시지를 받아오는 것"까지만 해준다. 그 이후 — 서버마다 독립적으로 전체를 받게 만들기, 특정 서버군만 골라 반응하게 만들기, 받은 메시지를 원래 이벤트 타입 그대로 스프링 이벤트 시스템에 태우기 — 는 전부 개발자 몫으로 남는다. `RemoteApplicationEvent`(+ Spring Cloud Bus)는 이 남는 몫을 미리 구현해서 라이브러리로 포장해둔 것뿐이다. 브로드캐스트의 밑바닥 원리(서버마다 다른 컨슈머 그룹)는 완전히 동일하고, 차이는 그 반복 작업을 직접 짤 것이냐 스프링이 만들어둔 부품을 가져다 쓸 것이냐다.

## anonymous 컨슈머 그룹

컨슈머 이름을 따로 지정하지 않으면 스프링 클라우드가 `anonymous.{식별자}` 형식으로 랜덤 그룹 ID를 자동 부여한다. 연결된 서버 수만큼 `anonymous.*` 그룹이 계속 생기므로, 모니터링 시에는 이 anonymous 그룹들을 필터링해서 노이즈를 줄인다.

## 한 줄 정리
> 평소 컨슈머 그룹은 메시지를 그룹 내에서 나눠 갖는 용도지만, 서버군 전체가 같은 인메모리 값을 동시에 갱신해야 하는 상황에서는 반대로 "모두가 받아야" 한다. 이를 위해 서버마다 컨슈머 그룹 ID를 다르게 줘서(그룹 자체를 서버 수만큼 쪼개서) 한 번의 발행이 모든 서버에 독립적으로 전달되게 하는 것이 카프카를 이벤트 버스로 쓰는 방식이고, `RemoteApplicationEvent`는 그 위에 "어떤 서버군을 향한 이벤트인지" 목적지를 얹어주는 스프링 클라우드의 추상화다.
