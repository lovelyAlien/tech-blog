# 인프라 장애 시나리오 — 모범 답안 (템플릿)

> 개인 면접 준비용 답안. Quartz 퍼블리시 대상에서 제외(`draft: true`)했지만, 저장소 자체는 공개 GitHub 저장소라 완전한 비공개는 아니다. 동일 내용은 비공개 저장소인 `interview_study/subjects/kafka/`에도 정식으로 보관 중.

> ⚠️ 아래는 이력서에 명시되지 않은 부분이라, 이력서의 인프라 스택(Kubernetes, GitOps, Prometheus/Grafana/AlertManager)과 자연스럽게 맞물릴 수 있도록 만든 **가상 시나리오 템플릿**이다. 실제 경험한 적 없다면 면접에서 그대로 쓰지 말고, 실제 겪은 다른 장애로 대체할 것.

## 시나리오 1: 랙 모니터링 도구 — Kafka Exporter + Prometheus

컨슈머 랙은 `kafka-exporter`(danielqsj/kafka_exporter 또는 Kafka Lag Exporter)를 Kubernetes에 파드로 배포해서 Prometheus가 스크래핑하도록 구성했다. `kafka_consumergroup_lag` 메트릭 기준으로 Grafana에 컨슈머 그룹별·토픽별 랙 추이를 대시보드로 만들고, 랙이 일정 임계치(예: 5분 이상 지속 증가)를 넘으면 AlertManager가 Slack으로 알림을 보내도록 설정했다.

## 시나리오 2: 브로커 디스크 풀(Disk Full)

브로커 로그 디렉토리 PVC 용량이 예상보다 빠르게 찬 상황을 겪었다. 원인은 특정 토픽의 `retention.ms`가 너무 길게 잡혀 있어 트래픽 증가만큼 디스크 사용량도 빠르게 늘어난 것이었다. Grafana에서 디스크 사용률이 90%를 넘는 시점에 알림을 받아 오래된 세그먼트를 정리하고, 보존 기간을 실제 필요 수준으로 줄이고 알림 임계치를 낮춰 조기 경보가 오도록 개선했다.

## 시나리오 3: 브로커 다운 (OOMKilled 반복 재시작)

브로커 파드가 OOMKilled로 재시작을 반복한 적이 있다. 원인은 힙 메모리 설정이 트래픽 대비 타이트해서 GC 압박이 심해지다 메모리 초과로 죽는 것이었다. 해당 파티션 리더가 다른 브로커로 넘어가며 잠깐 리밸런싱이 발생했고, 컨슈머 랙이 순간적으로 튀는 걸 확인했다. 힙 메모리 limit을 상향하고, 브로커별 메모리 사용률·재시작 횟수를 대시보드에 추가해 재발을 조기 감지하도록 했다.

## 시나리오 4: SSL 핸드셰이크 실패 (인증서 만료)

브로커-클라이언트 간 TLS 인증서가 만료되며 배포 직후 컨슈머 연결이 끊긴 장애를 겪었다. 로그에서 `SSLHandshakeException`을 확인해 원인을 특정하고 인증서를 갱신해 복구했다. 이후 인증서 만료 30일 전 알림을 추가해 재발을 방지했다.
