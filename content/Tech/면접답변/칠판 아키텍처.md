# 칠판에 그릴 프로젝트 아키텍처

자기소개 뒤에 "프로젝트 구조를 그려서 설명해 주세요"가 나오면 바로 그릴 수 있게 정리한 판이다. 데이터스트림즈 면접 준비용이라 제출한 노션 이력서(개선 전)의 불릿 번호를 빨간 배지로 붙였다. 칠판에는 박스 이름과 화살표만 쓰고, 배지는 말하면서 손으로 짚는다.

## 시간별로 무엇을 그릴까

| 시간 | 그릴 범위 |
|---|---|
| 1분 30초 | 판 ①의 윗줄만. Client → Talk 서버 → Kafka → CMS → WS 서버, 아래에 DB와 Redis. S1·S2를 짚고 끝낸다 |
| 3분 | 판 ① 전부. 아웃박스(W3 정정 멘트 포함), K Talk 재연결, 운영 띠까지 |
| 질문이 오면 | 판 ②(삼성 웨비나)를 옆에 그리고 "SenCloud와 반대로, 모든 서버로 보냅니다"로 시작 |

## 판 ① SenCloud · K Talk 메시지 전송

두 프로젝트의 전송 흐름은 같다. 이 판이 메인이다. 파란 실선은 메시지가 가는 길, 점선은 예외·보정 경로, 초록은 캐시 무효화와 재연결이다.

![[칠판 아키텍처-20261019-131200.png]]

### 그리는 순서와 말하기 대본

1. **Client A → Talk 서버, 아래에 DB**
   > SenCloud는 서울시교육청 업무 메신저이고, 총 사용자 10만 명, 동시 접속은 1.2만 명 규모입니다. 사용자가 메시지를 보내면 Talk 서버가 채널별 순번을 붙여 DB에 저장합니다.
2. **Talk 서버의 S1 짚기**
   > 저장한 뒤에는 누구에게 보낼지 알아야 해서 채널 참여자 목록을 조회합니다. 처음에는 메시지마다 DB에서 읽었고, 출근 시간처럼 몰릴 때 최대 1200ms까지 늦어졌습니다. 참여자는 입장·퇴장 때만 바뀌기 때문에 서버 메모리에 두고, 멤버가 바뀔 때만 Redis로 "지워라" 신호를 보냈습니다. 최대 지연이 50ms로 줄었습니다.
3. **Kafka → CMS**
   > Talk 서버는 메시지와 받을 사람 목록을 Kafka에 넣고 바로 응답합니다. 키를 채널 ID로 둬서 같은 채널의 메시지는 순서대로 처리됩니다. 실제 전달은 CMS가 Kafka에서 꺼내서 맡습니다.
4. **Redis Cluster, S2 짚기**
   > CMS는 받는 사람이 어느 WebSocket 서버에 붙어 있는지 Redis에서 찾습니다. 몰리는 시간에는 이 조회가 Redis 한 대에 집중됐습니다. 그래서 Redis Cluster를 직접 구축해 접속 위치를 여러 노드에 나눠 담았습니다.
5. **WS 서버 → Client B, 점선으로 푸시 서버**
   > CMS는 받는 사람을 서버별로 묶어 서버당 한 번씩 보내고, WS 서버가 자기에게 연결된 세션으로 내려 줍니다. 접속해 있지 않은 사람에게는 모바일 푸시로 보냅니다.
6. **DB 옆 아웃박스 점선, W3\* 짚기**
   > 이력서에는 삼성 웨비나 항목에 적었는데, 실제로 적용한 곳은 SenCloud라서 여기서 설명드리겠습니다. 저장은 됐는데 Kafka에 넣기 전에 서버가 죽으면 메시지가 전달되지 않습니다. 그래서 같은 트랜잭션에 아웃박스 기록을 남기고, 평소에는 바로 발행하다가 실패한 것만 스케줄러가 다시 발행하게 했습니다.
7. **초록 재연결 선, 아래 운영 띠 (K3 · K1 · K2)**
   > 농어촌공사 K Talk도 같은 구조 위에서 만들었습니다. 네트워크가 끊겼다 붙으면 마지막으로 받은 순번 이후를 다시 받아 오게 했습니다. 배포는 GitLab CI, Harbor, ArgoCD로 Git에 올린 대로 반영되게 했고, Prometheus와 Grafana, AlertManager로 장애 알림을 직접 구성했습니다.

캐시 지우기 신호를 왜 Kafka가 아니라 Pub/Sub으로 보냈냐는 꼬리 질문은 [[캐시 무효화 신호를 Kafka가 아니라 Redis Pub-Sub으로 보내는 이유]]에 정리했다.

## 판 ② 삼성전자 웨비나

동시 접속 1.5만 명. 큰 방 몇 개에 사람이 몰리는 트래픽이라, SenCloud와 반대로 모든 실시간 서버에 보내는 구조를 처음부터 직접 설계했다.

![[칠판 아키텍처-20261019-131201.png]]

### 그리는 순서와 말하기 대본

1. **Client → Chatting Server → Kafka (토픽 두 칸)**
   > 웨비나는 보내기는 REST로, 받기는 WebSocket으로 나눴습니다. Chatting Server는 메시지를 DB에 저장하지 않고 Kafka에 바로 넣습니다.
2. **WS Server 1…N, 위로 돌아가는 초록 선**
   > 실시간 서버마다 컨슈머 그룹을 다르게 둬서 모든 서버가 같은 메시지를 받습니다. 각 서버는 자기에게 붙은 세션 중 그 방 참여자에게만 보냅니다. 행사 하나에 수천 명이 몰리면 거의 모든 서버에 그 방 참여자가 있어서, 위치를 추적하는 것보다 이 방식이 단순했습니다.
3. **W1 짚기 (session-event 칸과 WS 서버)**
   > 행사 시작 직전에 입장이 몰리면 입퇴장 이벤트가 모든 서버에 그대로 퍼집니다. 채팅과 입퇴장 토픽을 나누고, 입퇴장은 한 건씩이 아니라 모아서 처리하게 바꿔 컨슈머 부하를 약 30% 줄였습니다.
4. **Backup Server → Backup DB, 옆에 DLQ (W4)**
   > 저장은 Backup Server가 따로 꺼내서 합니다. 그래서 DB가 느려져도 실시간 전달은 계속됩니다. 계속 실패하는 메시지는 몇 번만 재시도하고 DLQ로 빼서 뒤 메시지가 막히지 않게 했고, 같은 메시지를 다시 받아도 메시지 ID로 한 번만 저장되게 했습니다.
5. **Spring Batch → 대시보드, 왼쪽에 스케줄러 (W5 · W2)**
   > 행사 통계는 요청마다 집계하지 않고 Spring Batch로 미리 집계해 대시보드는 결과만 읽게 했습니다. "행사 시작 N분 전 알림" 같은 스케줄 작업은 Pod마다 돌아서 알림이 중복으로 나갔는데, Redisson 분산 락으로 한 대만 실행되게 막았습니다.

## 두 판의 차이 (비교 질문 대비)

| | SenCloud · K Talk | 삼성 웨비나 |
|---|---|---|
| 전달 | 받는 사람이 있는 서버에만 (Redis 위치 조회) | 모든 실시간 서버에 보내고 각 서버가 걸러냄 |
| 저장 순서 | DB 먼저 저장 → Kafka 발행 | Kafka 먼저 → Backup Server가 저장 |
| 유실 대비 | 아웃박스 재발행 | DLQ + 메시지 ID 멱등 저장 |
| 맞는 트래픽 | 작은 방이 아주 많음 (업무 채널) | 큰 방 몇 개에 사람이 몰림 (행사) |
| DB | Tibero | PostgreSQL |

## 배지별 불릿 위치

| 배지 | 이력서 불릿 (요지) | 그림 위치 | 상태 |
|---|---|---|---|
| S1 | In-memory 캐싱, 수신 대상 조회 1200ms → 50ms | Talk 서버 + 초록 무효화 선 | ⚠️ 측정 방법 재구성 |
| S2 | Redis Cluster 분산 캐시 구조 설계 | Redis Cluster | ⚠️ 노드 구성·수치 재구성 |
| S3 | 읽음 상태 버퍼 집계 → Bulk Upsert | DB | ⚠️ 설명 기준 미확정 |
| S4 | (channel_id, created_at) 복합 인덱스 | DB | ⚠️ Tibero인데 filesort 용어 |
| S5 | 공지 캐시 Stampede → Redisson 락 + Double-check | Redis Cluster | ⚠️ 현재 이력서에서 제거 |
| W3\* | 트랜잭션 아웃박스 (이력서는 삼성 소속) | 판 ① 아웃박스 | 실제 SenCloud, 먼저 정정 |
| K3 | 네트워크 단절 시 재전송·상태 동기화 | 초록 재연결 선 | ⚠️ 설명 기준 미확정 |
| K1 · K2 | GitOps 배포 / 모니터링·알림 | 운영 띠 | ✅ |
| K4 · K5 | 야간 만료 토큰 정리 / Spring Batch 이관 | 운영 띠 · 배치 | ✅ (주기는 "새벽 정기"까지만) |
| W1 | 토픽 분리 + 배치 소비, 부하 약 30% 절감 | 판 ② session-event · WS 서버 | ✅ (30% 지표는 재구성) |
| W2 | Redisson tryLock 스케줄 중복 실행 방지 | 판 ② 스케줄러 | ✅ |
| W4 | DLQ + 메시지 ID 멱등성 | 판 ② Backup Server · DLQ | ✅ |
| W5 | Spring Batch 후처리 집계 | 판 ② Spring Batch → 대시보드 | ✅ |

## 그리면서 조심할 것

- **S1 저장소**: Talk 서버 메모리(Caffeine 로컬 캐시)와 Redis Pub/Sub 무효화다. "Redis에 캐싱했다"고 말하지 않는다. 참여자 목록은 Redis에 두지 않았다.
- **W3 정정**: 아웃박스는 판 ①에 그리고, 그 자리에서 "실제 적용은 SenCloud"라고 먼저 말한다. 재발행 주기·기준값은 숫자를 말하지 않는다.
- **S3 · K3**: 제출 이력서 문장과 현재 아키텍처 문서(읽음 워터마크, 순번 기반 재동기화)의 설명이 다르다. 면접 전에 한 가지로 정해 두고, 칠판에서는 위치만 짚는다. 대본의 K3 문장은 순번 기반 재동기화 기준이다.
- **S4**: SenCloud DB는 Tibero다. filesort와 EXPLAIN은 MySQL 용어라 "어느 DB에서 본 실행 계획이냐"는 질문이 나올 수 있다.
- **W1 30%**: 어느 지표로 쟀는지는 확실하지 않다. "입장이 몰리는 구간의 컨슈머 처리 부하"까지만 말한다.
- **삼성 메시지 ID**: 어디서 만들었는지 기억이 불확실하다. 묻기 전에 "UUID로 만들었다"고 단정하지 않는다.

## 한 줄 정리
> SenCloud는 "받는 사람이 있는 서버에만, DB 먼저", 삼성 웨비나는 "모든 서버에, Kafka 먼저". 판 ①을 메인으로 그리고 배지로 불릿을 짚는다.
