## 비디오 업로드 절차

![[14장. 유튜브 설계-20260308-020828.png|511x633]]
원본 저장소:
원본 비디오 보관할 대형 이진 파일 저장소(BLOB) 시스템

트랜스코딩 서버:
- 원본 저장소의 비디오를 인코딩
- 단말이나 대역폭 요구사항에 맞는 최적 비디오 스트림 제공 목적 

트랜스코딩 비디오 저장소:
트랜스코딩이 완료된 비디오 저장하는 BLOB 저장소

CDN:
- 비디오 캐시하는 역할
- 사용자가 재생 버튼 누르면 CDN 통해 비디오 스트리밍

> BLOB으로 저장하는 이유는? 일반 파일 시스템은 안되나?

### 비디오 업로드, 비디오 메타데이터 갱신 병렬 처리
1. 비디오 업로드
	- 트랜스코딩 완료 이벤트를 트랜스코딩 완료 큐에 넣는다.
	- 트랜스코딩 완료 핸들러가 비디오 메타데이터 DB와 캐시 갱신
2. 비디오 메타데이터 갱신
	- 사용자가 메타데이터 파일 이름, 크기, 포맷 등 정보 갱신(DB, 캐시)

## 비디오 스트리밍

비디오 스트리밍:
장치가 원격지의 비디오로부터 지속적으로 비디오 스트림을 전송 받아 영상을 재생하는 것

### 스트리밍 프로토콜
- 비디오 스트리밍을 위해 데이터 전송할 때 쓰이는 표준 프로토콜
- 비디오는 CDN에서 바로 스트리밍 된다.

> 비디오 CDN에 캐싱할 때, 가장 가까운 CDN에 캐싱하는데, 어떻게 판단해서 가까운 CDN을 찾아가지?

비디오 업로드 절차
원본 비디오를 원본 저장소에 저장
트랜스코딩된 비디오를 CDN에 저장
저장을 원본 저장소에도 저장하고 트랜스코딩 비디오 저장소에도 저장하는 이유는?

원본 저장소가 필요한 이유
1. 재트랜스코딩 가능
2. 새로운 해상도 생성
3. 오류 복구

트랜스코딩 비디오 저장소 필요한 이유
사용자는 **원본 영상을 그대로 스트리밍하지 않습니다.**
왜냐하면 원본은 보통
```
용량 큼
비트레이트 높음
디바이스 호환성 낮음
```
그래서 **다양한 버전의 영상이 필요합니다.**
```
1080p
720p
480p
360p
240p
144p
```
또한 코덱도 다르게 생성합니다.
```
H264  
VP9
```

비디오 업로드와 메타데이터 갱신은 병렬로 진행되는 구조
- 업로드 시간을 줄이고 사용자 경험을 개선하기 위해서
```
클라이언트  
│  
├─① 비디오 파일 업로드  
│ ↓  
│ 원본 저장소 (Object Storage)  
│  
└─② 비디오 메타데이터 저장  
↓  
Metadata DB
```
참고로, 메타데이터 갱신에는 저장 or 업데이트 의미가 포함
영상 업로드 과정에서 메타데이터는 **한 번만 저장되는 것이 아니라 여러 번 갱신됩니다.**

| 단계          | 메타데이터 상태             |
| ----------- | -------------------- |
| 1. 업로드 시작   | 메타데이터 최초 생성 (CREATE) |
| 2. 업로드 진행   | 상태 업데이트 (UPLOADING)  |
| 3. 업로드 완료   | 상태 업데이트 (UPLOADED)   |
| 4. 트랜스코딩 시작 | 상태 업데이트 (PROCESSING) |
| 5. 트랜스코딩 완료 | 상태 업데이트 (READY)      |

왜 클라이언트가 API 서버가 아니라 Object Storage에 직접 업로드하도록 설계할까?
1. 영상 업로드는 **엄청난 트래픽**입니다.
	- Direct Upload 구조에서는 API 서버는 metadata 처리만 
	- 그래서 서버 부담이 **극적으로 감소**합니다.
2. 네트워크 병목 제거
	- 중계 방식 데이터 흐름은 `Client → API Server → Storage`
3. 서버 비용 절감

대규모 시스템(유튜브, Dropbox, Google Photos 등)에서 **클라이언트가 API 서버를 거치지 않고 Object Storage(S3 등)에 직접 업로드하도록 하는 이유**는 주로 **확장성, 비용, 성능** 때문입니다.
핵심 개념은 보통 **Presigned URL**입니다.

Object Storage 직접 업로드 (Direct Upload)
```
Client
   ↓
API Server (Presigned URL 발급)
   ↓
Client
   ↓
Object Storage
```
1️⃣ 클라이언트가 API 서버에게 **업로드 URL 요청**  
2️⃣ 서버가 **Presigned URL 발급**  
3️⃣ 클라이언트가 **Object Storage에 직접 업로드**

유튜브 비디오 처리 파이프라인에서 DAG(유향 비순환 그래프) 모델을 사용하는데 그 이유가 순환을 막기 위해 DAG를 쓰는건가?
결론부터 말하면 **“순환을 막기 위해 DAG를 쓴다”가 핵심 목적은 아닙니다.**  
**주된 목적은 작업 의존성을 명확히 표현하고, 병렬 실행을 가능하게 하기 위해서**입니다.  
**순환이 없다는 성질은 그 결과로 자연스럽게 따라오는 제약**에 가깝습니다.
```
Upload
  ↓
Transcoding
  ↓
Segment 생성
  ↓
Thumbnail 생성
  ↓
CDN 배포
```
이 흐름에서
- **이전 단계 결과가 다음 단계 입력**
- 데이터가 **뒤로 되돌아갈 이유가 없음**
그래서 자연스럽게 **cycle이 없는 구조**가 됩니다.

DAG를 사용하는 진짜 이유
```
          Transcoding
         /    |    \
      240p  480p  720p
         \    |    /
          Segment 생성
               ↓
            CDN 업로드
```
예를 들어 트랜스코딩 이후 여러 작업이 필요합니다.
여기서 중요한 것은
- **어떤 작업이 먼저 끝나야 하는지**
- **어떤 작업은 병렬로 실행 가능한지**
DAG는 이 **dependency 관계를 정확하게 표현**합니다.

② 병렬 실행 가능
DAG 구조에서는 **독립 노드가 동시에 실행**될 수 있습니다.
```
Transcoding  
   ↓  
240p   480p   720p
```
이 세 작업은 **동시에 실행 가능**합니다.
그래서
- 처리 속도 향상
- worker 확장 가능
- 대규모 처리 가능

③ 실패 복구
DAG는 실패 복구에도 유리합니다.
예를 들어 `720p transcoding 실패` 이 경우`720p 노드만 재실행`하면 됩니다.
전체 파이프라인을 다시 실행할 필요가 없습니다.

| 질문                      | 답          |
| ----------------------- | ---------- |
| 순환을 막기 위해 DAG인가?        | ❌ 핵심 이유 아님 |
| 작업 의존성을 표현하기 위해 DAG인가?  | ✅ 맞음       |
| 병렬 처리 가능하게 하기 위해 DAG인가? | ✅ 맞음       |
실제 대규모 시스템에서 DAG를 쓰는 이유

| 시스템                 | DAG 이유        |
| ------------------- | ------------- |
| YouTube transcoding | 작업 dependency |
| Airflow pipeline    | 데이터 처리 단계     |
| Spark job           | 연산 DAG        |
| CI/CD pipeline      | 빌드 단계         |
| TensorFlow graph    | 연산 그래프        |
유튜브 비디오 파이프라인에서 DAG를 사용하는 이유는 **작업 의존성을 표현하고 병렬 처리를 가능하게 하기 위해서이며, 순환이 없다는 것은 그 구조의 자연스러운 특성이다.**

라이브 스트리밍은 왜 병렬화 필요성이 떨어지지? 작은 단위 데이터를 실시간 빨리 처리하기 위함?

VOD(일반 업로드 영상)의 처리 방식 vs 라이브 스트리밍 처리 방식
라이브 스트리밍은 “빠른 지연(latency)”이 중요하기 때문에 깊은 병렬 파이프라인을 만들기 어렵고, 대신 “짧은 단계의 빠른 처리”가 필요합니다.
즉 **병렬성이 덜 필요하다기보다, 병렬화 방식이 VOD와 다릅니다.**

유튜브 업로드 영상(VOD(일반 업로드 영상)은 **실시간 제약이 없습니다.**
예:
- 사용자가 4GB 영상 업로드
- 처리에 몇 분 걸려도 괜찮음
그래서 **많은 작업을 병렬로 수행합니다.**
```
원본 업로드
   ↓
Transcoding
 ↙   ↓   ↘
240p 480p 720p 1080p
   ↓   ↓   ↓
Segment 생성
   ↓
Thumbnail 생성
   ↓
CDN 업로드
```
여기서 병렬화 가능한 부분:
- 여러 해상도 동시 트랜스코딩
- 여러 segment 동시 생성
- 썸네일 생성
즉 **대규모 DAG 기반 병렬 처리**가 가능합니다.

라이브 스트리밍은 **실시간으로 데이터가 계속 들어옵니다.**
```
카메라 → 인코더 → 스트리밍 서버 → CDN → 사용자
```
데이터가 계속 생성됨
그래서 아래와 같은 구조
```
Live Stream Input
      ↓
Real-time Transcoding
      ↓
Segment 생성
      ↓
CDN
      ↓
Viewer
```
- 데이터가 아직 존재하지 않음
	- 영상이 아직 만들어지고 있음
- 라이브는 **batch processing이 아니라 stream processing**입니다.
VOD
```
파일 기반  
batch 처리
```
라이브 스트리밍
```
stream 기반
```
예
```
1초 영상 → 처리 → 전송  
1초 영상 → 처리 → 전송
```

VOD는 전체 데이터가 이미 존재하기 때문에 대규모 병렬 처리(DAG)가 가능하지만, 라이브 스트리밍은 데이터가 실시간으로 생성되므로 빠른 지연을 위해 짧은 파이프라인으로 처리한다.
