- 로컬 버전 사용
- 서버 버전 사용

Google Docs에서 동기화 충돌이 거의 발생하지 않는 이유는 “파일 단위 동기화”가 아니라 “편집 연산(operation) 단위 동기화”를 사용하기 때문
Google Docs는 파일을 통째로 업로드하는 방식이 아니라 **사용자의 편집 행동을 실시간으로 서버에 전송**
# 3️⃣ 두 사용자가 동시에 편집

예를 들어

초기 문서

```
Hello world
```

User1

```
Hello amazing world
```

User2

```
Hello world!!!
```

Google Docs에서는 이렇게 전송됩니다.

```
User1:
insert("amazing ", position=6)

User2:
insert("!!!", position=11)
```

서버는 두 operation을 **순서대로 적용**합니다.

결과

```
Hello amazing world!!!
```

충돌 없이 **둘 다 반영됩니다.**

---

# 4️⃣ 이걸 가능하게 하는 기술

Google Docs는 보통 다음 기술을 사용합니다.

## OT (Operational Transform)

또는

## CRDT

이 기술은 **동시에 발생한 편집을 자동으로 조정**합니다.

예

```
User1: insert at position 5
User2: insert at position 5
```

이 경우 서버는

```
User2 position → 6으로 이동
```

같이 위치를 자동으로 조정합니다.

```
압축률 낮음

```

파일 유형마다 데이터 구조와 반복 패턴이 다르기 때문에 최적의 압축 알고리즘도 서로 다르다.

사용자가 접속 중이 아닐 때 오프라인 사용자 백업 큐에 넣고, 접속하면 동기화한다는 것은 무슨 의미인가?
사용자가 오프라인 상태일 때 발생한 파일 변경 이벤트를 서버가 **큐(queue)에 저장해 두었다가**, 사용자가 다시 접속하면 **그 변경 사항을 순서대로 전달하여 로컬 파일을 최신 상태로 맞추는 것**입니다.

사용자 B가 접속하면 클라이언트는 서버에게 동기화를 요청합니다.
```
Client → Server  
sync request
```
서버는 오프라인 큐에 있는 이벤트를 전달합니다.
```
Server → Client

1. report.doc updated
2. presentation.ppt added
3. image.png deleted
```

**델타 싱크에서 수정된 block은 기존 block을 대체하는 것인가, 아니면 새로 추가되는 것인가?**
대부분의 시스템에서는 **수정된 block을 새로 업로드하고, 파일 메타데이터가 새로운 block을 가리키도록 변경**합니다.  
즉 **물리적으로는 추가되고, 논리적으로는 대체됩니다.**

대부분의 클라우드 저장소는 **immutable block 방식**을 사용합니다.
