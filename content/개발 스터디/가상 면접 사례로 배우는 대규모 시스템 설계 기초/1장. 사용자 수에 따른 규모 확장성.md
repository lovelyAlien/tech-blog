## 어떤 데이터베이스를 사용할 것인가?
### 비 관계형 DB 선택은 언제하는가?
#### 1. 아주 낮은 응답 지연 시간
- ex. 채팅 메시지 조회, 타임라인 피드, 세션 조회
- RDB는 JOIN, 인덱스 탐색, 트랜잭션 비용
- NoSQL은 Key -> Value 조회, 디스크 I/O 최소화, 메모리 기반
#### 2. 직렬화된 데이터만 저장
- 객체 -> JSON -> 그대로 저장
- ex. JSON, YAML, XML 등(관계 해석 불필요)
#### 3. 아주 많은 데이터를 저장
- RDB는 수직 확장 한계
- NoSQL은 수평 확장(샤딩)을 전제로 설계
## 수직적 규모 확장 vs 수평적 규모 확장

수직 규모 확장에는 한계가 있다. 자동복구(failover) 방안이나 다중화(re-dundancy) 방안이 없다.
### 1. 웹 계층
로드밸런서
- 부하 분산 집합에 속한 웹서버들에게 트래픽 부하 분산 역할
- 로드밸런서가 웹 서버 대신 클라이언트 접속을 처리
	- 클라이언트 -> 로드밸런서 -> 웹 서버

### 2. 데이터 계층
보통은 주(master)-부(slave) 관계를 설정한다.
원본은 master 서버에, 사본은 slave 서버에 저장하는 방식이다.

### 2.1 장점
- **병렬**로 처리될 수 있는 질의(query) 수가 많아진다.
	- 쓰기 연산은 master 서버 + 읽기 연산은 slave 서버
- **안정성**(reliability)
	- master 다운돼도 slave에 사본이 있어서 데이터 보존
- **가용성**(availability)
	- 여러 서버에 데이터 복제해 둠으로써, 한 DB 서버 다운돼도 다른 DB 서버에서 서비스 가능

하지만 프로덕션 환경에서 벌어지는 일은 단순하지 않다. 부 서버에 보관된 데이터가 최신 상태가 아닐 수 있다. 없는 데이터는 복구 스크립트 돌려서 추가해야 한다. 
이러한 문제를 완화하기 위한 시도로, 쓰기 작업을 단일 서버에 의존하지 않는 구조가 도입되었다.
> 어차피 Replica가 최신이 아닐 수 있다면,  아예 모든 노드를 쓰기 가능하게 만들자
- 다중 마스터(multi-masters)
- 원형 다중화(circular replication)

> 다중 마스터, 원형 다중화?
#### 다중 마스터
모든 노드에서 읽기 쓰기 가능하다. 

왜 다중 마스터 쓸까?
1. 고가용성: 한 노드에 쓰기 의존하지 않는다 == Failover
2. 지리적 분산: 한국/미국/유럽 가까운 DB에 쓰기
3. 쓰기 부하 분산: 단일 Master 병목 제거

다중 마스터에서 발생하는 문제는?
- 쓰기 충돌 -> 자동으로 해결하기 어렵다.

충돌 해결 방식은?
- Last Write Wins: 타임스탬프 최신 값 승리
- 노드 우선 순위: A > B > C

```css 
Client → Master A (write)
Client → Master B (write)
Master A ↔ Master B (서로 복제)
```
#### 원형 다중화
- DB들이 원형 구조로 서로를 복제하는 다중 마스터 형태
- 결구 모두 마스터 형태
```css
Master A → B → C → A
```

왜 원형일까?
- 중앙 Master 없이 대칭 구조
- 노드 추가 단순
- 특정 DB 의존 X

원형 다중화 발생하는 문제는?
- 무한 복제 루프 위험
- 운영 난이도 높다
	- 장애 원인 추적이 어려움
	- 어디가 최신인지 파악 어려움
## 캐시

어플리케이션 성능은 DB를 얼마나 자주 호출하느냐에 좌우
### 캐시 계층
대표적인 캐시 전략 `읽기 주도형 캐시 전략(read-through caching strategy)`

> 다른 캐시 전략은 무엇이 있을까?

- Write Through
	- 쓰기 시 캐시와 DB 동시에 반영
- Write Behind
	- 쓰기 시 캐시 먼저 저장
	- DB 반영은 비동기

읽기 주도형 캐시 전략
- 캐시에 응답이 저장되어 있으면 해당 응답 반환
- 캐시에 없으면 DB에 데이터 찾아 캐시에 저장한 뒤 응답 반환

캐시 서버 이용 방법은?
- 대부분 프로그래밍 언어로 API 제공
- 대표적으로 memcached API

> memcached?

Memcached: 인메모리(Key-Value) 캐시 서버


### 캐시 사용 유의사항
- 언제 캐시 사용이 좋은가?
	- 갱신은 자주 일어나지 않지만 참조는 빈번한 상황
- 캐시는 어떻게 만료되는가?
	- 만료 기한이 너무 길면 원본과 캐시의 차이 발생
- 일관성은 어떻게 유지되는가?
	- 원본 갱신 연산과 캐시 갱신 연산이 단일 트랜잭션으로 처리되지 않는 경우 일관성이 깨질 수 있다.
- 장애는 어떻게 대처할 것인가?
	- 단일 장애 지점(SPOF) 가능성 유의
	- SPOF를 피하려면 캐시 서버 분산 필요
- 데이터 방출 정책은 무엇인가?
	- 캐시 꽉 차면 기존 데이터를 내보내야 한다.
	- ex. LRU(Least Recently Used, 최근 사용빈도 가장 낮은 것), FIFO(First in First Out)

> 실무에서 많이 사용되는 캐시 일관성 정책은? 

 Cache Aside - TTL
 1. DB 업데이트
 2. Cache 삭제
 3. 다음 read에서 재적재

> 캐시 분산 정책 대표적인 예?

1. Client-side Hashing
- 클라이언트가 어느 캐시 서버로 갈지 직접 결정
- 클라이언트가 키 → 캐시 노드를 직접 계산해서 요청
- 단점:
	- 노드 하나만 늘려도 거의 모든 키 위치가 변경됨
```text
nodeIndex = hash(key) % N
```

2. Consistent Hashing
- 노드 추가/삭제 시 영향을 최소화하는 해싱 기법 -> 노드가 바뀌어도 **일부** 키만 이동하게 만들자
- 핵심 개념: 해시 링 -> 전체 키 중 1/N 정도만 이동

> LRU와 FIFO는 각각 어떤 상황에 적합한가?

LRU: 최근 접근 데이터 재사용 높은 경우
FIFO: 접근 패턴 예측 어려울 때 -> 캐시 정책을 단순하게 유지하기 위해, 접근 이력 자체가 고려가 안됨
LFU: 특정 키 재사용 빈번한 경우


## CDN(Content Delivery Network)
정적 컨텐츠 전송에 쓰이는 지리적으로 분산된 서버의 네트워크이다.
- 정적 컨텐츠 예시: 이미지, 비디오, CSS, JavaScript 파일 등 캐시
### CDN을 사용하여 정적 컨텐츠 캐싱하는 방법
CDN 서버가 정적 컨텐츠를 캐싱하고 있고, 클라이언트가 요청하면 CDN 서버가 데이터를 대신 반환

## 무상태(stateless) 웹 계층

웹 계층의 수평적 확장을 위해서는 상태 정보(ex. 사용자 세션 데이터)를 웹 계층에서 제거해야 한다. 바람직한 전략은 상태 정보를 DB에 보관하는 것이다.

## 데이터 센터
### 데이터 센터 난제
- 트래픽 우회
	- GeoDNS: 사용자에게서 가장 가까운 데이터센터로 트래픽을 보낼 수 있도록 해야한다.
- 데이터 동기화
	- 데이터 센터마다 별도 DB를 사용하고 있다면, 자동 복구(failover)로 트래픽이 다른 DB로 우회되도, 해당 DB에 찾느 데이터가 없을 수 있다.

## 메시지 큐
메시지큐는 아래 특성을 갖는 컴포넌트이다.
- 무손실
- 비동기 통신
메시지 큐는 버퍼 역할을 하며 비동기적으로 전송한다.

> 무손실: durability, 즉 메시지 큐에 일단 보관된 메시지는 소비자가 꺼낼 때까지 안전히 보관된다는 특성

### 장점
서비스 또는 서버 간 느슨한 결합
- 안정성
	- 생산자는 소비자 문제 생겨도 이벤트 발행만 하면 된다.
	- 소비자는 생산자 문제 생겨도 이벤트 소비만 하면 된다.
- 비동기 처리
	- ex. 이미지 크로핑처럼 시간이 오래걸리는 프로세스 작업

## DB 규모 확장
저장할 데이터가 많아지면 DB 부하도 증가한다. 이를 해결하기 위해 DB 증설해야 한다. 
- 수직 확장: 스케일 업(고성능 자원 증설)
- 수평 확장: 샤딩

### 샤딩
대규모 DB를 샤드(shard)라고 부르는 작은 단위로 분할하는 기술이다.
모든 샤드는 같은 스키마를 쓰지만 샤드에 보관된 데이터 사이에는 중복이 없다.

샤딩 키(파티션 키)
- 데이터를 논리적인 조각(파티션)으로 나누는 기준이 되는 컬럼(들)

> 샤딩에서 말하는 같은 스키마의 의미는?

모든 샤드가
- 동일한 테이블 구조
- 동일한 컬럼
- 동일한 인덱스

### 샤딩 주의사항
샤딩이 DB 규모 확장에 좋은 기술이지만, 쉽지 않다. 복잡해지고 풀어야할 새로운 문제도 생긴다.

1) 재 샤딩(resharding)
하나의 샤드에 데이터가 몰려서 데이터 분포 불균등 발생하여 하나의 샤드로 데이터 규모 감당할 수 없는 상황 발생할 수 있다. 이를 **샤드 소진**(shard exhaustion)이라고도 부르는데, 샤드 계산 함수 변경해서 데이터 재배치해야 한다. 안정 해시 기법(consistent hashing) 기법을 활용하면 해결 가능하다.

> 안전 해시 기법 동작 방식은? 
1. 해시 링 생성 (0~2³²)
2. 노드와 키를 같은 해시 공간에 배치
3. 시계 방향으로 가장 가까운 노드 선택
-> 노드 추가/삭제 시 이동 최소화(ex. Redis, Cassandra 핵심 개념)

4) 유명인사(celebrity) 문제
핫스팟 키 문제라고도 부르는데, 특정 샤드에 질의가 집중되어 서버 과부하되는 것을 말한다. 이 문제를 풀려면 유명인사 각각에 샤드 하나 씩 할당하거나 더 쪼개야할 수 있다.

> 유명인사 각각 샤드 할당하고 쪼개라는 말이  어떨 때를 말하는거지?

```css
샤드 키 = roomId % 16

roomId = 777 (연예인 채팅방)
→ 전체 메시지의 40%가 여기로 들어옴
→ shard-9 과부하
```
해결: 전용 샤드 할당
```css
if roomId in [777, 888, 999]:
    → celebrity_shard_1
else:
    → normal_shard (hash 기반)
```

5) 조인과 비정규화
하나의 DB를 여러 샤드 서버로 쪼개고 나면, 여러 샤드에 걸친 데이터를 조인하기 힘들어진다. 해결 방법 중 하나로 DB를 비정규화하여 하나의 테이블에서 질의가 수행하는 방법이 있다.
