# 문서 모델을 선호하는 이유와 관계형 모델의 강점

데이터 중심 애플리케이션 2장에서 문서 모델을 선호하는 이유와, 이에 맞서는 관계형 모델의 강점을 정리한다.

## 두 모델의 정의

- **관계형 모델:** 데이터를 **테이블(표)**로 쪼개 저장하고, ID로 연결한다.
- **문서 모델:** 관련 데이터를 **JSON 문서 하나**로 묶어 저장한다.

```
// 관계형: 테이블로 쪼개서 저장
posts:    | id=1 | title=추상화 |
comments: | id=1 | post_id=1 | text=좋아요 |
          | id=2 | post_id=1 | text=감사   |
```

```json
// 문서: 하나로 묶어서 저장
{
  "id": 1,
  "title": "추상화",
  "comments": [{"text": "좋아요"}, {"text": "감사"}]
}
```

## 문서 모델을 선호하는 이유

### 1. 스키마 유연성

구조를 미리 고정하지 않아 새 필드를 그냥 추가할 수 있다. 관계형은 `ALTER TABLE`이 필요하다.

- **예시:** 글에 `tags` 필드를 새로 넣고 싶다.
  - 문서: 새로 저장하는 문서에 `"tags": ["DB"]`를 넣으면 끝이다. 기존 문서는 그대로 둔다.
  - 관계형: `ALTER TABLE posts ADD COLUMN tags ...`로 테이블 구조를 바꿔야 한다.

### 2. 지역성에 의한 성능

관련 데이터가 한 문서에 붙어 있어 한 번 읽으면 다 나온다. 함께 읽는 경우에만 이득이다.

- **예시:** 글 상세 페이지에서 글과 댓글을 한 번에 보여준다.
  - 문서: 문서 1번 읽기로 글 + 댓글이 나온다.
  - 관계형: `posts`와 `comments`를 JOIN하거나 쿼리를 두 번 해야 한다.
- 반대로 댓글만 필요한 경우에도 문서 전체를 읽는 것은 단점이다.

### 3. 애플리케이션 데이터 구조와 가까움

코드의 객체가 JSON 문서와 거의 그대로 대응된다.

```java
class Post {
    String title;
    List<Comment> comments;   // JSON 문서의 comments 배열과 같은 모양
}
```

- **예시:** `Post` 객체를 저장한다.
  - 문서: 객체를 JSON으로 바꿔 그대로 저장하고, 읽으면 바로 객체로 복원된다.
  - 관계형: `posts` 행 1개와 `comments` 행 여러 개로 쪼개 저장하고, 읽을 때 다시 합쳐 객체로 만드는 변환(ORM 등)이 필요하다.
- 이 불일치를 **객체-관계 불일치(임피던스 불일치)**라고 한다.
- "일부 애플리케이션"이라고 한 이유는 데이터가 트리 구조 객체일 때만 이 장점이 있기 때문이다.

## 관계형 모델의 강점

- **JOIN과 다대일·다대다를 더 잘 지원한다.**
- 관계 표현은 둘 다 가능하지만(외래 키 / 문서 참조), 합쳐서 읽는 JOIN을 DB가 얼마나 잘 처리하느냐가 다르다.

```sql
SELECT u.name, c.name FROM users u JOIN companies c ON u.company_id = c.id;
```

- 문서 DB는 JOIN이 약하거나 없어서 참조된 문서를 애플리케이션이 따로 조회해 합쳐야 한다.

## 한 줄 정리

> 문서 모델은 묶어서 저장해 유연하고 빠르고 객체와 닮았으며, 관계형 모델은 쪼개서 저장하고 JOIN으로 다대일·다대다 관계를 잘 다룬다.
