# 다대다 관계에서 문서 모델의 매력이 떨어지는 이유

데이터 중심 애플리케이션 2장에서 다대다 관계가 많으면 문서 모델의 매력이 떨어진다고 한다. 문서 DB는 JOIN이 약하고, 비정규화로 JOIN을 줄여도 일관성 유지를 애플리케이션이 직접 해야 하기 때문이다.

## 1. 문서 DB는 왜 JOIN이 약한가

"JOIN이 없다"가 아니라 "관계형만큼 핵심 기능이 아니다"라는 뜻이다(MongoDB의 `$lookup` 같은 JOIN 유사 기능은 있다).

1. **설계 철학:** 관련 데이터를 한 문서에 묶어 저장해서 애초에 JOIN이 필요 없게 만드는 것이 목표다. 관계형은 쪼개 저장하고 JOIN으로 합친다.
2. **분산 환경의 비용:** 수평 확장(샤딩)을 지향하는데, 서로 다른 서버에 있는 문서를 JOIN하려면 네트워크로 데이터를 주고받아야 해서 비싸다.
3. **쿼리 엔진:** 관계형은 JOIN 순서·인덱스 최적화를 오래 발전시켰지만, 문서 DB는 단일 컬렉션 조회에 맞춰져 있었고 JOIN은 나중에 추가됐다.
4. **느슨한 참조 무결성:** 참조한 ID가 실제로 있는지를 DB가 보장하지 않는 경우가 많아, 참조를 따라가는 책임이 애플리케이션으로 넘어간다.

## 2. 비정규화로 JOIN을 줄이면 생기는 문제

다대다는 같은 데이터를 여러 곳이 공유한다(학생 ↔ 수업). JOIN이 약하니 공유 데이터를 각 문서에 **복사해 넣는 비정규화**로 JOIN을 피한다.

```json
// 철수
{"name": "철수", "courses": [{"title": "데이터베이스", "professor": "김교수"}]}

// 영희
{"name": "영희", "courses": [{"title": "데이터베이스", "professor": "김교수"}]}  // ← 복사본
```

"데이터베이스" 수업의 교수가 최교수로 바뀌면 이 수업을 듣는 모든 학생 문서를 찾아 고쳐야 한다. 빠뜨리면 문서마다 교수 이름이 달라지는 불일치가 생긴다.

| | 관계형(정규화) | 문서 DB(비정규화) |
|---|---|---|
| 교수 이름 저장 위치 | `courses` 테이블 1곳 | 학생 문서 여러 곳 |
| 교수가 바뀌면 | 1곳만 수정 | 복사본 전부 수정 |
| 일관성 보장 | DB | 애플리케이션 코드 |

## 한 줄 정리

> 문서 DB는 JOIN을 줄이려고 묶어서 저장하는 모델이라 JOIN이 약하고, 비정규화로 보완하면 복사본의 일관성 유지를 애플리케이션에 떠넘긴다.
