# SQL은 무엇을 추상화하는가

데이터 중심 애플리케이션 1장(단순성)에서 추상화의 예로 SQL이 나온다. SQL이 정확히 무엇을 숨겨주는지 예시로 정리해 둔다.

## 추상화란

복잡한 내부 구현을 숨기고, 쓰는 사람에게는 단순한 인터페이스만 보여주는 것이다. 복잡도를 한곳에 가둬서 시스템을 단순하게 만든다.

| 추상화 | 숨기는 것 | 사용자가 보는 것 |
|---|---|---|
| 고수준 프로그래밍 언어 | 기계어, CPU, 레지스터, 시스템 호출 | 변수, 함수, 조건문 |
| SQL | 디스크·메모리의 데이터 구조, 동시 요청, 고장 후 불일치 | `SELECT ... FROM ... WHERE ...` |

## 1. 데이터 구조

```sql
SELECT * FROM users WHERE email = 'a@b.com';
```

- 개발자는 "이메일이 일치하는 행을 찾는다"만 안다.
- 숨겨진 것: B-Tree 인덱스를 탈지 풀 스캔을 할지, 데이터가 디스크 페이지에 어떻게 놓여 있는지, 버퍼 풀에 캐시돼 있는지.
- 인덱스를 추가하거나 저장 방식이 바뀌어도 쿼리는 그대로다.

## 2. 동시성

두 사용자가 마지막 남은 재고 1개를 동시에 주문하는 상황이다.

```sql
BEGIN;
UPDATE stock SET qty = qty - 1 WHERE item_id = 10 AND qty > 0;
COMMIT;
```

- 개발자는 재고를 1 줄이는 쿼리만 썼다.
- 숨겨진 것: 같은 행을 동시에 건드릴 때 DB가 락이나 MVCC로 순서를 정리한다. 재고가 -1이 되는 일은 막힌다.
- 애플리케이션에서 `synchronized`나 분산 락을 직접 짜지 않아도 된다.
- 대기할지 실패할지는 격리 수준과 DB 구현에 따라 다르다.

## 3. 고장 후 불일치

계좌 이체 예시다.

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;  -- A 출금
UPDATE account SET balance = balance + 100 WHERE id = 2;  -- B 입금
COMMIT;
```

- 개발자는 두 UPDATE를 트랜잭션으로 묶었을 뿐이다.
- 숨겨진 것: 중간에 서버가 죽어도 DB가 재시작할 때 로그(WAL, redo/undo log)를 보고 복구한다.
- 원자성은 전부 반영되거나 전혀 반영되지 않는 것, 내구성은 커밋된 결과가 장애 후에도 남는 것이다.

### 보충: 두 번째 UPDATE에서 고장 나면?

첫 번째 UPDATE는 **실행은 됐지만 커밋은 안 된 상태**다. COMMIT에 도달하지 못했으므로 최종적으로 취소(롤백)된다.

| 시점 | 첫 번째 UPDATE의 상태 |
|---|---|
| UPDATE 실행 직후 | DB 안에는 반영됐지만 미확정. 로그에 기록되고 데이터 페이지가 바뀌었을 수도 있다. |
| 두 번째 UPDATE에서 고장 | COMMIT에 도달하지 못한다. |
| 롤백 또는 복구 | 미확정 변경을 undo해서 원래대로 되돌린다. |

"중간 상태가 남지 않는다"는 말은 실행된 적이 없다는 뜻이 아니라, 실행됐더라도 **최종 결과에는 남지 않는다**는 뜻이다.

#### 고장 종류별 동작

1. **쿼리 에러(제약 위반 등):** `ROLLBACK`으로 첫 번째 UPDATE를 즉시 되돌린다.
2. **서버 크래시:** 재시작할 때 로그를 읽고, COMMIT 기록이 없는 트랜잭션은 미완료로 보고 undo한다. 이미 디스크에 반영된 변경도 로그로 되돌린다.
3. **COMMIT 직후 크래시:** 커밋 기록이 로그에 있으면 redo로 복구해서 결과를 유지한다(내구성).

#### 다른 사용자가 조회하면

| 시점 | 제3자가 보는 A 계좌 잔액 |
|---|---|
| 트랜잭션 시작 전 | 1000 |
| 첫 UPDATE 실행 후 (미커밋) | 1000 |
| 롤백 후 | 1000 |

- 제3자는 중간 값(900)을 본 적이 없다. 바깥에서 보면 처음부터 변화가 없었던 것과 같다.
- 대부분의 DB는 MVCC로 커밋 전 변경을 다른 트랜잭션에 보이지 않게 한다. InnoDB는 undo log의 이전 버전을, PostgreSQL은 튜플 버전을 읽게 한다.
- 예외는 `READ UNCOMMITTED`다. 이 격리 수준에서는 커밋 안 된 값이 보일 수 있고, 이를 dirty read라고 한다. 롤백 후 존재하지 않게 된 값을 근거로 판단하게 되므로 실무에서는 거의 쓰지 않는다.
- PostgreSQL은 `READ UNCOMMITTED`를 지정해도 내부적으로 `READ COMMITTED`처럼 동작한다.

## 한 줄 정리

> SQL은 데이터 구조, 동시성, 고장 후 불일치라는 복잡도를 DB 안에 가둬서, 개발자가 쿼리와 트랜잭션 경계만 신경 쓰게 해주는 추상화다.
