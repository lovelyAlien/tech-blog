# Spring Batch Partitioning은 한 줄로 어떻게 설명하고, 성능 결과는 어떻게 읽는가

Partitioning의 구조와 흐름은 [[Spring Batch Partitioning 구조와 처리 흐름]]에 정리했다. 이 노트는 면접에서 **짧게 정의하는 법**, 그리고 카카오페이 사례의 **"10.9배 빨라졌다"는 결과를 어디까지 믿고 말할 수 있는지**를 정리한다.

## 면접용 한 줄 정의

> **"Partitioning은 데이터를 겹치지 않는 범위(파티션)로 나누고, 파티션마다 독립된 Worker Step을 실행해 병렬로 처리하는 Spring Batch의 확장 방식입니다."**

꼬리 질문이 나오면 이렇게 덧붙인다.

> "Manager Step이 Partitioner로 범위를 나누고, PartitionHandler가 스레드 풀을 통해 Worker Step들을 실행합니다. Worker마다 Reader·Writer를 따로 가져서 스레드끼리 상태를 공유하지 않습니다."

| 등장인물 | 맡은 질문 | 하는 일 |
|---|---|---|
| Manager Step | 전체 총괄 | 계획을 받아 실행을 맡기고 최종 상태를 정함 |
| Partitioner | **무엇을** 나눌까 | 범위(표지, ExecutionContext)만 만든다. 데이터는 안 읽는다 |
| PartitionHandler | **어떻게** 실행할까 | 스레드 풀·Worker Step·gridSize를 설정하고, 배분하고 기다린다 |
| Worker Step | 실제 처리 | Reader → Processor → Writer |

## "나누기"는 세 겹이다

이 사례에는 크기가 다른 "나누기"가 세 번 나온다. 이걸 하나로 보면 사례 전체가 헷갈린다.

| 나누기 | 무엇을 → 무엇으로 | 목적 | 담당 |
|---|---|---|---|
| ① **파티셔닝** | 한 달 → **하루치 31개** | 일을 여러 일꾼에게 나눠 맡기기 | Partitioner + PartitionHandler |
| ② **Cursor batchSize** | 하루치 수백만 건 → **1,000건씩 받아 오기** | 메모리에 조금씩만 올리기 | Reader |
| ③ **Chunk** | 1,000건씩 → **쓰고 커밋** | 처리·트랜잭션 단위 | Worker Step |

```
3월 한 달
 └─ ① 파티셔닝: 3/1, 3/2, ... 3/31   (31개 파티션, 스레드 6개가 나눠 맡음)
      └─ 3/5 하루치 수백만 건
           └─ ② Cursor: 1,000건씩 DB에서 받아 옴
                └─ ③ Chunk: 1,000건 가공 → 쓰기 → 커밋 → 다음 1,000건
```

## 파티셔닝은 병렬 처리와 같은 말이 아니다

파티셔닝은 **나누고 독립적으로 실행하는 구조**다. 병렬은 **TaskExecutor(스레드 풀)가 만든다.**

- 스레드 풀 대신 한 스레드로 차례대로 실행하는 동기 executor를 넣으면, 파티셔닝이지만 병렬은 아니다.
- 여러 서버(JVM)로 나눠 실행하면 Remote Partitioning이다.
- 카카오페이 사례는 한 JVM 안에서 스레드 6개로 돌렸으니 Local Partitioning + 병렬 처리다.

## 사례 요약

1. 원장 통계 구조가 바뀌어 과거 수억 건을 다시 만들어야 했다.
2. 기간을 월 단위 배치로 나누고, 배치 안에서 다시 하루 단위로 나눠 병렬 처리했다(Partitioning).
3. 스레드 6개가 하루치(수백만 건)씩 한꺼번에 메모리에 올리자 OOM이 났다.
4. 읽기는 Cursor로 조금씩, 쓰기는 Bulk로 한 번에 바꿨다.

## 성능 결과

비즈니스 로직 없이 읽고 쓰기만 하는 배치로 측정했고, 두 방식 모두 chunkSize는 1,000이다.

| 데이터 건수 | 기본 방식 | 최적화 방식 | 차이 |
|---|---|---|---|
| 1만 | 3초 | 2초 | 1.5배 |
| 10만 | 33초 | 15초 | 2.2배 |
| 100만 | 11분 22초 | 1분 53초 | 약 6배 |
| 500만 | 1시간 37분 25초 | 8분 55초 | 약 10.9배 |

### 데이터가 늘 때 시간이 몇 배로 느는지 본다

| 구간 | 데이터 증가 | 기본 방식 시간 증가 | 최적화 방식 시간 증가 |
|---|---|---|---|
| 10만 → 100만 | 10배 | 약 21배 📈 | 약 7.5배 |
| 100만 → 500만 | 5배 | 약 8.6배 📈 | 약 4.7배 |

- **기본 방식**은 데이터가 늘어난 것보다 시간이 더 많이 는다. 늘수록 가속이 붙는다. Paging의 "매번 처음부터 세기"와 같은 모양이다.
- **최적화 방식**은 데이터가 늘어난 만큼 시간도 비슷하게 는다. Cursor의 "비용 일정"과 같은 모양이다.

그래서 데이터가 많을수록 차이가 벌어진다.

또 하나의 단서가 있다. 병렬 처리만으로 빨라진다면 스레드 6개로는 **최대 약 6배**가 한계다. 그런데 500만 건에서 10.9배가 나왔다. 병렬 말고도 **기본 방식을 크게 느리게 만드는 다른 요인**이 있었다는 뜻이다.

> 원문은 "기본 방식"이 정확히 어떤 Reader·Writer·스레드 구성인지 밝히지 않는다. "기본 방식이 Paging이었다"는 숫자 모양에서 추측한 것이지 단정할 수 없다.

### "Bulk 덕분에 10.9배"라고 말할 수 없는 이유

최적화 방식에는 세 가지가 **한꺼번에** 들어 있다.

```
최적화 방식 = Partitioning + Cursor Reader + Bulk Writer
```

감기에 걸려 약 세 가지를 한꺼번에 먹고 나았다면, 어느 약 덕분인지 알 수 없다. 마찬가지로 각 기법의 기여도는 알 수 없다. 정확한 표현은 이거다.

> "세 기법을 **함께 적용했더니** 500만 건 기준 약 10.9배 빨라졌다."

각각의 효과를 알려면 하나씩 추가하며 재야 한다(ablation).

| 실험 | 구성 | 알 수 있는 것 |
|---|---|---|
| 1 | 기본 | 기준값 |
| 2 | 기본 + Partitioning | 병렬 처리의 효과 |
| 3 | 2 + Cursor | 읽기 방식의 효과 |
| 4 | 3 + Bulk | 쓰기 방식의 효과 |

원문은 1과 4만 비교했다.

### 결과를 읽을 때 주의할 점

1. 세 기법을 **함께 적용한 효과**다. 각각의 기여도는 모른다.
2. **"기본 방식"이 무엇인지** 원문에 없다.
3. **비즈니스 로직 없이** 읽고 쓰기만 했다. 실제 통계 계산이 들어가면 차이가 줄 수 있다.
4. 서버 사양, 문서 크기 같은 **측정 환경**이 없다.
5. 원문 그래프의 500만 건 기본 방식 라벨은 **87.42**인데, 표와 본문은 1시간 37분 25초(≈97.42분)다. 10.9배도 97.42 ÷ 8.92로 계산된다. **표 기준**으로 읽는다.

## 내가 헷갈렸던 것

| 처음 이해 | 정확한 이해 |
|---|---|
| 하루치를 한 번에 가져오지 않고 조각만큼 가져오는 게 파티셔닝이다 | 그건 **Cursor**다. 파티셔닝은 **작업 범위를 나눠 맡기는 것**이다 |
| 파티셔닝 = 병렬 처리 | 파티셔닝은 나누는 구조, 병렬은 **스레드 풀**이 만든다 |
| "Bulk 덕분에 10.9배 빨라졌다" | 세 기법을 **함께** 적용한 결과다. 기여도는 분리할 수 없다 |
| Partitioner가 총괄 매니저다 | 총괄은 **Manager Step**이다. Partitioner는 계획, PartitionHandler는 실행 |

## 스스로 확인할 질문

- Partitioning을 한 문장으로 정의하고, 등장인물 네 명의 역할을 1분 안에 말할 수 있는가?
- 이 사례의 "나누기" 세 겹은 각각 무엇을 무엇으로 나누는가?
- 스레드 6개인데 10.9배가 나왔다는 사실에서 무엇을 추론할 수 있는가?
- 이 결과로 말할 수 있는 것과 말할 수 없는 것은?

## 확인 필요

- 원문 "기본 방식"의 실제 구성(Reader, Writer, 스레드 수)은 원문에 없다. 기여도를 말하려면 하나씩 추가하는 실험이 필요하다

## 한 줄 정리

> Partitioning은 데이터를 겹치지 않는 범위로 나눠 Worker Step마다 독립 처리하는 구조이고, 병렬은 스레드 풀이 만든다. 사례의 10.9배는 Partitioning·Cursor·Bulk를 함께 적용한 결과라 기법별 기여도는 알 수 없다.
