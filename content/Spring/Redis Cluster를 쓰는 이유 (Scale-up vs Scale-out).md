# 단일 Redis 노드 대신 Redis Cluster를 쓰는 이유

트래픽이 늘어날 때 캐시 서버를 어떻게 확장할지는 "노드 스펙을 올릴 것이냐(Scale-up), 노드를 늘릴 것이냐(Scale-out)"의 선택 문제다. 면접에서 "왜 Cluster를 선택했나요?"라고 물으면 이 트레이드오프로 답해야 한다.

## Scale-up(단일 노드 스펙 증가)의 한계

- 결국 물리적으로 붙일 수 있는 메모리·CPU에는 상한이 있다. 트래픽이 계속 늘면 언젠가는 막힌다.
- 노드가 하나뿐이라는 건 그 노드가 곧 단일 장애점(SPOF)이라는 뜻이다. 이 노드가 죽으면 캐시 전체가 죽는다.

## Scale-out(Redis Cluster)의 이점

Redis Cluster는 데이터를 여러 노드에 **샤딩(hash slot 기반)**해서 분산시킨다.

```
[클라이언트]
     │
     ▼
┌─────────┬─────────┬─────────┐
│ Node A  │ Node B  │ Node C  │  ← 각 노드가 hash slot 일부씩 담당
│(슬롯 0~5460)│(5461~10922)│(10923~16383)│
└─────────┴─────────┴─────────┘
     │         │         │
   Replica   Replica   Replica   ← Primary 장애 시 자동 승격
```

- **확장성**: 트래픽이 늘면 노드를 추가하는 것만으로 대응 가능. 특정 노드에 트래픽이 몰리는 핫스팟 문제도 샤딩으로 분산된다.
- **가용성**: Primary 노드에 장애가 나면 Replica가 자동으로 승격되어 캐시 가용성을 유지한다.

## Redisson 클라이언트의 역할

Cluster를 쓰면 노드 구성이 리밸런싱되거나 장애 조치(failover)가 일어날 때 토폴로지가 바뀐다. 이걸 애플리케이션 코드에서 직접 추적하면 복잡해지는데, Redisson 같은 클라이언트를 쓰면 이 토폴로지 변화를 클라이언트가 자동으로 추적해줘서 애플리케이션 코드는 노드 구성 변화를 신경 쓸 필요가 없다.

## 한 줄 정리
> Scale-up은 성능 한계와 SPOF 문제를 안고 가는 선택이고, Scale-out(Redis Cluster)은 노드 추가로 확장하고 Replica 승격으로 가용성을 챙기는 선택이다 — 트래픽이 계속 늘어날 걸 전제하면 Scale-out이 구조적으로 더 안전하다.
