# 좌석 하나를 두고 여러 명이 동시에 예약하면 어떻게 막을까 — 5가지 동시성 제어 전략 비교

인기 콘서트 티켓팅처럼 "재고 1개를 여러 명이 동시에 채가려는" 상황은 동시성 제어의 정석 교과서 같은 문제다. 실제 티켓팅 프로젝트(우아한 티켓팅)는 같은 인터페이스(`ReservationService`)를 구현하는 5개의 전략을 동시에 빈으로 등록해두고, 어떤 걸 `@Primary`로 쓰느냐만 바꿔서 손쉽게 비교할 수 있게 짜여 있다. 각 전략이 "동시에 두 명이 같은 좌석을 선택하면"이라는 같은 문제를 어떻게 다르게 푸는지 정리한다.

## 문제 상황

좌석 1개, 동시 요청 2개(스레드 A, B). 어떻게 하든 결과는 "딱 한 명만 성공"해야 한다.

```
A ──┐
    ├─► [ 좌석 1번 ] ──► 둘 다 조회하면 둘 다 "선택 가능"으로 보임 → 둘 다 성공하면 안 됨
B ──┘
```

## 1. 낙관적 락 (Optimistic Lock)

JPA `@Version` 컬럼 + `LockModeType.OPTIMISTIC`. "충돌은 드물 것"이라 가정하고, 커밋 시점에 버전이 바뀌었으면 그제서야 예외를 던진다.

```java
@Version private Long version;

@Query("SELECT s FROM Seat as s WHERE s.seatId = :seatId")
@Lock(LockModeType.OPTIMISTIC)
Optional<Seat> findByIdWithOptimistic(@Param("seatId") Long seatId);
```

이 프로젝트는 충돌 시 **재시도를 하지 않고** 바로 "선택 불가" 에러로 변환한다.

```java
try {
    reservationTransactionService.selectSeat(memberEmail, seatSelectionRequest);
} catch (OptimisticLockingFailureException | StaleObjectStateException e) {
    throw new TicketingException(ErrorCode.NOT_SELECTABLE_SEAT);
}
```

재시도를 안 하는 게 버그가 아니라 의도된 설계에 가깝다 — 좌석 선택은 "이미 남이 가져간 좌석을 나도 재시도해서 뺏어오는" 게 의미가 없는 도메인이라, 실패하면 바로 사용자에게 "이미 선택된 좌석입니다"라고 알려주는 게 맞다.

## 2. 비관적 락 (Pessimistic Lock)

`SELECT ... FOR UPDATE`로 DB 로우 자체를 잠근다. 락을 획득 못한 트랜잭션은 DB 커넥션을 잡은 채로 **대기**한다.

```java
@Query("SELECT s FROM Seat as s WHERE s.seatId = :seatId")
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Seat> findByIdWithPessimistic(@Param("seatId") Long seatId);
```

낙관적 락과 정반대 철학이다 — "충돌이 자주 일어날 것"이라 가정하고 아예 처음부터 막아버린다. 대신 대기하는 트랜잭션 수만큼 DB 커넥션 풀이 묶이므로, 동시 요청이 많아지면 커넥션 고갈로 이어질 수 있다.

## 3. Redisson 분산 락

Redis를 "여러 서버가 공유하는 락 저장소"로 쓴다. 서버가 여러 대여도 딱 한 서버의 한 스레드만 통과시킬 수 있다는 게 핵심.

```java
RLock lock = redissonClient.getLock("seat:" + seatId);
if (!lock.tryLock(1, 60, TimeUnit.SECONDS)) {
    return;
}
try {
    action.run();
} finally {
    lock.unlock();
}
```

Redisson의 핵심 장점은 **락을 기다리는 방식이 폴링이 아니라 Pub/Sub**라는 것이다. 락이 풀리면 Redis가 대기자에게 알림을 보내는 구조라서, "계속 물어보는" 스핀락보다 Redis 부하가 훨씬 적다. (자세한 흐름은 [[Mutex Lock]] 참고)

## 4. Lettuce로 직접 구현한 락

Redisson 같은 라이브러리 없이, `SETNX`만으로 락을 흉내낸 버전. 진짜 스핀락이다.

```java
public Boolean seatLock(String key) {
    return redisTemplate.opsForValue().setIfAbsent(key, "lock", Duration.ofMinutes(1));
}

// 사용부
int retryLimit = 5;
while (retryLimit > 0 && !lettuceRepository.seatLock(lockKey)) {
    retryLimit -= 1;
    Thread.sleep(300); // 실패할 때마다 300ms씩 자면서 재시도 = 스핀락
}
```

Redisson과 나란히 두면 "왜 스핀락이 Redis에 부하를 주는가"가 바로 체감된다 — 락이 안 풀리는 동안 계속 `SETNX`를 던지면서 Redis에 물어보기 때문이다.

## 5. 순수 Redis (DB 락 없이, 이 프로젝트가 실제로 쓰는 방식)

`@Primary`로 지정되어 실제 운영에 쓰이는 구현. DB 락은 아예 걸지 않고, **Redis 키 자체가 곧 "좌석 점유권"**이다.

```java
Boolean result = redisTemplate.opsForValue()
        .setIfAbsent("seat-selected-number:" + seatId, member.getEmail(),
                     reservationReleaseDelay, TimeUnit.SECONDS);
if (Boolean.FALSE.equals(result)) {
    throw new TicketingException(ErrorCode.NOT_SELECTABLE_SEAT);
}
```

여기서 재밌는 부분은 결제 확정 시점이다. "내가 점유한 좌석이 맞는지" 확인하고 지우는 걸 **Lua 스크립트로 원자적으로** 처리한다.

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

왜 `GET` 하고 나서 `DEL`을 따로 호출하면 안 될까? `GET`으로 확인한 순간과 `DEL`을 실행하는 순간 사이에 시간차가 있으면, 그 틈에 키가 TTL로 만료되거나 다른 요청이 끼어들 수 있다(Check-Then-Act 레이스). Lua 스크립트는 Redis 안에서 **한 번에 원자적으로** 실행되므로 이 틈이 아예 없다.

## 실제 코드에서 발견한 버그 2가지

같은 "락 해제(finally)" 코드인데, 구현마다 소유권 확인 여부가 다르다.

**Lettuce 버전 — 락을 못 얻었는데도 지워버림**

```java
try {
    while (retryLimit > 0 && !lettuceRepository.seatLock(lockKey)) {
        retryLimit -= 1;
        Thread.sleep(300);
    }
    if (retryLimit > 0) {
        action.run();
    } else {
        throw new TicketingException(ErrorCode.NOT_SELECTABLE_SEAT); // 락 획득 실패
    }
} finally {
    lettuceRepository.unlock(lockKey); // ⚠️ 실패했어도 무조건 호출됨
}
```

`retryLimit`이 0이 되어 락 획득에 실패해도 `finally`는 무조건 실행된다. 즉 **내가 가진 적도 없는 락을, 지금 그 락을 진짜로 쥐고 있는 다른 스레드보다 먼저 지워버릴 수 있다.** 소유권 확인 없이 무조건 `DEL`을 날리는 게 원인이다.

**Redisson 버전 — tryLock 실패해도 unlock 시도**

```java
try {
    if (!lock.tryLock(tryTime, releaseTime, TimeUnit.SECONDS)) {
        return; // 락 획득 실패
    }
    action.run();
} finally {
    lock.unlock(); // ⚠️ return 했어도 finally는 실행됨 → 소유 안 한 락을 unlock 시도
}
```

`tryLock`이 실패해서 `return`해도 `finally`의 `unlock()`은 실행된다. Redisson은 소유하지 않은 락을 풀려고 하면 `IllegalMonitorStateException`을 던지므로, 이 경로를 타면 원래 던지려던 예외 대신 엉뚱한 예외가 나갈 수 있다.

**올바른 패턴**: `finally`에서 `unlock()`을 호출하기 전에 "내가 정말 이 락을 획득했는가"를 먼저 확인해야 한다. Redisson은 `lock.isHeldByCurrentThread()`, 직접 구현한 락은 저장한 값과 내 식별자를 비교(Lua CAS)하는 방식으로 확인할 수 있다.

## 다섯 전략 한눈에 비교

| 전략 | 잠그는 대상 | 실패 시 동작 | 특징 |
|---|---|---|---|
| 낙관적 락 | DB row (버전 비교) | 예외 즉시 반환, 재시도 없음 | 충돌이 드물 때 유리, 커넥션 안 묶음 |
| 비관적 락 | DB row (`FOR UPDATE`) | 락 풀릴 때까지 대기 | 충돌이 잦을 때 유리, 커넥션 오래 묶임 |
| Redisson | Redis 키 (RLock) | tryLock 타임아웃까지 대기(Pub/Sub) | 여러 서버로 확장 가능, DB 부하 없음 |
| Lettuce 직접 구현 | Redis 키 (SETNX) | 재시도(sleep) 후 포기 | 스핀락이라 Redis에 폴링 부하 |
| 순수 Redis (`@Primary`) | Redis 키 (SETNX, DB 락 없음) | 즉시 실패 | DB 락 자체가 없어 가장 가볍다 |

## 한 줄 정리
> 낙관적 락은 "충돌은 드물다"는 가정, 비관적 락은 "충돌은 흔하다"는 가정이고, 분산 락(Redisson/Lettuce)은 그 가정을 여러 서버로 확장한 것이다. 그리고 어떤 락이든 "해제" 코드에서 소유권을 확인하지 않으면, 남의 락을 실수로 지워버리는 레이스가 생긴다.
