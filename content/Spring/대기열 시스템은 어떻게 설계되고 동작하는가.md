# 대기열 시스템은 어떻게 설계되고 동작하는가

콘서트 예매 오픈 순간처럼 "동시에 수만 명이 예매 페이지로 몰리면 서버가 감당을 못 한다"는 문제를, 실제로 다 받아주되 **입장 가능 인원수만 제한**해서 순서대로 통과시키는 방식으로 푼 게 대기열(waiting queue) 시스템이다. 실제 티켓팅 프로젝트(우아한 티켓팅) 코드를 따라가며 요청 하나가 들어왔을 때 실제로 무슨 일이 벌어지는지 정리한다.

## 핵심 개념: 대기실과 작업공간을 분리한다

- **대기실(Waiting Room)**: "줄 서 있는 사람들". 순번만 있고 아직 아무것도 못 한다.
- **작업공간(Running Room)**: "지금 입장해서 좌석을 고를 수 있는 사람들". 인원수 제한이 있고, 일정 시간 활동이 없으면 쫓겨난다.

놀이공원 인기 놀이기구를 떠올리면 된다 — 대기줄에 있는 사람 수는 무제한이지만, 놀이기구 안에 탈 수 있는 인원은 정해져 있고, 시간이 지나면 내리고 다음 사람이 탄다.

## 요청 하나가 들어왔을 때 실제 흐름

좌석 목록 조회처럼 무거운 API(`GET /api/performances/{id}/seats`)에는 `@Waiting` 어노테이션이 붙어 있고, `WaitingAspect`가 이걸 가로챈다.

```java
@Around("@annotation(...Waiting)")
private Object waitingRequest(ProceedingJoinPoint joinPoint) throws Throwable {
    ...
    if (waitingSystem.isReadyToHandle(email, performanceId)) {
        return joinPoint.proceed();           // 작업공간에 있으면 → 원래 로직 실행
    } else {
        waitingSystem.enterWaitingRoom(email, performanceId); // 없으면 → 대기실 등록
        return ResponseEntity.status(HttpStatus.TEMPORARY_REDIRECT)
                .location(URI.create("/api/performances/" + performanceId + "/wait"))
                .build();
    }
}
```

```
요청 → @Waiting 붙은 API 호출
         │
         ▼
   지금 작업공간에 있는가? ──Yes──► 원래 로직 실행 (좌석 조회 등)
         │No
         ▼
   대기실에 등록 + 307 리다이렉트 (Location: /api/performances/{id}/wait)
         │
         ▼
   프론트: /wait 엔드포인트를 5초 간격으로 폴링
         │
         ▼
   내 순번이 될 때까지 반복 ──► remainingCount <= 0 되면 원래 페이지로 이동
```

실제로 브라우저에서 이 프로젝트를 띄워보면 "대기열 정보를 5초마다 갱신 중입니다"라는 문구와 함께 이 폴링이 그대로 눈에 보인다.

## 폴링 한 번마다 서버에서 벌어지는 일

```java
public long getRemainingCount(String email, long performanceId) {
    long memberWaitingCount = waitingManager.getMemberWaitingCount(email, performanceId);
    long runningCount = runningManager.getRunningCount(performanceId);
    long remainingCount = memberWaitingCount - runningCount;

    eventPublisher.publish(pollingEventCache.computeIfAbsent(performanceId, PollingEvent::new));
    if (remainingCount <= 0) {
        eventPublisher.publish(new LastPollingEvent(email, performanceId));
    }
    return remainingCount;
}
```

- **남은 인원 = 내 순번 − 현재 작업공간 입장 인원**. 예를 들어 내가 150번째로 대기실에 들어왔고 지금 100명이 작업공간에 있다면, 남은 인원은 50명.
- 폴링할 때마다 `PollingEvent`를 발행한다 → 리스너가 대기실→작업공간 이동 로직(`moveUserToRunning`)을 트리거한다. 즉 **"내 순번 확인하러 온 요청"이 동시에 "전체 대기열을 한 칸씩 밀어주는 트리거" 역할도 한다.**
- 내 순번이 됐으면(`remainingCount <= 0`) `LastPollingEvent`를 발행해서 내 작업공간 체류 시간을 5분으로 갱신한다 — 방금 입장했는데 바로 만료되는 걸 막기 위함.

## moveUserToRunning — 대기실에서 작업공간으로 밀어넣기

```java
public void moveUserToRunning(long performanceId) {
    Set<String> removeMemberEmails = runningManager.removeExpiredMemberInfo(performanceId); // 1
    waitingManager.removeMemberInfo(removeMemberEmails, performanceId);                       // 2
    long availableToRunning = runningManager.getAvailableToRunning(performanceId);            // 3
    Set<String> emails = waitingManager.pullOutMemberEmails(performanceId, availableToRunning); // 4
    runningManager.enterRunningRoom(performanceId, emails);                                   // 5
}
```

1. 작업공간에서 시간 초과(5분 무활동)된 사람을 찾아 제거
2. 그 사람들을 대기실 명단에서도 지움 (좀비 상태 방지)
3. 작업공간에 지금 몇 자리가 비었는지 계산 (`정원 100 − 현재 인원`)
4. 대기실에서 **가장 오래 기다린 순서대로** 빈 자리 수만큼 꺼내옴
5. 꺼내온 사람들을 작업공간에 입장시킴 (입장 즉시 최소 30초 체류 보장)

## 왜 폴링마다 이 로직을 다 돌리면 안 되는가 — 디바운스로 막기

같은 공연을 대기 중인 사람이 1000명이면, 5초마다 1000개의 폴링 요청이 들어오고 그때마다 `moveUserToRunning`이 1000번 실행될 뻔했다. 실제로는 5초에 한 번만 실행되면 충분한 로직인데 말이다. `DebounceAspect`가 `WaitingSystem.moveUserToRunning(long)` 자체에 포인트컷을 걸어서 이 문제를 막는다.

```java
@Pointcut("execution(public void ...WaitingSystem.moveUserToRunning(long))")
private void moveWaitingMemberToRunning() {}

@Around("debounceAnnotation() || moveWaitingMemberToRunning()")
public Object debounce(ProceedingJoinPoint joinPoint) throws Throwable {
    if (debounce.setIfAbsent(getDebounceKey(performanceId), "debounce", 5, TimeUnit.SECONDS)) {
        return joinPoint.proceed();   // 5초 안에 이미 실행됐으면 여기 못 옴
    }
    return null;
}
```

1000개의 요청 중 딱 하나만 `moveUserToRunning`을 실제로 실행하고, 나머지 999개는 조용히 스킵된다. 이 프로젝트의 README에 나오는 "GC 빈도를 낮추기 위해 로직을 개선"이 바로 이 부분이다 — 불필요한 객체 생성/쿼리를 1000번에서 1번으로 줄인 것.

## 결제가 끝나면 작업공간에서 바로 빼준다

```java
@TransactionalEventListener(PaymentEvent.class)
public void pullOutRunningMember(PaymentEvent event) {
    ...
    waitingSystem.pullOutRunningMember(event.getEmail(), performanceId);
}
```

결제까지 끝낸 사람을 5분 만료될 때까지 굳이 작업공간에 붙잡아둘 이유가 없다 — 결제 성공 즉시 자리를 비워줘서 다음 대기자가 더 빨리 들어올 수 있게 한다. `@EventListener`가 아니라 `@TransactionalEventListener`를 쓴 이유도 중요한데, 결제 트랜잭션이 **커밋된 이후**에만 이 리스너가 실행되도록 보장하기 위해서다. 만약 커밋 전에 실행되면, 아직 결제가 실제로 확정되지 않은 상태에서 사용자를 작업공간 밖으로 밀어낼 위험이 있다 (관련 개념은 [[ApplicationEventPublisher와 TransactionalEventListener]] 참고).

## Redis 자료구조 선택 — 왜 하필 ZSet인가

대기실/작업공간은 전부 Redis로 구현돼 있는데, 자료구조를 상황에 맞게 다르게 골라 썼다.

### 대기열 순서 보장: ZSet + INCR

```java
// 순번 발급 (String + INCR, 원자적이라 중복 순번 없음)
public long getNextCount(long performanceId) {
    return waitingCounter.increment(getWaitingCounterKey(performanceId), 1);
}

// 대기열 등록: 순번을 score로 저장
waitingLine.add(key, email, waitingCount);

// 대기열에서 꺼내기: 점수가 가장 낮은(가장 오래 기다린) N명을 원자적으로 꺼냄
Set<TypedTuple<String>> popped = waitingLine.popMin(key, availableToRunning);
```

ZSet은 "값 + 점수" 쌍을 점수 순으로 정렬해서 저장한다. 점수를 "입장 순번"으로 쓰면 자연스럽게 FIFO 큐가 되고, `ZPOPMIN`이 원자적 연산이라서 여러 서버 인스턴스가 동시에 "빈 자리만큼 꺼내가기"를 호출해도 같은 사람이 중복으로 뽑히는 일이 없다.

### 필드별 TTL이 없는 문제: ZSet score를 만료 시각으로

Redis Hash나 Set은 멤버 하나하나에 개별 TTL을 걸 수 없다. 그런데 작업공간은 "사람마다 각자 다른 만료 시각(입장 시각 + 5분)"이 필요하다. 그래서 작업공간도 ZSet으로 만들고, **score 자리에 만료 시각(epoch seconds)을 넣는다.**

```java
// 입장 = "지금부터 30초 뒤"를 만료 시각으로 등록
runningRoom.add(key, email, (double) minimumRunningTime.toEpochSecond());

// 만료된 사람 정리 = "현재 시각보다 score가 작은" 멤버를 범위로 찾아서 지움
Set<String> expired = runningRoom.rangeByScore(key, 0, now);
runningRoom.removeRangeByScore(key, 0, now);
```

`ZRANGEBYSCORE` + `ZREMRANGEBYSCORE`로 "특정 시각 이전에 만료된 멤버들"을 통째로 찾아 지운다. 개별 키 TTL 대신 **정렬된 점수 범위 조회**로 만료를 흉내내는 패턴이다.

## 코드에 남아있는 동시성 이슈 (작성자가 직접 주석으로 인정한 부분)

```java
/**
 * 러닝룸 만료시간을 5분뒤로 업데이트 한다. 동시성 문제가 발생할 수 있다.
 */
public void updateRunningMemberExpiredTime(String email, long performanceId) {
    if (runningRoom.score(key, email) != null) {   // ① 아직 있는지 확인
        runningRoom.add(key, email, 새로운만료시각);   // ② 있으면 갱신
    }
}
```

①에서 "이 사람이 아직 작업공간에 있다"를 확인하고 ②에서 갱신하는데, 이 둘은 별개의 Redis 명령이라 **원자적이지 않다.** ①과 ② 사이에 다른 스레드가 `removeExpiredMemberInfo`로 이 멤버를 지워버리면, ②는 "이미 나간 사람"을 다시 작업공간에 되살려버린다 — 전형적인 TOCTOU(Time-Of-Check to Time-Of-Use) 레이스다. 앞서 본 `popMin`이나 `INCR`처럼 Redis의 원자적 명령 하나로 끝내지 않고 "확인 후 실행"을 두 스텝으로 나누면 이런 문제가 생긴다는 걸 보여주는 좋은 반례다.

## 전체 그림 요약

```
[사용자] ──/seats 요청──► [WaitingAspect]
                              │
                작업공간에 있음? ──Yes──► 원래 로직
                              │No
                              ▼
                        대기실 등록 + 307
                              │
                              ▼
                [사용자] ──5초마다 폴링── /wait
                              │
                    getRemainingCount 호출
                              │
                    PollingEvent 발행 (매번)
                              │
                    ┌─────────────────────┐
                    │  Debounce: 5초에 1번만 통과 │
                    └─────────────────────┘
                              │
                      moveUserToRunning
                    (만료자 제거 → 빈자리 계산 → 대기실에서 순서대로 입장)
                              │
                    remainingCount <= 0 되면
                              │
                      LastPollingEvent (내 만료시간 갱신)
                              │
                              ▼
                        프론트가 원래 페이지로 이동
```

## 한 줄 정리
> 대기열 시스템의 핵심은 "줄 서는 곳(대기실)"과 "일하는 곳(작업공간)"을 분리하고, 폴링 요청 자체를 "내 순번 확인"이자 "전체 대기열을 한 칸 밀어주는 트리거"로 재사용한 것이다. 다만 트리거가 수천 명분 동시에 몰리면 그만큼 반복 실행되므로, 디바운스로 실제 처리 빈도를 강제로 제한해야 한다.
