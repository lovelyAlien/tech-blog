## filesort는 왜 발생하는가

`WHERE channel_id = ? ORDER BY created_at DESC` 같은 쿼리에서 `channel_id`에만 인덱스가 있으면, DB는 인덱스로 해당 채널의 행들을 걸러낸 뒤 그 결과를 다시 `created_at` 기준으로 **별도 정렬**해야 한다. 이게 filesort다. 정렬 대상 행이 많아질수록 비용이 커진다.

## 복합 인덱스로 정렬을 없애는 원리

`(channel_id, created_at)` 복합 인덱스를 잡으면, 인덱스 내부가 이미 `channel_id`별로 묶이고 그 안에서 `created_at` 순으로 정렬된 상태로 저장된다. 그래서 DB는 인덱스를 순서대로 읽기만 하면 되고 별도 정렬이 필요 없다.

**컬럼 순서 원칙**: 동등 조건(`=`)으로 쓰이는 컬럼이 앞, 정렬·범위 조건으로 쓰이는 컬럼이 뒤. `channel_id = ?`는 동등 조건이라 앞, `created_at`은 정렬 기준이라 뒤에 온다. 순서가 바뀌면(`(created_at, channel_id)`) 인덱스가 `created_at` 전체를 먼저 정렬해버려서 `channel_id` 필터링에는 못 쓰이고, filesort도 그대로 남는다.

## OFFSET 페이지네이션의 한계

```sql
-- 페이지가 뒤로 갈수록 앞의 행을 스캔하고 버리는 비용이 커진다
SELECT * FROM messages WHERE channel_id = ? ORDER BY created_at DESC LIMIT 20 OFFSET 10000;
```

`OFFSET 10000`이면 DB는 앞의 10000개 행을 읽고 버린 뒤에야 원하는 20개를 반환한다. 페이지 번호가 커질수록 이 낭비가 누적된다.

## 커서(keyset) 기반 페이지네이션

OFFSET 대신 **마지막으로 받은 값**을 다음 쿼리의 조건으로 넘긴다.

```sql
-- 이전 페이지 마지막 메시지의 created_at을 커서로 사용
SELECT * FROM messages
WHERE channel_id = ? AND created_at < ?  -- 커서 값
ORDER BY created_at DESC
LIMIT 20;
```

인덱스가 이미 `(channel_id, created_at)` 순으로 정렬돼 있으므로, `created_at < ?` 조건도 인덱스 레인지 스캔만으로 처리된다. 몇 페이지를 넘어가든 스캔 비용이 일정하다.

### 함정: 동률 타임스탬프

`created_at`만 커서로 쓰면 같은 밀리초에 여러 행이 생성됐을 때 일부가 누락되거나 중복될 수 있다. `created_at`이 동일한 행 사이에서는 순서가 보장되지 않기 때문. 안전하게 하려면 `(created_at, id)` 튜플을 커서로 써서, `created_at`이 같을 때 `id`로 타이브레이크한다.

```sql
WHERE (created_at < ?) OR (created_at = ? AND id < ?)
```

## 조회 조건이 늘어날 때

새 필터 조건(예: 메시지 타입)이 **항상 동등 조건으로 함께 쓰인다면** 인덱스를 `(channel_id, message_type, created_at)`처럼 확장하는 게 맞다. 가끔만 쓰이는 조건이라면 기존 인덱스를 건드리지 않고 별도 인덱스를 추가하는 편이 낫다. 인덱스가 늘어날수록 쓰기(INSERT/UPDATE) 비용이 커지는 트레이드오프가 있으므로, 실제 조회 빈도를 보고 결정해야 한다.

## 추가로 고려할 것: 커버링 인덱스

SELECT 절에 필요한 컬럼까지 인덱스에 포함시키면, DB가 인덱스만 읽고 실제 테이블(힙)에는 접근하지 않아도 되는 **커버링 인덱스**가 된다. 조회 컬럼이 적고 고정적이라면 고려할 만하다.

## 면접 모범 답안 예시

> "채널별로 메시지를 시간순 정렬해서 페이지네이션하는 쿼리에서, channel_id에만 인덱스가 있어 걸러진 행을 다시 정렬하는 filesort가 발생했습니다. 그래서 (channel_id, created_at) 복합 인덱스를 잡았습니다. channel_id가 동등 조건이라 먼저, created_at이 정렬 기준이라 그 뒤에 오도록 해서, 인덱스 자체가 이미 정렬된 상태가 되어 별도 정렬이 필요 없어졌습니다.
>
> 페이지네이션은 OFFSET 대신 커서 방식을 썼습니다. 마지막으로 받은 created_at 값을 다음 요청의 조건으로 넘겨서 인덱스 레인지 스캔만으로 다음 페이지를 찾도록 했고, 이게 인덱스 컬럼 순서와도 맞물려 range 조건까지 인덱스만으로 처리됐습니다."

## 한 줄 정리
> 복합 인덱스는 (동등 조건 컬럼, 정렬/범위 조건 컬럼) 순으로 잡아야 filesort를 없앨 수 있고, 그 인덱스 순서를 커서 기반 페이지네이션의 조건과 맞추면 페이지가 깊어져도 스캔 비용이 늘지 않는다. 단, 정렬 기준 컬럼에 동률이 있을 수 있다면 PK 같은 타이브레이커를 커서에 함께 넣어야 안전하다.
