### Paging과 Cursor 조회는 무엇이 다른가

> chunkSize는 쓰기 단위일 뿐 메모리 상한이 아니다. Paging은 메모리는 일정하지만 매번 처음부터 세서 느려지고, Cursor는 DB 서버가 위치를 기억해 메모리와 속도가 모두 일정하다. 대신 열어 둔 커서는 DB 자원을 차지하니 반드시 닫는다.

- chunkSize는 Writer에 한 번에 넘기는 건수일 뿐, Reader가 DB에서 얼마나 쥐고 있는지는 Reader 구현이 정한다.
- JVM 힙은 모든 스레드가 함께 쓰는 그릇 하나라, 병렬로 돌리면 메모리 사용량도 스레드 수만큼 곱해진다.
- Paging(`OFFSET`, `skip`)은 메모리는 같지만 DB가 처음부터 세서 뒤로 갈수록 느려진다(누적 O(N²)).
- Cursor는 DB 서버가 조회 상태·읽은 위치를 들고 있고, 애플리케이션은 커서 번호만 가진다. 끝나면 반드시 닫는다.
- "커서 기반(keyset) 페이지네이션"은 매번 새 쿼리를 보내는 다른 개념이다.

**헷갈렸던 것**
| 처음 이해 | 정확한 이해 |
|---|---|
| chunkSize 1,000이면 메모리에 1,000건만 있다 | Reader가 내부에서 전부 조회하면 수백만 건이 남는다 |
| Paging은 뒤로 갈수록 메모리를 많이 쓴다 | 메모리는 같고 **느려진다** |
| 책갈피(읽은 위치)를 애플리케이션이 가진다 | 위치는 **DB 서버**가 갖고, 애플리케이션은 **커서 번호**만 가진다 |

### 경쟁 상태와 thread-safe

> 스레드들은 힙을 공유하기 때문에, 같은 값을 동시에 고치면 중간 단계가 끼어들어 결과가 틀어진다(경쟁 상태). 해결은 잠그기, 원자적 연산, 공유하지 않기 세 가지이고, Spring Batch Partitioning은 Worker마다 Reader를 따로 줘서 공유 자체를 없앤다.

- 스택(지역 변수)은 스레드마다 따로, 힙(객체·필드)은 모든 스레드가 공유한다.
- `count++`는 읽기 → 더하기 → 저장 세 단계라, 동시에 실행하면 +1이 사라질 수 있다.
- 해결: 잠그기(`synchronized`, 대가는 병목) / 원자적 연산(`AtomicInteger`) / 공유하지 않기.
- 싱글톤 Bean 필드에 요청별 상태를 두면 같은 문제가 생긴다.

**헷갈렸던 것**
| 처음 이해 | 정확한 이해 |
|---|---|
| Reader 하나를 쓰면 한 명이 점유하고 나머지가 기다리는 게 문제다 | 그건 **잠금이 있을 때**(병목)다. 잠금이 없으면 상태가 꼬여 **결과가 틀린다** |
| `count`는 Spring Batch에 있는 변수 이름이다 | 설명용 이름이다. 실제로는 "현재 위치", "현재 페이지" 같은 상태 값이다 |

원본: [[경쟁 상태와 thread-safe]]

### ThreadPoolExecutor 작업 처리 순서

> 스레드 풀은 core → 대기열 → max → 거절 순으로 작업을 받는다. max는 대기열이 꽉 차야 쓰이고, 대기열이 0이면 max를 넘는 작업은 거절된다.

- 판단 순서: core 미만이면 새 스레드 → 대기열 → 대기열이 차면 max까지 추가 → 그래도 차면 거절.
- 작업을 미리 나눠 주지 않고 먼저 끝난 스레드가 다음 작업을 가져가서, 작업 크기가 달라도 고르게 나뉜다.
- Spring `ThreadPoolTaskExecutor`의 queueCapacity 기본값은 `Integer.MAX_VALUE`라 max가 쓰이지 않는다.
- gridSize 시작값은 CPU 코어 × 1.5, OOM이 나면 절반으로 줄인다(사례 가이드).

**헷갈렸던 것**
| 처음 이해 | 정확한 이해 |
|---|---|
| 스레드 6개에 31개 작업을 5일씩 미리 배정한다 | 미리 배정하지 않는다. **끝난 스레드가 다음 것을 가져간다** |
| queueCapacity가 0이면 작업이 안 버려진다 | 반대다. 대기 의자가 없으니 max까지 차면 **거절된다** |

### Spring Batch JobScope와 StepScope

> `@StepScope`는 Step이 실행될 때마다 Bean을 새로 만들어, 실행 시점의 값(파티션별 날짜)을 넣어 주고 스레드끼리 Reader를 공유하지 않게 한다. 값은 jobParameters → Partitioner → ExecutionContext → Reader 순서로 전달된다.

- 싱글톤 Reader의 문제 두 가지: 앱 시작 시점엔 값을 넣을 수 없고, 스레드끼리 공유되어 상태가 꼬인다.
- `@JobScope`는 Job 실행 때 생성되어 `jobParameters`를, `@StepScope`는 Step 실행마다 생성되어 `stepExecutionContext`까지 읽는다(지연 바인딩).
- Partitioner는 데이터를 읽지 않고 날짜 표지만 만든다. 걸러내는 건 Reader의 조회 조건과 DB다.
- Worker Step 정의 1개, 실행 31개, 스레드 6개 — 개수가 다르다.
- Partitioner가 넣는 키와 Reader가 꺼내는 키 이름이 같아야 한다.

**헷갈렸던 것**
| 처음 이해 | 정확한 이해 |
|---|---|
| 누군가 원장 데이터를 31개로 쪼갠다 | 아무도 쪼개지 않는다. **조회 조건(날짜)만** 나눈다 |
| 파티션 31개면 Worker도 31개 | 정의는 1개, 실행은 31개, 스레드는 6개 |
| 스레드별 하루치를 가져오는 것도 PartitionHandler가 설정한다 | "하루치" 기준은 **Partitioner**, "누가 동시에 몇 명"은 **PartitionHandler**, "실제로 가져오기"는 **Reader** |

### Bulk 쓰기와 ORDERED UNORDERED

> Bulk는 Chunk 하나를 한 번의 왕복으로 보내서 쓰기 시간을 줄이는 **속도** 대책이다. 독립적인 데이터면 UNORDERED로 실패해도 나머지를 진행하고, 롤백 여부는 DB 트랜잭션에 달려 있으니 재시작 중복까지 고려해야 한다.

- Bulk가 줄이는 건 네트워크 왕복 횟수다. Writer 호출 횟수와 DB 요청 횟수는 다르다.
- 한 스레드가 read → process → write를 순서대로 하므로, Writer가 느려도 메모리는 쌓이지 않고 전체가 느려질 뿐이다.
- ORDERED(기본값)는 실패 지점에서 멈추고 뒤는 실행하지 않는다. UNORDERED는 실패 건만 빼고 나머지를 저장한다.
- 기준은 "앞 작업 결과에 뒤 작업이 기대는가". 독립적인 통계 적재라 UNORDERED를 골랐다.
- RDB는 Chunk 전체 롤백, MongoDB(트랜잭션 미사용)는 저장된 건이 남아 재시작 시 중복될 수 있다.

**헷갈렸던 것**
| 처음 이해 | 정확한 이해 |
|---|---|
| Bulk는 메모리 대책이다 | **속도** 대책이다. 메모리는 어느 쪽이든 Chunk 크기만큼이다 |
| Chunk가 실패하면 1,000개가 롤백되고 실패 목록으로 간다 | 롤백은 DB 트랜잭션에 달렸다(MongoDB는 남는다). 실패 목록은 MongoDB Bulk 결과다 |
| ORDERED에서 실패하면 나머지는 멈춰 있는 상태다 | 멈춰서 기다리는 게 아니라 **실행되지 않고 끝난다** |

### Spring Batch Partitioning 면접 설명과 성능 결과 해석

> Partitioning은 데이터를 겹치지 않는 범위로 나눠 Worker Step마다 독립 처리하는 구조이고, 병렬은 스레드 풀이 만든다. 사례의 10.9배는 Partitioning·Cursor·Bulk를 함께 적용한 결과라 기법별 기여도는 알 수 없다.

- 등장인물: Manager Step(총괄), Partitioner(무엇을 나눌까), PartitionHandler(어떻게 실행할까), Worker Step(실제 처리).
- "나누기" 세 겹: ① 파티셔닝(한 달 → 하루치 31개) ② Cursor batchSize(1,000건씩 받아 오기) ③ Chunk(1,000건씩 쓰고 커밋).
- 기본 방식은 데이터 증가보다 시간이 더 늘고, 최적화 방식은 비슷하게 는다.
- 스레드 6개인데 10.9배 → 병렬 말고도 기본 방식을 느리게 만든 요인이 있었다는 뜻이다.
- 기여도를 알려면 하나씩 추가하며 재는 실험(ablation)이 필요하다.

**헷갈렸던 것**
| 처음 이해 | 정확한 이해 |
|---|---|
| 하루치를 조각만큼 가져오는 게 파티셔닝이다 | 그건 **Cursor**다. 파티셔닝은 **작업 범위를 나눠 맡기는 것**이다 |
| 파티셔닝 = 병렬 처리 | 파티셔닝은 나누는 구조, 병렬은 **스레드 풀**이 만든다 |
| "Bulk 덕분에 10.9배 빨라졌다" | 세 기법을 **함께** 적용한 결과다. 기여도는 분리할 수 없다 |
