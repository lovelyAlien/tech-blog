# 대기열 시스템은 실제로 어떻게 설계되고 동작하나

`hhplus-concert-reservation-system`의 `queue-management-service` 코드를 끝까지 따라가봤다. "WAITING → PROCESSING" 2단계 구조이고, 실제 Redis 조작은 이 서비스가 직접 하지 않고 전담 마이크로서비스(`redis-service`)에 위임하는 게 특징이다. [[동시성 제어와 Kafka, MSA에서 실제로 어떻게 짜여있나]]에서 다룬 결제/락 얘기와 같은 프로젝트라 이어서 본다.

## 전체 그림

```
1) 토큰 발급          POST /waiting-queue-token
        │
        ▼
2) WAITING 큐 인입     Redis ZSet(waitingQueue)에 추가, score=요청시각(epoch초)
        │
        │   ← TokenScheduler가 1초마다 승급 시도
        ▼
3) PROCESSING 승급     ZSet에서 제거 + Redis String(TTL 30초)로 캐싱 + 카운터 +1
        │
        │   ← 30초 안에 예약~결제 끝내야 함
        ▼
4) 만료 or 완료        (a) TTL 만료 → keyspace 이벤트로 감지 → 카운터 -N
                       (b) 결제완료 이벤트 → 캐시 즉시 삭제 + 카운터 -1 (다만 현재는 死코드)
```

## 1) 토큰 발급 — 랜덤이 아니라 결정적(deterministic) 값

```java
// QueueTokenGenerator.java
private static final String SECRET_KEY = "secret-key";

public static String generateToken(String userId) {
    String input = userId + SECRET_KEY;
    byte[] hash = MessageDigest.getInstance("SHA-256").digest(input.getBytes(UTF_8));
    return Base64.getUrlEncoder().withoutPadding().encodeToString(hash);
}
```

`userId + "secret-key"`를 SHA-256 해시한 값이 토큰이다. 즉 **같은 유저는 언제 요청하든 항상 같은 토큰값**을 받는다 — curl/UI 테스트를 여러 번 반복해도 매번 똑같은 토큰이 나와서 처음엔 헷갈렸다.

- 장점: 같은 유저가 재요청해도 별 문제 없이 멱등하게 처리됨 (뒤에 나올 ZSet에 같은 member로 다시 들어가면 score만 갱신됨).
- 단점: `SECRET_KEY`가 소스에 평문으로 박혀있어서, 이 알고리즘과 시크릿을 아는 사람은 누구든 임의의 userId에 대한 토큰을 직접 계산해낼 수 있다. 대기열 새치기·토큰 위조가 가능한 구조적 약점.

## 2) 대기열 인입 — Redis ZSet

`WaitingQueueEnqueueCoreRepository.enqueue`가 redis-service에 `ZADD waitingQueue <token> <score>`를 요청한다. score는 `System.currentTimeMillis()/1000.0`(요청 시각) — 그래서 순서가 자연스럽게 FIFO가 된다. 내 순번(`position`)은 `getMemberRank`로 이 ZSet에서의 랭크를 그대로 가져온다.

## 3) 승급 — 1초마다 도는 스케줄러

```java
// TokenScheduler.java, application.yml: scheduler.queueTransferRate=1000
@Scheduled(fixedRateString = "${scheduler.queueTransferRate}")
public void processScheduledQueueTransfer() {
    processingQueueFacade.processQueueTransfer();
}
```

실제 로직 (`SimpleProcessingQueueService.processQueueTransfer`):

```java
AvailableSlots availableSlots = processingQueueRepository.countAvailableSlots(); // PROCESSING_QUEUE_COUNTER 조회
if (availableSlots.isSlotLimited()) return; // 자리가 없으면 그냥 스킵

waitingQueueRepository.retrieveTopTokens(availableSlots.counts()).forEach(waitingToken -> {
    processingQueueRepository.enqueue(waitingToken.toProcessing()); // PROCESSING으로 캐싱 + 카운터 +1
    waitingQueueRepository.remove(waitingToken);                    // WAITING ZSet에서 제거
});
```

`processing-queue.policy.max-limit: 1000` — 동시에 "결제 진행 중"일 수 있는 인원이 최대 1000명이라는 뜻. 매초, 지금 비어있는 슬롯 수만큼 대기열 맨 앞(ZSet에서 score가 가장 낮은, 즉 가장 먼저 온) 사람들을 끌어올린다. 그래서 유저가 몇 명 없는 로컬 테스트 환경에서는 대기열에 진입하자마자 거의 즉시(다음 스케줄 틱 안에) PROCESSING으로 승급된다.

## 4) PROCESSING 토큰 — 30초 TTL

승급될 때 `ProcessingQueueCoreRepository.enqueue`가 두 가지를 한다:
- `cache(token, ttl=30초)` — redis-service에 String 키로 캐싱 (`processing-queue.policy.token-expiry-as-seconds: 30`)
- `increment(PROCESSING_QUEUE_COUNTER)` — 원자적 카운터 +1

이때부터 유저는 **30초 안에** 좌석 선택 → 임시예약 → 결제까지 끝내야 한다. 다른 서비스가 `X-Queue-Token` 헤더로 요청이 올 때마다 `ProcessingQueueTokenController`가 이 캐시 존재 여부로 유효성을 검증한다 — 캐시가 있으면 통과, TTL이 지나 캐시가 사라졌으면 404 계열로 실패한다. 실제로 UI를 손으로 클릭해가며 테스트했을 때 결제 단계에서 "토큰 만료" 에러를 겪었는데, 정확히 이 지점이었다.

## 5) 만료 감지 — Redis keyspace 이벤트 + 배치 처리

TTL이 자연 만료되면 Redis가 keyspace 이벤트를 쏘고, `RedisKeyExpiredListener`가 이걸 받는다:

```java
@Async("redisKeyExpiredListenerExecutor")
public void onMessage(Message message, byte[] pattern) {
    String expiredKey = new String(message.getBody());
    expiredKeysQueue.put(expiredKey);   // 일단 큐에 쌓아둠
}
```

그리고 별도 스케줄러가 1초마다 돌면서 **10개씩 모이면** 배치로 처리한다:

```java
while (expiredKeysQueue.size() >= BATCH_SIZE) {  // BATCH_SIZE = 10
    List<String> keys = ...;  // 10개 꺼냄
    processingQueueFacade.completeTokens(expireCommand(keys));  // 카운터를 batch size만큼 DECR
}
```

이건 토큰 단위 상태 전이가 아니라 **카운터를 그냥 batch size만큼 까는 방식**이다. 두 가지 허점이 있다:
- 멱등하지 않음 — 같은 만료 이벤트가 두 번 오면 카운터가 실제보다 더 깎임
- 만료 키가 10개 미만이면 한동안 반영이 안 됨 (배치가 안 차서 flush가 안 일어남)

## 6) 완료 처리 — 정상 경로 vs 안전망, 그리고 죽은 Kafka 코드와의 연결고리

`ProcessingQueueService`엔 만료 처리(`completeTokens`, 복수, 배치)와 별개로 **정상 완료 처리**(`completeToken`, 단수)가 따로 있다 — 결제가 성공하면 30초를 다 기다릴 필요 없이 그 자리에서 캐시를 지우고 카운터를 -1 해서 슬롯을 즉시 반납하라는 의도다. 이건 `concert-reservation-payment` Kafka 토픽의 컨슈머(`QueuePaymentEventHandler.handlePaymentCompleteEvent`)가 호출하도록 설계돼 있다.

**근데 이 토픽에 발행하는 코드(`PaymentFacade`의 `applicationEventPublisher.publishEvent(...)`)가 주석 처리돼 있다.** 그 말은 지금 이 시스템에서는 **결제에 성공한 사람도 즉시 슬롯이 반납되지 않고, 무조건 30초를 다 채우고서야 TTL 만료로 반납된다**는 뜻이다. 트래픽이 몰리는 상황을 가정하면, 결제 완료자가 불필요하게 슬롯을 붙잡고 있어서 신규 승급이 그만큼 늦어지는 처리량 손실로 이어질 수 있다 — 별개로 발견했던 "Kafka 발행 죽은 코드" 하나가 대기열 시스템의 실제 슬롯 회전율에도 영향을 주고 있었던 셈이다.

## 발표용 토론 포인트

- 토큰을 왜 랜덤 UUID가 아니라 `hash(userId+secret)`으로 만들었을까? 멱등성 vs 예측 가능성(위조 가능성)의 트레이드오프를 어떻게 볼지.
- WAITING → PROCESSING 승급을 "폴링 스케줄러(1초마다 조회)" 대신 이벤트 기반으로 짰다면 어떻게 달라졌을까? (Redis Pub/Sub으로 슬롯 반납 알림을 받아 그 즉시 승급하는 방식과 비교 — [[Redis Pub_Sub 신호 유실을 List 폴링으로 방지하는 원리]] 참고)
- 만료 카운터 배치 처리(10개 단위)를 멱등하게 고치려면 어떻게 설계해야 할까? (예: 만료 처리 완료 여부를 토큰별로 마킹하거나, 카운터 대신 실제 멤버 존재 여부를 세는 방식)
- 이 시스템의 "선착순 대기열" 설계를 올리브영 사례([[올영세일 선착순 쿠폰, 미발급 0%를 향한 여정]])와 비교하면 어떤 차이가 있을지 — 특히 동시 접속 폭주 상황 대비 여부.

## 한 줄 정리
> 대기열은 Redis ZSet으로 순서를 매기고, 1초마다 도는 스케줄러가 빈 자리만큼 앞사람들을 PROCESSING(TTL 30초)으로 승급시키는 구조다. 정상 완료 시 슬롯을 즉시 반납하는 경로가 있긴 한데 그 트리거(Kafka 발행)가 죽어있어서, 지금은 모든 유저가 성공하든 실패하든 30초를 꽉 채우고서야 슬롯이 풀린다.
